# 主张↔测试映射(X-2)

> 状态:**设计 + 已落地(首批 12 条)**。第七轮复核的横切建议之二:把 `guard-cli coverage`
> 那套"声明必须对着仓库核实、无依据的声称是错误"的纪律,从**学术攻击面**扩到**面向用户的能力
> 声明**——商店文案、平台能力矩阵、路径模型、端点表里那些"我们能做 X"的话。

## 为什么要有这份文档

这个项目反复抓到的一类缺陷,形状都一样:**一句话声称的能力,比它背后的代码强。** 平台矩阵曾经
说 Android 的 Critical Confirm "✅(notif)",而那条通知权限声明了却从不在运行时申请;商店文案
可以写"签名、防篡改的审计",而"防篡改"到底被哪条测试证明过,没人拴得住。`guard-cli coverage`
已经把这条纪律用在攻击面上:每个 surface 声称的规则必须存在、场景必须通过、而且必须**真的命中**
那条规则,否则命令失败。

X-2 是同一招换一个对象:**面向用户**的声明。区别在于对象不是论文攻击面,而是用户读到的承诺;
不变的是那条原则——**一句对外的能力声明,必须能指着一段代码说"这是兑现它的",并指着一条测试
说"这证明它真的会触发";做不到的声称是错误,不是待办。**

## 被机器核对的是什么(以及**不是**什么)

映射表在 `eval/capability-claims.yaml`,核对逻辑在 `crates/guard-eval/src/capability_claims.rs`,
入口是 `guard-cli capability-claims`(已进 `make capability-claims` 和 release-gate)。

每条声明登记四样东西:一句 `claim`、它印在哪(`source.doc` + 一段 `source.anchor` 锚文本)、
由哪段代码兑现(`mechanism`)、由哪条(些)测试证明(`proven_by`:测试函数名 + 源文件)。

核对**两件硬事实**,任一不成立就是错误:

1. **声明真的印在那份用户可见的文档里。** `source.anchor` 必须作为子串出现在 `source.doc`。
   这挡住两个方向的漂移:映射表声称"我们宣传了 X"而文档里根本没有 X;以及文档改了措辞、悄悄
   把某条能力删了,而映射表还挂着它。
2. **每条证明测试真的存在。** `proven_by` 里每条 `fn <名>(` 必须出现在它声明的源文件里。删掉 /
   改名一条证明测试而不更新映射,就红——和 `coverage.rs`、X-1 的入站面清册是同一个钉子。

**不**被机器核对的是 `mechanism`(哪段代码兑现)。它是描述性的,和 `coverage.rs` 的 `mechanism`
一样。把它也做成"符号必须存在于文件里"会给一层**假精确**:一个函数改了名不代表那条能力没了,
真正钉住"能力还在"的是那条**测试**是否还在、是否还绿。所以这份映射把机器信任只押在两处它能
可靠判真伪的地方,其余留给人读。

### 一条派生纪律:锚文本要**具体到这条能力**

锚不能选泛词(选 "audit" 就几乎永远命中,等于没核对),要选一段**只有做出这条承诺时才会写**的
措辞(如 `"signed, tamper-evident audit trail"`、`"label + icon dHash"`)。这样"文档不再这么说了"
才会真的让它红。这条是 `coverage.rs` 里"覆盖必须是规则**被命中**、不只是**存在**"的同款要求:
让核对贴着语义,而不是贴着字符串的存在性。

## 边界(如实)

- **这张表不能自动发现"你又对用户承诺了一件事却没测"。** 那需要从文档里做自然语言抽取,超出
  范围。它是**人工维护**的清单;它保证的是**已登记**的声明其证明测试不被悄悄摘掉、其文案不被
  悄悄改没。加一条新的对外承诺时,得**主动**把它登进 `eval/capability-claims.yaml` 并配测试——
  这条边界是显式的,和 X-1 入站面清册、`coverage.rs` 语料库同一性质。
- **`mechanism` 不被核对**(见上)。它对不上现实不会让门禁红;要防它漂移,靠的是那条测试。
- **端点表另有专门的一致性测试。** `/v1/*` 路由与 `docs/local-api.md` 端点表的一致由 P2 的
  `端点表与实际路由一致` 直接比对,比锚文本更强,所以端点没有重复登进这张表。

## 残余(尚未映射的用户声明)

诚实列出这张表**还没**兜住、但文档里确实对用户说了的能力,作为后续排期:

- **平台矩阵里带 🟡 限制标注的格子**(Windows overlay 只覆盖自绘、Android/浏览器 Critical 只事后
  通知、Chromium 仅语法编译),它们的"限制"本身是承诺的一部分,值得各配一条"限制确实存在"的
  测试(部分已有 note 兜底,但未进机器核对)。
- **隐私文案**("默认不上传浏览历史""发现默认留在本地"):需要一条证明默认路径不外发的测试,
  目前是配置断言而非端到端证明。
- **iOS 行**:文档已如实写成全 ❌ / "none",没有能力可兑现,所以也没有可映射的正向声明——这是
  一条"声明为空"的诚实,不是缺口。
- **各平台打包/CI 声明**(如"macOS 3 packaging tests"):属于构建产物层,和能力语义正交,单列。

这些不是被忽略,是被点名地留在表外,好让"表里 12 条都绿"不被误读成"所有对用户的承诺都兜住了"。
