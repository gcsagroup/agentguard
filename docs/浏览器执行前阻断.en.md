# Pre-Execution Browser Blocking (E2)

> Status: **Implemented for in-page vectors**. The Chromium extension has been upgraded from post-event
> notification to pre-execution interception—but only where it can **actually reach**, with explicit boundaries.

## Why post-event notification cannot become pre-execution blocking without moving position

By the time `background.js` receives the host’s decision, the DOM event **has already happened**. Native messaging
is asynchronous, so the host sees the event afterward and nothing can hold it. This is not an implementation
shortcut; it follows from where the observer sits. An observer cannot stop the thing it has already observed.

E2 therefore **moves the interception point** into the **content script**, which runs synchronously on the page. A
capture-phase `submit` / `click` listener can call `preventDefault()` **before the action actually happens**, show a
local confirmation, and programmatically replay the action only after the user selects “Allow once.” This path does
not make the asynchronous host round trip, so it can genuinely hold the action.

## What is blocked

During the capture phase, the content script (`content.js`) synchronously evaluates two classes of page-owned action.
The decision logic is in the pure module `guard-gate.js`:

| Trigger | Criterion | Action |
|---|---|---|
| Form `submit` | A “trap control + nonessential PII” has been filled in the form | preventDefault → local confirmation → replay once with `requestSubmit(original submitter)` when allowed |
| `click` / `submit` | Target is a payment/transfer CTA (copy match) | Same as above |
| **Page-originated `fetch` / `XHR`** | URL path has a payment shape (pay/checkout/charge/transfer…) and the method is not read-only | Page-world wrapper (`guard-page.js`) awaits confirmation before sending; rejection causes reject/abort (E2.1) |
| Network request / navigation | The **engine** classified the host as malicious (`INTEL-DOMAIN`) | Host adds it to response `block_hosts`; `background.js` installs a declarativeNetRequest rule that blocks before sending (E5) |

The first two classes are page DOM actions synchronously intercepted by the content script. The third is handled at
the network layer by DNR, the correct MV3 API for blocking before a request is sent. Each interception is sent to
background with `sendMessage`, placed in the recent list, and forwarded to the host for the signed audit trail. A
pre-execution block is an event that deserves a record just like a decision.

## What this covers and **does not** cover

Covered: the page’s **own** DOM submissions/clicks (payment CTA and PII submission under a trap), plus navigations
and requests that match the host blocklist.

**~~Scripts that call fetch()/XHR directly~~ E2.1 adds this, when it can get there first.** Page-world
`guard-page.js` wraps `window.fetch` and `XMLHttpRequest`, awaiting confirmation before sending outbound requests
whose paths look like payments. It still **does not** cover:

- a script that captured the original `fetch` reference before us (earlier than `document_start`, or borrowed from a
  clean iframe). In MAIN world, the page and extension have equal standing and either can modify `window.fetch`, so
  this is **best effort**, not an impenetrable wall;
- request bodies. The criterion examines only a payment-shaped URL path because bodies vary by site and create high
  false-positive risk; false blocking makes users disable the gate more readily than a miss. It blocks direct
  requests that look like payments, not all outbound traffic;
- actions inside cross-origin iframes (the manifest runs the content script only in the main frame);
- **actions in any native app**, which a browser extension cannot reach.

In short, this gate stops “completing this step on this page,” not “any network access on this machine.” Blocking
all outbound access to a host belongs to the host-based DNR layer and Linux jail’s kernel, port-based `scope.net`
(E1), not this layer.

### E5: Engine decision → hard browser network block (connecting the two layers)

The DNR row previously meant “if the host decides to block a host,” but **nothing generated that list**;
`block_hosts` was an unwired connection. E5 wires it up. The engine already decides that a URL’s host is malicious
(`is_malicious_domain` → an `INTEL-DOMAIN` Block decision). The host (`guard-nm-host`) now extracts that hostname
from the decision, puts it in response `block_hosts`, and `background.js` installs a DNR rule. The chain is closed:
**engine declares malicious → browser hard-blocks the next request to that host before it is sent**, rather than
merely showing a post-event notification.

Hostname extraction uses a **shared contract** (`guard_schema::INTEL_DOMAIN_RULE_ID` +
`MALICIOUS_DOMAIN_MSG_PREFIX`). The producer (guard-core decision) and consumer (nm-host parser) reference the same
constants, so wording changes update both sides and are caught at compile time instead of making one parser silently
return nothing. It accepts only structured `INTEL-DOMAIN` rule_id and takes only the first word after the prefix
(hostnames contain no whitespace, so the gate-appended “ (user denied…)” suffix is naturally removed). This pure
extraction function has unit tests including negative cases: another rule_id, no prefix, and a gate suffix that must
still produce only the hostname.

**E7 extension: block not only “known malicious” hosts, but also destinations this task should never visit.** In
addition to malicious domains, the engine decides when a destination exceeds the task-declared `scope.hosts` ceiling
(`SCOPE-HOST` Block). These hosts now also enter `block_hosts` through the same shared-prefix contract
(`SCOPE_HOST_RULE_ID` + `SCOPE_HOST_MSG_PREFIX`; the hostname is between two `'` characters, while sentinel
`<unnameable>` is excluded). A critical security property is **inherited from the engine**: `check_scope_host` emits
this rule **only when the task declares `scope.hosts`**. No declaration → no rule → no block, so an unconfigured
scope never blocks normal browsing. Declaring `hosts: []` explicitly means “no network access” and blocks all
outbound destinations.

### E8: Blocklist accumulation semantics (retain malicious hosts; expire out-of-scope hosts with the session)

The first E5 version had a weakness: each decision batch made `installBlockedHosts` **replace the entire** dynamic
rule set. A malicious host was therefore cleared by the next benign decision with empty `block_hosts`, making a hard
block survive only until the next clean decision. E8 gives host categories different lifetimes:

- **`malicious` (known malicious domain): retained cumulatively** and persisted in `chrome.storage` across service-
  worker restarts (then reinstalled). A `MAX_PERSISTENT` limit respects the DNR dynamic-rule quota; the oldest entry
  is removed when the limit is exceeded.
- **`out_of_scope` (outside task scope): expires with the session** (removed by default after 30 minutes without a
  renewed out-of-scope decision). It is **task-relative** and must not permanently block normal access to that host.
  A task that did not declare booking.com does not imply that the user can never visit booking.com again.

Merging and expiry are pure function `guard_gate.mergeBlocklist`, covered by six node unit tests: malicious hosts
accumulate rather than being cleared by benign decisions; out-of-scope entries expire; another decision refreshes
expiry; an entry that is both malicious and out of scope becomes persistent; and the persistent-list limit holds.
`nm-host` now gives each `block_hosts` item a `kind` (`malicious` / `out_of_scope`), which `background.js` uses to
separate them.

**Explicit limitations:**
- DNR is fail-open: installation failure is recorded and not misrepresented as a block, avoiding loss of all browser
  networking. Real Chrome/Firefox E2E has not been validated.
- Session expiry is driven by **time**, without a strong “session ended” signal. An out-of-scope entry can therefore
  live for up to one TTL rather than ending at the exact session boundary.
- The malicious-domain list comes from the built-in intelligence baseline. Pre-release `intel-keygen` key rotation
  remains tracked in `docs/发布阻塞项.md`.
- **Trigger-surface boundary:** malicious-domain checks apply to any event with a `url`, including browser `ui_text`,
  so malicious-domain → DNR works immediately on the browser path. `SCOPE-HOST`, however, applies only to **network
  flow / data-exfiltration** events. The engine deliberately does not treat “reading a page” as “sending to it”; see
  the `check_scope_host` comment. The browser extension currently sends `ui_text`, not network-flow events, so the
  complete out-of-scope → DNR loop awaits browser network-flow reporting. **The extension deliberately does not send
  every outbound URL to the host**, because doing so would violate the privacy baseline that findings remain local
  by default. E7 completes the **generic** engine/host bridge—any out-of-scope decision feeds DNR—and Android/desktop
  network-flow events can already drive it. The pure-browser `ui_text` segment remains explicit residual work.

### E9: Send the task allowlist to the browser for local scope checks (without returning URLs)

E7 completed the generic engine/host bridge but left a residual: pure-browser `ui_text` does not trigger
`SCOPE-HOST`, while the extension **deliberately does not send every outbound URL to the host** because findings must
remain local by default. E9 closes the loop in the opposite direction: **send the allowlist to the browser** and
evaluate scope **locally**.

- The `nm-host` response carries `scope_hosts`, a **snapshot** of the current session’s authorized `scope.hosts`
  (exposed by the new engine method `granted_hosts()`). This is **policy**, not browsing history: the host sends a
  table of “where you may go” and receives no URL describing “where you went.”
- `background.js` stores it in `storage`; `content.js` sends it to page-world `guard-page.js`; and the fetch/XHR gate
  locally calls `scopeGateHost(host, allowlist)` for each outbound destination. A destination outside the allowlist
  receives the same confirmation as a payment-shaped request.

The security-critical detail is that JS `hostInScope` mirrors Rust `host_in_scope` and **must reject the same suffix
spoofs** (`stripe.com.evil.example` is not a subdomain of `stripe.com`). Semantic drift could let JS allow a
destination that Rust blocks. The node test `hostInScope_对齐Rust拒绝后缀伪造` pins down these spoof cases.

The properties inherited from E7 remain: missing `scope_hosts` (not declared) → no local block; `[]` (explicitly no
network access) → block all. **Explicitly:** this is a MAIN-world client check and, like the fetch gate, is best
effort because the page can modify `window.fetch`. It supplements, rather than replaces, kernel-layer jail
`scope.net` (E1) and engine decisions (E5/E7). Allowlist liveness depends on the session declaring `scope.hosts`.

### E10: Popup management surface (visible + removable)

The cumulative E8 list is now visible in the extension popup. It lists currently blocked network destinations,
distinguishes cumulative “malicious domains” from session-relative “outside task scope,” and gives each an “Unblock”
button. `background.js` messages `get_blocklist` / `unblock_host` support reads and deletion, immediately reinstalling
DNR afterward. **E12 provenance:** each entry also displays its “triggering rule” (`INTEL-DOMAIN` / `SCOPE-HOST`).
Every `nm-host` `block_hosts` item includes `rule_id`; background persists it in a provenance mapping with the list;
and the popup shows it on the second line, making the reason a host was blocked immediately visible. This is
usability, not a security capability, so it is **not included** in X-2 claim-to-test mapping, which includes only
capability claims backed by proof tests. Correctness relies on the tested E8 pure logic in `mergeBlocklist`. The UI
itself follows the repository invariant of sink-free DOM construction (`createElement` + `textContent` +
`addEventListener`, without innerHTML).

### E2.1 failure directions

- Payment-shaped request → **hold for confirmation**: `fetch` returns a Promise awaiting the decision and rejects on
  refusal; `XHR` does not actually `send` before confirmation and calls `abort` on refusal. When the page does not
  interfere with the message channel, nothing is sent before “Allow once.”
- No content-script response within 15s (an extreme case) → **fail-open allow**, as declared. This layer is additive
  and must not cut off normal requests because it became stuck. The real defense is layered, not this single point.
- **The MAIN-world channel is not a security boundary.** The request gate and isolated world exchange
  `REQ`/`DECISION`/`SCOPE` over page-observable `window.postMessage`. A hostile page can forge allow or scope messages
  and can see the delivered host allowlist. E2.1/E9 are therefore best-effort interlocks for cooperative pages, not
  defenses against an actively adversarial page; only extension-controlled DNR is a network enforcement boundary.

## Failure direction: the two gates point in **different** directions by design

- **Synchronous content-script gate: fail-closed tendency.** If decision logic is not loaded
  (`self.AgentGuardGate` is absent), `gateEvent` returns without changing page behavior; it does not pretend to block
  under uncertainty. More importantly, when it does intercept, it **really does** intercept because preventDefault
  has already executed and it does not depend on any asynchronous response.
- **DNR network gate: fail-open, explicitly.** If DNR installation fails, the failure is recorded and not
  misrepresented as a block. It deliberately is not fail-closed: an extension unable to reach DNR must not make the
  entire browser lose network access. It adds a layer to the synchronous content-script gate and is not the only
  defense.

This is written down because an undeclared fail-open point is as dangerous as assuming everything is fail-closed.

## Validation status (honestly stated)

- **Decision logic** (`guard-gate.js`: which finding kinds are blocked and how DNR rules are built) is pure. Twenty
  node unit tests in `scripts/gate.test.mjs` include negative cases (ordinary findings are not blocked, preventing
  the gate from becoming noise) plus DNR deduplication, ordering, and stable IDs. They are included in
  `make check-extension-gate` and release-gate.
- **DOM wiring** (capture listeners and replay in `content.js`) has syntax coverage plus two minimal event-chain tests
  in `content-event.test.mjs`, covering one prompt/submission across click→submit and non-leaking approval tokens.
- **Real Chrome end-to-end behavior has not been validated.** Whether a real payment submission is held and whether
  “Allow once” replays it with precisely equivalent behavior have not been tested on a real device. This is the same
  honest boundary as the jail syscall path and macOS AX push: testable pure functions pin down the security logic,
  while platform wiring is explicitly marked as unvalidated in the real environment.
