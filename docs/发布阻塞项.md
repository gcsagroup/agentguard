# 发布阻塞项清理

上一轮结束时列了五条"上线之前必须处理"。这份文档逐条记录**判断**和**实际做了什么** ——
判断本身比结论重要:其中两条我判定是可接受的已记录限制,另外三条不是。

分辨标准只有一条:**这条限制,能不能被一个不读文档的运维踩到,而且踩到的时候它是在
"授予"方向上?** 是的话就是真阻塞。这个标准来自本项目反复出现的第一种缺陷形状 ——
攻击者可自行断言的输入被用在授予方向上。

---

## 1. 发布注册表里的夹具密钥 —— **真阻塞,已修**

`policies/agent-registry.yaml` 为 `claude-desktop` 和 `shopping-helper` 钉了两把
Ed25519 公钥,它们的私钥是单字节重复的种子(`0xa1`、`0xb2`),仓库里就有。

原先的处理是文档:文件顶部有整整一段横线框住的 `FIXTURE KEYS` 告示,说清了
"真实部署请替换",还写了"一个钉了公开私钥的注册表比没有注册表更糟,因为它会验证一个
任何人都能产生的签名"。

**那段话是对的,而它没有拦住任何东西。** 一个运维照抄示例注册表、再按
`docs/agent-identity.md` 打开 `require_attestation`,得到的就是:任何本机进程都能为
`claude-desktop` 伪造出一个**验签通过**的 attestation,而验签通过会设置
`attested_session`,也就是在授予方向上。

### 做了什么

不是加更多文档,是让判决层认出这种密钥:

- `guard_schema::PUBLICLY_KNOWN_AGENT_KEYS` —— 一张硬编码的表,(公钥, 出处)。
- 新的判决 `AgentIdentity::PubliclyKnownKey` → `AGENT-KEY-PUBLICLY-KNOWN`。
  检查放在**验签之后**:签名错的照样报 `AGENT-BAD-SIGNATURE`(那是更准确的诊断),
  而且不消耗 nonce —— 这个身份没被确立,不该占用重放窗口。
- 语义等同于 `NoKeyOnRecord`:不是 `Verified`,也不是"冒充"(签名确实有效,
  它只是不构成证据)。`require_attestation: false` 时会话照走,打开后被拒。失败是关闭的。

### 三条互相咬住的测试

| 测试 | 守的是什么 |
|---|---|
| `公开密钥表确实是那些种子推出来的` | 那张表不是两个魔法字符串。改错一个字符,机制静默失效,而所有"夹具密钥被拒"的测试仍然会过 —— 它们用的是同一个错字符串。 |
| `发布注册表钉的密钥必须全部可被识别为夹具密钥` | 以后有人往示例注册表加一张新卡配一把新夹具密钥、忘了同步那张表,那把钥匙就变成一把**真能验签**的钥匙,而私钥在同一次提交里。 |
| `评测注册表的密钥必须不在公开密钥表里` | 反方向。哪天有人把评测密钥也加进那张表(看起来更"安全"),`AGENT-REPLAY` 和 `AGENT-TASK-NOT-PERMITTED` 就再也跑不到了 —— 它们都在 `Verified` 的下游。 |

第三条是这次清理里最值得记下来的一件事:**把一个安全检查加得更严,可能把另一个安全
检查的覆盖删掉。** 加上 `PubliclyKnownKey` 之后,评测语料里两个场景立刻从
`AGENT-REPLAY` / `AGENT-TASK-NOT-PERMITTED` 改判成了 `AGENT-KEY-PUBLICLY-KNOWN` ——
仍然是"拦住了",所以断言"必须拦住"的测试仍然全绿,而那两条攻击路径已经没人在跑了。

修法是把评测和发布分开:`eval/fixtures/agent-registry.yaml` 用自己的密钥
(种子 `0x11` / `0x22`),四个场景的签名重新生成。这也更接近真实 —— 真实部署也用
自己的密钥。

### 边界说清楚

那张表管的是 **`policies/` 下面**钉的密钥,因为那是运维会照抄的目录。单元测试和
`eval/fixtures/` 里的私钥同样是公开的,它们不在表里,所以"验签通过 ⇒ Verified"
这条路径仍然有覆盖。这个边界是刻意的,两个方向都有测试守着。

## 2. `api-serve` 的 bearer 令牌默认 `dev-secret` —— **真阻塞,已修**

代码本身没问题:不传 `--token` 时 `resolve_api_token` 生成 `ag_` + 32 位十六进制。
问题在两个人写的地方:

- `Makefile` 的 `api-serve` 目标:`--token $${AGENTGUARD_API_TOKEN:-dev-secret}`
- `docs/local-api.md`:`export AGENTGUARD_API_TOKEN='dev-secret'`

也就是说,任何**照文档跑起来**的部署,令牌都是一个写在公开仓库里的字符串。文档同时
是问题的来源和它的说明书。

后果不小。这个 API 上:`POST /v1/pause` 能把守卫停掉,`POST /v1/confirm` 能替人回答
确认框。猜到令牌 = 绕过整个产品。而且服务器没有速率限制,一个本机进程可以按网络速度试。

### 做了什么

- `api_token_weakness()`:短于 24 字符,或命中一张公开示例值表(`dev-secret`、
  `changeme`、`password`……),不区分大小写、去首尾空白。
- 检查放在 `serve()` 里,**不是** `resolve_api_token()` 里 —— `serve` 才是唯一必经
  之路,放在解析函数里的话任何直接构造 `ApiConfig` 的嵌入方都绕过去了。
- 弱令牌**拒绝启动**,而且是在 `bind` 之前(有测试从外面确认那个端口是空的)。
- 明确的覆盖口子 `--insecure-token`。留这条口子是刻意的:一个没有覆盖路径的检查,
  最终会被整个删掉。
- `agentguard api-token` 打印一个强令牌。存在的理由很实际 —— 必须有一条比
  "自己想一个"更短的路,否则运维会去加 `--insecure-token`。
- Makefile 的硬编码默认值删了;`docs/local-api.md` 改了。

错误信息会**点名** `dev-secret`("本项目文档里的示例值"),而不是只报"太短"。
看到"太短"的人会去加长它;问题不在长度。

`ApiConfig::insecure_token` 没有默认值,每个调用点都要自己写出这个选择。

## 3. MSRV 未钉 —— **真阻塞,已修(而且是测出来的)**

`Cargo.toml` 里既没有 `rust-version`,也没有 `rust-toolchain.toml`。谁都不知道底线
在哪,直到某个用户的 CI 炸掉。

没有直接写"最新 stable"。一个只在最新 stable 上能编的安全产品,等于要求运维在装守卫
之前先升级工具链。

### 做了什么

装了几条旧工具链实际跑:

| 版本 | 结果 |
|---|---|
| 1.82 | 编不过 —— `clap_lex` 需要 `edition2024` |
| 1.85 | 编不过 —— `icu_*` 声明需要 1.86 |
| 1.86 | 编不过 —— `guard-privacy` 的 Luhn 校验用了 `is_multiple_of`(1.87 稳定) |
| **1.87** | **`cargo test --workspace` 全过** |

所以 `rust-version = "1.87"`,并传播到每个成员。`make check-msrv` 用 1.87 重跑整个
测试集,CI 里也是一个独立 job —— 因为 `Cargo.toml` 里那一行只是**声明**,声明不是执行:
没有这个 job,任何人用了一个 1.88 才有的 API,MSRV 就静默抬高一格,而所有测试仍然
全绿,因为大家都在 stable 上跑。

## 4. `require_attestation: false` 默认关闭 —— **可接受的已记录限制**

判定它不是阻塞,理由是**方向**:它关着的时候,少的是"没有出示签名的会话会被拒"这一条;
伪造和重放的 attestation 两种模式下都会被拒。也就是说,它不在授予方向上。

而打开它会怎样:目前没有任何已发布的适配器会签会话,所以打开等于拒掉每一个会话。
一个装上去就把所有东西拦死的守卫会被立刻卸掉,那时保护是零。

> 这是本项目反复撞到的设计教训:**把"更严"当成"更安全"本身就是一种失效模式。**

所以它保持关闭,但不再只写在文档里 —— `agentguard preflight` 会把它作为 WARN 打出来,
并说清打开的前置条件。

## 5. 发布产物未验证 —— **部分可修,剩下的是已记录限制**

分成两个问题,原先混成一个:

**能修的:字节一致性。** `scripts/release-manifest.sh` 对每个产物算 SHA-256,写出
`SHA256SUMS`,`sha256sum -c` 可核对。

**修不了的:来源。** 本项目没有代码签名身份(没有 Apple Developer ID、没有
Authenticode 证书、Android 用的是调试签名)。checksum 答不了"这个文件真的来自
AgentGuard 吗"。

脚本自己会把这条限制打印出来,包括最关键的那一句:**如果 checksum 和产物放在同一个
页面上,攻击者改了产物顺手就把 checksum 也改了** —— 这份清单必须走一条独立渠道。
把这条说清楚,比装作有签名更有用。

## 6. 计费 webhook 未认证 —— **真阻塞,已修(第七轮复核)**

`POST /webhook/billing` 对原始 body **没有任何签名校验**,而 `apply_webhook_event` 会直接用
本地密钥从 payload 里自铸并激活授权令牌。判据全中:一个**不读文档的运维**把这个接收端暴露
出去,任何人一个匿名 POST `{"type":"purchase","plan":"enterprise"}` 就自授 Enterprise ——
未认证输入,用在**授予**方向上。

当时之所以还没被利用,是因为授权本身是装饰性的(没有功能读那些 flag)。但那是两个洞叠在一起
互相遮蔽:一旦授权接进真正的功能门(见下),这个 webhook 就是现成的绕过口。所以两个都修。

### 做了什么

- **webhook 认证**:`AGENTGUARD_WEBHOOK_SECRET` + `X-AgentGuard-Signature: sha256=<HMAC-SHA256
  (secret, 原始 body)>`,常数时间比较;缺头/对不上 → 401。**没设密钥 → 拒收所有 POST(503,
  fail-closed)** 并在启动时告警。HMAC 用已有的 sha2 手写标准构造,不引新依赖。
- **授权真门控**:`audit-export` 现在由 `enterprise_export` 门控(`allows_enterprise_export`),
  Free / Pro / 过期都被拒 —— 这是授权第一处真正影响行为的地方,授权不再是纯装饰。

### 测试

`签名验证拒绝伪造`(篡改 body / 错密钥 / 缺头都拒)、`health_and_signed_purchase_via_http`
(无签名 401、正确签名 200)、`enterprise_export门控`(Free/Pro/过期拒、Enterprise 放行)。
变异验证:签名恒真 → 拒伪造测试红;门控恒真 → 门控测试红。

### 一条如实的残余

另两个 flag(`unlimited_audit`、`custom_rules`)目前仍未门控 —— `docs/billing.md` 已如实标注,
不该让读者以为它们已强制。接真实 provider 时,`AGENTGUARD_WEBHOOK_SECRET` 的 HMAC 换成
provider 各自的签名方案,但**签名校验这一步不能省**。

## 附带修掉的两个真 bug

清理过程中新写的 `agentguard preflight` 立刻抓到了一个,另一个是 clippy 全量门禁
暴露的。两个都属于本项目的第二种缺陷形状 —— **机制没有接到它被调用的那个入口上**。

### `guard-jail` 的后端探测有假阴性

`mountns::can_unshare()` 原来的写法是
`Command::new("/proc/self/exe").arg("--jail-probe-unshare")`,靠 `agentguard-jail` 的
`main` 认出这个参数、在子进程里 `unshare`、用退出码回答。

从 `guard-cli` 调用时,子进程是 `guard-cli`,它的 clap 解析器不认识这个参数,以非零码
退出 —— 探测把它读成"这台机器不支持 mount namespace"。

于是 `agentguard preflight` 的第一次运行就告诉我:"这台机器上没有可用的内核约束后端",
而同一台机器上 `agentguard-jail --probe` 报的是"可用"。方向比一般的假阴性更糟:
**它让人以为自己没有保护,而不是以为自己有。**

现在的写法完全不依赖二进制是谁:`pre_exec` 在 fork 之后、exec 之前跑,它在子进程里
`unshare`,然后**故意**返回一个哨兵 errno,于是 exec 永远不发生(那个程序路径也就不
需要存在)。std 把这个 errno 通过管道送回父进程。哨兵 = 可用,其它 errno = 原因。

`agentguard-jail` 里那个隐藏参数删掉了。回归测试就跑在 lib test harness 里 ——
一个**不是** `agentguard-jail` 的二进制,正是原来会失败的场景;断言查的是失败理由的
**形状**(有 errno,没有 usage / unexpected argument),所以在真的不支持 namespace 的
机器上也能过。

### `cargo clippy --fix` 删掉了一个只有 macOS 用的导入

`adapters/mac-adapter/src/ax_native.rs` 里有 `use std::ffi::CStr;`,只被两处
`#[cfg(target_os = "macos")]` 的代码用到。在 Linux 上它确实是未使用的导入,
`--fix` 就把它删了 —— 一个**只在 macOS 上出现**的编译失败,从 Linux 完全看不见。

和更早那次 `NativeWinAdapter` 不是 `Send` 是同一形状:**跨平台 crate 的自动化只对它
当前能编译的那个平台负责。**

修法有两部分。导入加上 `#[cfg(target_os = "macos")]`,两边都对。更重要的是
`scripts/check-macos-paths.sh`:把源码复制一份,把 `target_os = "macos"` 全部改写成
`target_os = "linux"` 再编,于是那半边代码在 Linux 的 CI 上第一次真的被编译过。

这个脚本自己也验过不是空的:删掉那行导入,它报 `cannot find type CStr`;加回去,通过。

它能查到编译期的一切(缺导入、类型、借用、`Send`/`Sync`),查不到 Objective-C 那侧、
framework 符号和真机行为 —— 那些只有 macOS 能验。所以它不是"macOS 构建通过"的替代品,
它是把"从来没编译过"变成"编译过"。

## `agentguard preflight`

这次清理里出现的一个变体:代码确实有那个性质,但只写在 YAML 注释和 `docs/` 里,
而运维不读它们。所以加了这个命令。判据是:

> **一条限制,如果只有读文档的人才知道,就等于不存在。**

它只看**配置** —— 打开的这一套策略文件,能不能支撑运维以为自己买到的那些保证。
九组检查(在仓库自带的这套配置上产出 13 条结论),四档结论:

- `PASS` —— 这条保证成立。
- `INFO` —— 一个陈述句,不是问题。单独一档是必要的:合作式网关"可被绕过"是**设计**,
  把它印成 WARN 会让运维去找一个不存在的修法,并且学会忽略 WARN。
- `WARN` —— 能跑,但少了一个运维大概以为自己有的保证。
- `FAIL` —— 部署是坏的,或者有一个陷阱在等着被踩。退出码 1,可直接当 CI 门禁。

每一条 `WARN` / `FAIL` **必须**带一个下一步,有测试守这个不变量:一个没有修法的告警,
运维唯一能做的就是忽略它;忽略够几次之后,整份报告都不再被读。

仓库自带的这套策略**报 FAIL** —— 因为它就是不该上线的(发布注册表钉的是夹具密钥)。
`仓库自带的策略自检不通过` 这条测试守着这件事:"照着仓库跑"和"可以上线"之间必须有
一个能被看见的差别。哪天有人把它改成期望 PASS,那就是把陷阱又埋回去了。

## 这一轮的门禁

```
make check              # clippy(-D warnings)+ 617 项测试 + 三个评测门 + macOS 代码路径 + 自检
make check-msrv         # 用 1.87 重跑整个测试集
make check-windows      # x86_64-pc-windows-msvc 目标 + clippy -D warnings
make check-jail         # 探测后端,再跑内核约束的集成测试
make check-macos-paths  # macOS 专属代码路径能通过 rustc
make check-android      # Android SDK,真的产出 APK
make release-manifest   # 发布产物的 SHA-256 清单
```

CI 九个 job:`test`、`windows`、`macos-shell`、`android`、`jail`、`macos-paths`、
`msrv`、`preflight`、`frontend`。
