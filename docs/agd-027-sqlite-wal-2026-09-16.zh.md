# AGD-027：持久同步定位与 SQLite WAL 修复

日期：2026-09-16。源码基线：`b5980082944ed2153706ba5809f9483cacad22b9`。本批先定位同步开销，随后发现数据库依赖位于上游 WAL-reset 缺陷的影响范围，优先升级依赖。性能验收仍未通过，未改动固定 App 或用户历史数据库。

## 同步对照

预先冻结六段顺序：4 KiB 文件同步、原诊断网关、约 56 KiB 文件同步、约 56 KiB 文件同步、原诊断网关、4 KiB 文件同步。四轮文件对照各有 5 次预热和 100 次计时，每次包含两段追加写入及两次成功的 `F_FULLFSYNC`，全部字节回读一致；没有降级为普通 fsync。57,680 字节只是 14 个 WAL 页及页头的量级对照，不是实际数据库页分布的复刻。

| 对照 | 两次同步 p95 | 整次写入与同步 p95 |
| --- | ---: | ---: |
| 4 KiB，第 1 轮 | 7.995 ms | 8.131 ms |
| 57,680 字节，第 2 轮 | 8.046 ms | 8.207 ms |
| 57,680 字节，第 3 轮 | 8.033 ms | 8.185 ms |
| 4 KiB，第 4 轮 | 7.970 ms | 8.088 ms |

同期两轮原诊断网关读取 p95 为 10.631／9.715 ms，事务提交约占总耗时的 86%。观察到 WAL 检查点或复用转换的样本分别为 5／3 个，最大耗时为 19.203／16.798 ms；未观察到转换的样本 p95 为 9.911／9.540 ms。这只能说明本批长尾与转换相关，不是系统调用追踪或完整因果证明。此前普通请求也曾超过预算的失败结果继续保留。

四轮共 840 次完整同步、同期 210 次网关读取及 842 条审计通过独立核对；核对器 5 项测试包括缺失同步、失败同步、不可能时长和字节篡改反例。诊断网关仍是 `a3917b3` 基线的旧诊断二进制 `75163aa9…`，没有配置签名者，不能归属到升级后的 SQLite，也不是新的正式性能验收。

SQLite 的官方说明确认，FULL 模式提交会同步 WAL，而默认检查点在触发阈值的提交线程内执行，可能增加个别提交耗时。见[官方 WAL 说明](https://www.sqlite.org/wal.html)。本批没有改变检查点阈值、同步要求或提交次数；也没有停止其他项目及系统扫描来制造通过结果。

## 优先修复数据库依赖

核对上游资料时发现：SQLite 官方确认 WAL-reset 竞态可能发生在多连接同时写入或做检查点时，罕见情况下会损坏数据库；3.51.3 及之后版本已修复。见[官方缺陷说明，第 11 节](https://www.sqlite.org/wal.html)。本批没有复现罕见竞态，也没有发现用户数据损坏；版本范围、实际链接库和项目并发入口构成升级依据，不能把单次压力测试通过当作不存在该问题。

| 链接方式 | 升级前实际版本 | 升级后实际版本 |
| --- | --- | --- |
| 普通 SQLite | 3.46.0 | 3.53.2 |
| SQLCipher | 4.5.7 community，内部 SQLite 3.45.3 | 4.14.0 community，内部 SQLite 3.51.3 |

工作区及两个桌面壳的锁文件同步升级为 `rusqlite 0.40.2`／`libsqlite3-sys 0.38.2`。只适配新版的附加数据库名称接口，并显式启用原有的无符号整数转换行为。新增测试直接检查实际链接版本，普通和加密构建均须包含修复，避免只更新普通 SQLite。

数据库表结构、加密格式、签名消息、旧缓存兼容、执行前后两次持久提交及 FULL／fullfsync 设置保持。没有增加后台检查点线程；须先完成此依赖修正的候选复验，再决定是否值得改变检查点调度。
