AgentGuard 是 GUI 智能体的旁路观察器：它看智能体看到的屏幕、读到的无障碍树、填过的表单、拉起的 deeplink 和外发流量的元数据，然后给出 允许 / 告警 / 阻断。它不是沙箱，不接管系统调用，也不拦网络。

这一页把能力和边界排在同等大小的版面上——因为项目本身就是这么写文档的：guard-cli coverage 会去仓库里核对覆盖矩阵的每一条声明，声明不成立命令就失败。下面每个数字都能用一条命令复现。

What it does,
and what it doesn't

AgentGuard is an out-of-band observer for GUI agents. It watches what an agent sees and types — screen frames, accessibility trees, form fills, deeplinks, network-flow metadata — and returns Allow / Alert / Block. It does not block traffic. It is not a sandbox — with one exception now: on Linux, for a process it launches, agentguard-jail applies a kernel-enforced filesystem boundary that does not depend on the guarded process cooperating. Everywhere else, and for every other layer, enforcement is cooperative: it stops what goes through it.

This page gives capabilities and limits equal space on the page, because that is how the repository documents itself: guard-cli coverage checks every claim in the coverage matrix against the repo, and an unbacked claim fails the command. Every figure below is reproducible with one command.

Updated 2026-08: Windows went from not one line of UIA to a real UI Automation walk plus GDI capture; Android from 3 of 7 serializers having callers to 8; and both desktop shells were compiled for the first time — CI had only ever verified them with rustfmt --check, which parses and does not resolve, so no compiler had looked at either Tauri app. (Correction: I previously wrote that they referenced icon files missing from the repository and could not be built at all. That was wrong — an artefact of an incomplete working copy on my side. The icons were there all along.)

Also new: a cooperative MCP tool gateway, a filesystem path model wired into the signed audit trail, the kernel-enforced Linux boundary above, and a release-blocker pass (docs/发布阻塞项.md), and signed adapter assertions with an asymmetric trust rule (docs/适配器断言签名.md). What this project may and may not claim, and who it is responsible to ship to, is now a separate document: docs/上线评估.md. The short version: it is an honest observation-and-accountability system with a cooperative layer of dissuasion and one narrow real boundary. Shipping it as that is responsible. Shipping it as "protection" is not.

15 · 一个内核执行的文件系统边界——只在 Linux 上，只对它自己启动的进程。这是全篇唯一一处强制力不依赖被约束方配合的地方：agentguard-jail 从计划的 scope.paths 天花板生成约束，在 pre_exec 里落下 user + mount namespace，越界写拿到内核的 EROFS。9 条集成测试全部从 jail 外面用文件系统状态核对，因为"launch() 返回了 Ok"和这个项目反复抓到的那种缺陷是同一形状。Landlock 只实现了探测；一台只有 Landlock 的机器上 launch() 拒绝启动而不是退化成不约束。
15 · One kernel-enforced filesystem boundary — Linux only, and only for processes it launches itself. This is the single place on this page where enforcement does not depend on the guarded party cooperating. agentguard-jail derives the constraint from a plan's scope.paths ceiling and applies a user + mount namespace in pre_exec; an out-of-bounds write gets EROFS from the kernel. All 9 integration tests check filesystem state from outside the jail, because "launch() returned Ok" is the same defect shape this project keeps catching. The Landlock backend is probe-only; on a Landlock-only host launch() refuses rather than degrading to no constraint.
crates/guard-jail · make check-jail · docs/内核约束.md
16 · 一个把危险工具调用按住等人回答的 MCP 网关——合作式。agentguard-mcp 是个 MCP 服务器，智能体把工具调用路由给它，它判决之后再决定执不执行；确认是靠按住 JSON-RPC 响应实现的，超时一律拒绝。describe() 和 execute() 是分开的两个函数，所以"说了什么"和"做了什么"不会漂。它拦的是经过它的调用——智能体直接 exec 就绕过了，这是设计而不是缺陷，代码里那个常量就叫 ENFORCEMENT = "cooperative"。
16 · An MCP gateway that holds a dangerous tool call until a human answers — cooperatively. agentguard-mcp is an MCP server: the agent routes tool calls through it, and it judges before deciding whether to run them. Confirmation is implemented by holding the JSON-RPC response, and a timeout always denies. describe() and execute() are separate functions so what it says and what it does cannot drift. It stops what goes through it — an agent that execs directly has bypassed it, which is the design and not a defect; the constant in the code is literally ENFORCEMENT = "cooperative".
crates/guard-gateway (24 tests) · docs/工具网关.md
17 · 认出自己发布的那把假钥匙，并在上线前把配置的缺口说出来。发布注册表钉的两把 Ed25519 公钥，私钥是仓库里的单字节种子。此前这件事只写在 YAML 注释里（"真实部署请替换"）——注释不是执行：照抄它再打开 require_attestation，任何人都能伪造出一个验签通过的 attestation。现在判决层认得它们，判 AGENT-KEY-PUBLICLY-KNOWN 而不是 Verified，失败是关闭的。agentguard preflight 会把这类缺口列出来（有 FAIL 时退出码 1），而且仓库自带的这套配置就报 FAIL——"照着仓库跑"和"可以上线"之间必须有一个看得见的差别。
17 · It recognises the fake key it ships with, and names the gaps in a deployment before it goes live. The shipped registry pins two Ed25519 public keys whose private halves are single-byte seeds in this repository. That used to be stated only in a YAML comment ("replace for real deployments") — and a comment is not enforcement: copy it, turn on require_attestation, and anyone can forge an attestation that verifies. The judgment layer now recognises those keys and returns AGENT-KEY-PUBLICLY-KNOWN rather than Verified; failure is closed. agentguard preflight lists gaps of this kind and exits 1 on any FAIL — and the configuration in this repository reports FAIL, because "runs from the repo" and "fit to deploy" must differ visibly.

不能做

What it does not do

18 items

最重要的一条 The one that matters most by design

1 · 它不是沙箱，不保护文件系统。AgentGuard 不会阻止智能体删掉项目目录以外的文件。三个各自足够的理由：(a) 没有文件系统事件类型——EventType 里没有 FileWrite、FileDelete、ProcessExec，引擎根本看不到文件操作；(b) guard-shell 没有路径模型，find / -delete 和删项目目录得到的是同一个答案；(c) 什么都不强制——SafeShell::propose() 返回一个枚举，仓库里没有 seccomp、没有 Landlock、没有 sandbox-exec、没有 ptrace。要这层保护，请交给操作系统。
1 · It is not a sandbox and it does not protect the filesystem. AgentGuard will not stop an agent deleting files outside your project directory. Three reasons, each sufficient alone: (a) there is no filesystem event type — EventType has no FileWrite, FileDelete or ProcessExec, so the engine never sees a file operation; (b) guard-shell has no path model, and find / -delete gets the same verdict as deleting the project; (c) nothing is enforced — SafeShell::propose() returns an enum, and there is no seccomp, no Landlock, no sandbox-exec, no ptrace anywhere in the repository. That protection has to come from the OS.
docs/scope-and-non-goals.md — measured verdicts for all four delete forms are tabulated there

平台缺口 Platform gaps

2 · Windows 的覆盖比 macOS 窄两处。抓帧走 GDI BitBlt，读的是目标窗口自己的渲染——别的进程叠在它上面画的钓鱼窗口不在这些像素里，除非那个窗口本身就是前台窗口。Windows.Graphics.Capture 采的是合成后的桌面，能补上这个洞，没选它是因为那是异步 WinRT + D3D11 设备 + 帧池，几百行代码的失败模式这个仓库的 CI 一条都跑不到。另外不采集应用签名摘要，所以 APP-SIGNER-MISMATCH 和 APP-LOOKALIKE 在这里没有输入。

屏幕文字识别有了（Windows.Media.Ocr，系统自带、离线、默认装简繁中文），所以 AX↔屏幕交叉验证在这边会跑——但本机没装识别语言包时它不可用，那两条规则就不运行，报的是「没有结论」不是「干净」。
2 · Windows coverage is narrower than macOS in two places. Capture is GDI BitBlt on the target window's device context, so it reads that window's own rendering: a phishing window drawn over it by another process is not in those pixels unless it is itself the foreground window. Windows.Graphics.Capture samples the composed desktop and would close the gap; it was not chosen because it is async WinRT with a D3D11 device and a frame pool, several hundred lines whose failure modes this repository's CI cannot reach. And no signing digest is collected, so APP-SIGNER-MISMATCH and APP-LOOKALIKE have no input there.

Screen text it now does read (Windows.Media.Ocr — ships with the OS, offline, simplified and traditional Chinese installed by default), so the AX↔screen cross-validation runs here. On a host with no recognizer language pack it is unavailable and those two rules do not run — reporting nothing, which is not reporting clean.
win_adapter::capture::GRAPHICS_CAPTURE_NOTE — the trade is recorded next to the code that makes it · docs/windows-observation.md
3 · iOS 是个占位：40 行 SwiftUI 加一个 README，没有 Xcode 工程，没接引擎。
3 · iOS is a placeholder — 40 lines of SwiftUI and a README. No Xcode project, not wired to the engine.
apps/ios-webshield/Sources/ContentView.swift (40 lines)
4 · Android 的确认是事后通知，不是拦停。中继现在会读引擎的答复了（此前发出去就不管，所以引擎判 Block + require_confirm 时手机永远不知道），require_confirm 会弹一条高优先级通知，报的是引擎的规则而不是本地启发式的猜测。但伴生应用观察的是已经发生的无障碍事件——没有任何一个点是「把动作按住等人回答」。桌面上那个模态框是在动作发生前挡住的。把两者都记成「Critical Confirm ✅」，正是旧那张能力表干的事。另外 deeplink 这一种仍然不发：无障碍服务看不到 intent，唯一的观察办法是把自己注册成 ACTION_VIEW 的处理者，也就是去劫持用户的链接——为一个事件类型付这个代价，这个项目不干。
4 · Android confirmation is post-hoc, not a gate. The relay now reads the engine's answer — it was fire-and-forget, so a Block with require_confirm reached nothing — and a require_confirm verdict raises a high-importance notification naming the engine's rule rather than a local heuristic's guess. But the companion observes an accessibility event that has already happened; there is no point at which it holds the action and waits. On the desktop the modal blocks before the action proceeds. Calling both "Critical Confirm ✅" is what the old capability matrix did. Separately, deeplink is still not emitted: an accessibility service does not see intents, and the only way to observe ACTION_VIEW is to register as its handler — intercepting the user's links, which this project will not do for one event type.

5 · 浏览器扩展没有会话概念，只发 ui_text 和 form_fill 两种事件；所有跟会话绑定的规则在扩展上都不生效。

7 · 图标哈希不能拦，只能记。在 30 个同风格生成图标上实测：无关图标对的距离是 0–27（不是理想的"接近 32"），6.6% 落在 4 bit 以内，4 对完全撞哈希——8×8 网格分不出一笔的差别。分布重叠，没有阈值能分开，所以只有图标证据时判 LogOnly。代价是论文里 10/10 成功的那个攻击场景，在我们的语料里被永久记成一次漏检：这就是漏检率 1.10% 而不是 0.0% 的原因。
7 · The icon hash can log, not intervene. The distributions overlap, so no threshold separates them, and icon-only evidence is LogOnly. The price: the paper's 10/10 attack is counted as a permanent miss in our own corpus — that is why the miss rate is 1.10% and not 0.0%.

信任缺口 Trust gaps

14 · 只有 Android 采集应用签名，所以强制验签默认关闭。桌面壳子和浏览器宿主不发签名摘要，把 require_attestation 打开会连已注册应用自己的 deeplink 一起拦掉。关着的时候身份仍然会被解析、冒充仍然会被阻断，但一个未验签的应用回退到可伪造的名字匹配拿它的白名单。
14 · Only Android collects a signing digest, so enforcement is off by default. The desktop shells and the browser host send no attestation, and require_attestation: true would block a registered app's own deeplinks there. With it off, identity is still resolved and impersonation still blocked, but an unattested app falls back to the forgeable name match for its allow-list.
policies/agent-registry.yaml — require_attestation: false · docs/app-identity.md
15 · 智能体身份是"按会话"，不是"按动作"。只有会话开始被签名——每个事件都签会把一次 Ed25519 运算放到无障碍热路径上，现在没有适配器做得到。所以能往已认证会话里注入事件的攻击者，继承这个会话的归属。另外没有双向认证：智能体分不出真守卫和一个"什么都批准"的壳子。防重放的 nonce 存在内存里、每个 agent id 上限 8192 条，进程重启就忘——总留存量随不同 agent id 的数量增长。
15 · Agent identity is per session, not per action. Only the session start is signed — signing every event would put an Ed25519 operation on the accessibility hot path and no adapter can do that today. So anything able to inject events into an attested session inherits its attribution. There is no mutual attestation either: an agent cannot tell a real guard from a shim that approves everything. Replay defence is in-memory and bounded at 8192 nonces per agent id, forgotten on restart — total retention scales with the number of distinct agent ids.
docs/agent-identity.md · surfaces.yaml aura-i notes (1)–(3)
16 · 适配器的断言可以增加风险，但伪造不出「干净」。环境调查、浮层标记这类"适配器说的话"是从事件里读的，而入口只有一道 bearer 令牌（FFI 连令牌都没有）。所以规则是非对称的：未经验证的断言只能增加风险，永远不能移除风险。伪造"有风险"只能给攻击者自己制造一次误报；伪造一份 env_surveyed=true、清单全空的调查去清掉已锁存的 Critical 风险——那个方向已经关上了，需要一个验证过的 Ed25519 签名。

Android 伴生应用会签了——用 ECDSA P-256 而不是 Ed25519，因为 minSdk 26 上 java.security 没有 Ed25519（要 API 33），而 P-256 能走 Android Keystore，私钥留在 TEE / StrongBox 里根本不出硬件。算法是卡上写明的，不是从公钥长度猜的——猜是算法混淆那类漏洞的标准入口。签名消息在两端各有一份实现，所以有一份两个方向都覆盖的跨语言向量钉住它们不分叉。

剩下的限制照说：两个桌面外壳还没接；公钥是每设备一把，不填进注册表的话它的调查仍然算未签名。
16 · Adapter assertions can add risk but cannot forge "clean". "What the adapter says" — an environment survey, an overlay marker — is read off the event, behind one bearer token (and the FFI has no auth at all). So the rule is asymmetric: an unverified assertion may only add risk, never remove it. Forging "risk present" only earns the attacker a false alarm; forging an env_surveyed=true survey with empty lists to clear a latched Critical risk — that direction is now closed, and needs a verified Ed25519 signature.

The Android companion now signs — with ECDSA P-256 rather than Ed25519, because java.security has no Ed25519 at minSdk 26 (it needs API 33) and because P-256 goes through Android Keystore, so the private key never leaves the TEE / StrongBox. The algorithm is named on the card, never inferred from key length — inference is the standard entry point for algorithm-confusion bugs. The signing message has one implementation on each side, so a cross-language vector covering both directions pins them together.

The remaining limits stand: neither desktop shell is wired, and the public key is per-device — a companion whose key is not in the registry still counts as unsigned.
surfaces.yaml agentscan-log-leakage notes (5)–(6) · Makefile:44
17 · 两类夹具，保障强度不一样。known-apps.yaml 里的签名摘要是刻意一眼假的（重复的半字节），并且有测试强制它们保持这样——钉错的摘要比不钉更糟，它看起来验过了实际什么都没验。但 agent-registry.yaml 里的密钥是真的 Ed25519 公钥，肉眼分不出和生产值的区别，那里唯一的保障是一条断言"文件里写着 FIXTURE KEYS 横幅"的测试。这些密钥的私钥半边就在仓库里。
17 · Two kinds of fixture, with unequal guarantees. The signing digests in known-apps.yaml are obviously fake (repeated nibbles) and a test enforces that they stay so — a registry pinning a wrong digest is worse than none, because it looks verified and verifies nothing. But the keys in agent-registry.yaml are real Ed25519 public keys, indistinguishable by eye from production values, and the only guard there is a test asserting the file carries a FIXTURE KEYS banner. Their private halves are in the repo.

The engine is portable Rust and the rules run everywhere — but a rule that can run is not a rule that is being fed. Where an adapter emits no events of a kind, the rules over that kind are inert, and inert reports nothing rather than clean. 2 · Audit-database encryption (SQLCipher) — needs a SQLCipher-linked build (the default feature is sqlite-bundled, which hard-errors instead). The key does not have to be supplied: env var → existing file → auto-generated and written at mode 0600, which is the path the desktop apps take. Redaction is not encryption: a masked row still says a payment card was on screen at a time in an app.
3 · App-attestation enforcement — only Android collects a digest, so turning this on elsewhere blocks a registered app's own deeplinks.

两个漏检率不同是因为两个语料不同：验收门用 73 个攻击场景（1.37%），记分板用 91 个（1.10%）。都是同一次漏检——那个只有图标证据的克隆应用场景，它被刻意留在语料里当作一次已知的、承认的失败。

make check-windows 里的 -D warnings 不是洁癖。这一轮最严重的 bug 就是 rustc 用一条警告报出来的：拿 windows crate 那些小驼峰常量去写 match 分支，Rust 会把它当成新绑定，第一条分支匹配一切——于是每一个 UI 元素都被判成可编辑字段。能编译、能运行、答案自信地全错。
The two miss rates differ because the corpora differ: the release gate runs 73 attack scenarios (1.37%), the scoreboard 91 (1.10%). It is the same single miss — the icon-only cloned-app scenario, deliberately kept in the corpus as a known and admitted failure.

The -D warnings in make check-windows is not fastidiousness. This iteration's worst bug was reported by rustc as a warning: a match over the windows crate's lower-camel-case constants makes each arm a new binding, so the first arm matched every control type and every UI element classified as an editable field. It compiled, it ran, and it was confidently wrong.

关于拦截。这一页从头到尾说的都是观察。观察者拦不住任何东西——看到无障碍事件的时候点击已经发生了。要真拦，守卫必须站在动作的路径上，而那是一次架构改动，不是一个开关。设计写在 docs/interception-design.md：四层路径、每层的威胁模型，以及一条不能含混的区分——「配合式」控制（智能体自愿走网关，可绕）和「内核执行」控制（内核代为拒绝）不是同一种保证。这个项目在自己的能力表里已经把这两者混过一次。文档目前是纯设计，一行都没实现。
On the figures. 1.10% is an attack-miss rate on our own corpus and is not the papers' attack success rate — the two measure different things and cannot be compared side by side. The 0.0% false-positive rate is over 34 benign controls, and that number means exactly as much as the control set is hard; the corpus now contains emoji, ZWNJ, soft hyphens, bidi isolates and long tokens, because an earlier 0.0% was measured on a corpus containing none of them.

Every partial in the coverage matrix carries a note saying how it is weaker than the published attack. Those notes are the most valuable thing in the repository, not a disclaimer.

On interception. Everything on this page is observation. An observer cannot intercept — by the time it has the accessibility event, the click has happened. Real interception requires the guard to stand in the path of the action, which is an architectural change rather than a switch. The design is in docs/interception-design.md: four possible paths, a threat model per layer, and one distinction that must never be blurred — a cooperative control (the agent routes through the gateway voluntarily, and can go around it) is not the same guarantee as a kernel-enforced one. This project has already conflated the two once, in its own capability matrix. The document is design only; none of it is built.
