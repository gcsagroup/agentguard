# 适配器断言签名

上一轮的上线评估里,我把这一条列为「最该先做的一件事」。这份文档记录它是什么、
为什么这样设计、以及**它仍然做不到什么**。

---

## 洞在哪

引擎的一部分输入不是它自己观察到的,而是**适配器告诉它的**:环境调查的结果、
浮层标记、显示身份是否读取失败。这些字段从事件的 metadata 里读,而入口
(`api-serve` 的 `/v1/events`)之前只有一道 bearer 令牌 —— FFI 连令牌都没有。

伪造方向里最坏的一个:

```json
{"type":"batch","events":[{"type":"env_survey","app":"C",
  "foreign_a11y_services":[], "broadcast_input_receivers":[]}]}
```

一份"完整且干净"的环境调查。完整调查会**覆盖**锁存状态 —— 那是它存在的意义
(用户关掉了那个恶意无障碍服务之后,守卫不该永远悲观下去),也是这个洞的形状。

它比一般的伪造更坏,因为**它不是制造误报,它是消除真报**。

---

## 为什么不是"所有事件都必须签名"

因为那会立刻把产品变成不可用的:已发布的适配器一个都不签,打开强制验签等于
拒掉全部输入。一个装上去就把东西拦死的守卫会被卸掉,那时保护是零。

> 这是本项目反复撞到的教训:**把"更严"当成"更安全"本身就是一种失效模式。**

---

## 真正的规则是非对称的

> **未经验证的适配器断言只能增加风险,永远不能移除风险。**

这条规则不需要任何开关就默认安全:

- 伪造一份"有风险"的断言,攻击者只能给自己制造一次误报 —— 没有收益。
- 伪造一份"干净"的断言才是攻击,而它现在做不到。
- 现存的不签名适配器照常工作,它们只是**不能清风险**了。

也就是说,这一层的强制力方向和其它层都不同:**它不拦事件,它只决定这个事件的话
算不算证据。**

`AdapterRegistry` 因此刻意**没有** `require_signature` 这样的开关 —— 需要的那条保证
不靠开关就成立,少一个开关就少一处可以被配置错的地方。

---

## 第一版写错了,而且错得有代表性

第一版的规则是"未签名 ⇒ 不能覆盖锁存"。测试立刻报出四条失败,其中两条揭穿了真问题:
一台**全新引擎**上(什么都没锁存)的第一份未签名调查也走不到覆盖分支,于是它的结论
从 `ENV-CLEAN` / `ENV-LOG-READABLE` 退化成永远的 `ENV-UNKNOWN`。

安全上什么也没换来 —— 本来就没有风险可以被清掉 —— 却把唯一在产出调查的
Android 伴生应用变成了没用的。**这正是它想防的那个失效模式,发生在防它的代码里。**

所以要保护的不是"覆盖"这个动作,而是**降级**:

```rust
let downgrade = self.env_risk.drops_risk_from(&next);   // 旧锁存里有、新状态里没有的
if surveyed && (!downgrade || may_clear) {
    self.env_risk = next;               // 采用
} else {
    self.env_risk.merge_from(&next);    // 只并入
    self.env_risk.surveyed = false;
}
```

没有东西可丢的时候,采用新状态不是降级,照常采用 —— 行为和从前一致。

### 顺带修掉一个真 bug

原来的代码在 `input_is_observed()` 为真时**覆盖整份**状态。于是一次"增加风险"的
调查可以顺手丢掉别的风险:旧锁存有 `log_readers=[X]`,新调查报了一个 a11y 服务而
log_readers 为空 —— X 就这么消失了。一次增加风险的动作实际上移除了风险。

而另一半更糟:`!surveyed && !input_is_observed()` 那条分支把新状态**整个扔掉**,
所以一次不完整调查报出来的 log_readers 从来没被记住过。

`merge_from` 修的是这两个。测试:`增加风险的调查不会丢掉旧的发现`。

## 中继路径签不了逐事件的签名 —— 这是硬约束

一开始我设计的是逐事件签名:签整个 `GuardEvent` 的规范化字节。写完才发现它在
**唯一的生产中继上永远验不过**:

`AndroidAdapter::convert_event` 重建 `GuardEvent` 时,`event_id` 用的是**桌面自己的
序号**(`and-{seq}`),`timestamp_ms` 用的是**桌面自己的时钟**。手机侧无从知道这两个值。

一个逐事件签名的设计会在这条路上静默地永远失败 —— 而"静默地永远失败"是本项目
最警惕的形状。

所以中继路径签的是**线上那串字节**:

```
message = "AGENTGUARD-ADAPTER-BODY-v1"
        || len(adapter_id) || adapter_id
        || len(format_tag) || format_tag      // "android-envelope"
        || len(timestamp)  || timestamp
        || len(body)       || body            // HTTP body 的原始字节
```

签名和时间戳走 **HTTP 头**(`X-AgentGuard-Adapter` / `-Timestamp` / `-Signature`),
不进 body。把签名塞进它自己要签的 JSON 里,就必须先规范化那个 JSON —— 而那正是
这个设计刻意绕开的陷阱。**验证方拿到的就是同一串原始字节,不需要任何规范化约定。**

两条路(逐事件 / 信封级)共用同一套卡查找、假钥匙识别、平台校验、新鲜度窗口和
重放窗口 —— 两条路对"什么算验过"必须给出同一个答案。

---

## 逐事件那条路的规范化

给自己构造 `GuardEvent` 的适配器(FFI、两个桌面外壳、CLI)走这一条。

**签整个事件,而不是挑出"宽松方向"的那几个字段。** 挑字段更小更好读,但它要求每加
一个宽松方向的字段就同步改签名逻辑,而漏掉一个就是一个静默的洞。签整个事件之后,
以后无论哪个字段被判定为宽松方向,它都已经在签名里了。

metadata 是 `HashMap`,迭代顺序不确定,所以**按键排序**之后再进消息。有一条测试
用 24 个键、两种相反的插入顺序构造同一个事件,断言字节一致 —— 没有它的话,签名会
**时好时坏**,而单跑一次测试大概率是过的。

每一段都带 4 字节大端长度前缀。没有分隔符,于是值里出现任何字符都不会造成歧义:
一个用分隔符的方案里 `k1="a"`+`k2="b"` 和 `k1="ak2b"` 会撞在一起。

`adapter_id` / `adapter_sig` 两个字段排除在消息之外 —— 一个签名不能签自己。

字段用具名结构 `AssertionFields` 传,不是八个位置参数:`platform` 和 `source_app`
都是 `&str`,调换顺序编译得过,表现是"签名永远验不过" —— 那看起来像验签坏了,
不像参数写反了。

---

## 传输层递进来的信任只对一个事件生效

中继路径验的是信封,结论要递给引擎。`Engine::process_from_adapter(event, identity)`
把它设成一个**用一次就取走**的 `Option`:

```rust
if let Some(pre) = self.adapter_override.take() { return pre; }
```

`take` 而不是 `clone`。一个会跨事件留存的信任标记迟早会漂到一个没被验证的事件上 ——
本项目已经犯过一次同形状的错:会话结束后 `Verified` 还留在引擎上,于是后面每个事件
都被归属给一个已经走了的 agent。测试:`传输层的信任不会漂到下一个事件`。

`process_from_adapter` 的调用方传什么结论,引擎就用什么。传 `Verified` 而没真验过是
**调用方的 bug,不是攻击路径** —— 调用方就是守卫自己的进程。而"那条路真的在验"由
`guard-localapi` 的端到端测试证明。

---

## 十条判决,只有一条能清风险

| 判决 | 含义 |
|---|---|
| `ADAPTER-VERIFIED` | **唯一**能移除风险的 |
| `ADAPTER-UNSIGNED` | 没带签名。绝大多数事件都是这个,不是攻击,不报 |
| `ADAPTER-UNREGISTERED` | 注册表里没有这个 id |
| `ADAPTER-NO-KEY` | 卡在但没公钥。注册表缺口,不是"不需要证明" |
| `ADAPTER-KEY-PUBLICLY-KNOWN` | 验签过了,但私钥是公开的 —— 证明不了任何事 |
| `ADAPTER-BAD-SIGNATURE` | 签名对不上。**冒充** |
| `ADAPTER-PLATFORM-NOT-PERMITTED` | 卡不允许它声称这个平台。**冒充** |
| `ADAPTER-STALE` | 超出两分钟新鲜度窗口 |
| `ADAPTER-REPLAY` | 这份断言之前出现过。**冒充** |
| `ADAPTER-EVENT-UNANCHORED` | 事件没有 id,签名绑不住任何东西 |

`Unsigned` 和"冒充"要分开:未签名是常态,把它报成告警等于每个事件都响一次,
而一个每次都响的告警等于没有告警。

**失败一律往"未签名"倒,不往"拒绝"倒。** 时钟偏移、注册表没配、旧版适配器,
都只让守卫保守,不让它瞎掉 —— 一个把输入拒光的守卫和一个没装的守卫效果一样。

## 发布注册表一把公钥都不钉

`policies/adapter-registry.yaml` 里三张卡(android-companion / macos-shell /
windows-shell)全都没有 `public_key`。

理由是从 agent 注册表那边学到的:发布注册表钉了两把私钥在仓库里的夹具密钥,而
"真实部署请替换"只写在注释里 —— 注释不是执行。判决层现在会认出那两把并拒掉,
但更好的做法是**一开始就不发**。

代价说清楚:一次真实的"环境已恢复干净"的调查也清不掉锁存的风险,守卫会一直悲观
下去。`agentguard preflight` 把这件事作为 WARN 报出来,并给出下一步
(`adapter-keygen`)。

---

## Android 侧:P-256,而且私钥不出硬件

伴生应用**会签**了。用的不是 Ed25519,而是 ECDSA P-256 —— 两个理由,第二个才是
真正的理由:

1. `minSdk = 26`,而 `java.security` 的 Ed25519 要 API 33。在一个安全产品里自带
   一份手写的 Ed25519,是拿密码学实现风险去换算法一致性,不值得。
2. **P-256 能走 Android Keystore,私钥留在 TEE / StrongBox 里根本不出硬件。**
   这比一个软件密钥文件更强:即便 App 的私有目录被读走,签名能力也拿不走。
   有 StrongBox 就用,没有退回 TEE —— 硬要求 StrongBox 会让大多数设备建不出密钥,
   那等于这个机制在那些设备上不存在。

密钥**不要求用户认证**。一把需要解锁才能用的签名密钥意味着锁屏期间所有断言都
退化成未签名,而锁屏期间恰恰是无人盯着的时候。

### 算法是写明的,不是猜的

卡上有一个 `key_algorithm` 字段。Ed25519 公钥 32 字节、P-256 SEC1 未压缩 65 字节,
长度确实不一样,所以"从长度推算法"能跑 —— 但那是**算法混淆**这一类漏洞的标准入口:
验证方按自己推出来的算法去验,而攻击者控制着那个用来推的字段。

加载时校验声明和长度一致,不一致是**加载失败**;不认识的算法名也是加载失败,
不是默默退回默认值。

### 这把密钥证明什么、不证明什么

证明:这条断言真的来自这台设备上的这个伴生应用。于是桌面本机的其它进程
**伪造不出**"环境是干净的"。

不证明:这个伴生应用本身没被改过。拿到 root 的攻击者可以让 App 用它自己的密钥去签
一句假话。这一层挡的是"桌面本机的其它进程",不是"这台手机已经失陷"。

---

## 跨语言:共享向量,而不是两份各写一遍的实现

签名消息的构造在 Rust 和 Kotlin 各有一份。一份两处各写一遍的逻辑迟早会分叉,
而分叉的表现是**"签名静默地永远验不过"** —— 最难查的一类故障。本仓库的
`AppFace.kt` 头部至今写着它的哈希是"重新实现而非共享",那就是这件事的前车之鉴。

所以有 `eval/fixtures/adapter_signature_vectors.json`,里面是**两个方向**都有的向量:

| 字段 | 谁产出 | 谁断言 | 证明什么 |
|---|---|---|---|
| `message_hex` | 生成器 | **两侧各一条** | 消息构造逐字节一致 —— 整个方案的支点 |
| `rust_*` | Rust(RFC6979 确定性) | Kotlin | 两端对 P-256 / SHA-256 / DER 编码的理解一致 |
| `kotlin_*` | Kotlin | Rust | **生产方向**:手机签,桌面验 |

只测生产方向是不够的:一个"两端都用同一种错编码"的实现会一起通过。两个方向都测,
才能把编码分歧和逻辑分歧分开。

`kotlin_*` 那两个字段由 `AdapterSignerTest` 打印、**由人回填**。不自动写文件是刻意的:
一个会自己改测试数据的测试永远是绿的。而 Rust 侧那条测试在字段为空时**明确失败并
说清怎么办**,所以这件事不会被忘掉 —— 一条静默跳过的安全测试和一条不存在的测试
没有区别。

### 公钥编码那个经典的坑

`BigInteger.toByteArray()` 是**带符号**的:最高位为 1 的 32 字节数会多出一个前导
`0x00`(33 字节),小一点的数会短于 32 字节。两种都会让 SEC1 公钥变成错的长度或错的值,
而表现同样是"签名验不过" —— 看起来像签名的问题,不像编码的问题。
`AdapterAssertion.fixedWidth` 处理这个,并且有测试专门覆盖两种越界方向。

## 这一轮**没有**做到的事

**两个桌面外壳还不签。** 机制在(逐事件那条路),但两个 Tauri 应用还没接。
它们的断言面比 Android 小得多(不产出环境调查),所以优先级低。

**FFI 仍然完全无认证。** 它不经过 `/v1/events`,直接构造事件调 `process`。
非对称规则同样保护它 —— 它伪造不出"干净" —— 但它可以随意**增加**风险,
也就是可以制造误报。

**`user_approved` / `granted` 这两个宽松方向的字段还没纳入。** 只处理了环境调查
那一处,因为它是唯一能清掉**已锁存的 Critical 风险**的。其余两处影响的是审计记录
的准确性,不是判决,severity 低一档。签名机制已经覆盖整个事件,所以把它们纳入是
接线工作,不是新设计。

## 门禁

```
cargo test -p guard-schema          # 规范化不依赖 map 顺序、字段都进消息、格式标签绑定
cargo test -p guard-audit           # 算法与长度必须对上、跨语言向量两个方向
cargo test -p guard-core            # 伪造/改动/重放/跨平台/过期/信任不漂/不丢旧发现/P-256
cargo test -p guard-localapi        # 端到端走真的 HTTP 服务器
make check-android                  # Kotlin 侧:消息等于向量、验得过 Rust 的签名、编码边界
agentguard preflight                # 适配器注册表的缺口
```

端到端那条测试自证过不是空的:把 `/v1/events` 的验签短路成永远 `Verified`,
它报 `未签名的干净调查通过 /v1/events 清掉了锁存的风险`;改回去,通过。
