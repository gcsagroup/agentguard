# 跨浏览器:Chrome / Edge / Firefox / Safari（E4）

> 一句话结论:**Edge 基本是免费的(同 Chromium),Firefox 是一次真实的移植(已做骨架,真机未验证),
> Safari 是另一个量级(要 Xcode 包壳、原生消息模型完全不同,本环境无法构建也无法验证)。**

浏览器扩展的三样东西决定了移植成本:**扩展 API 命名空间**、**manifest / 打包**、**原生消息host**。
下面逐个浏览器说清各自到哪一步、剩下什么。

## Edge —— 直接可用(Chromium)

Edge 就是 Chromium,加载的是同一套 MV3 扩展:`chrome.*`、`declarativeNetRequest`、
`world: "MAIN"` 内容脚本全都一样。所以:

- **扩展包**:和 Chrome 同一个 zip(`package-store.sh` 不加参数那份)。
- **原生消息 host**:只有 manifest 目录不同——`install-host.sh --browser edge <extension-id>` 会装到
  Edge 的 `NativeMessagingHosts` 目录(macOS `…/Microsoft Edge/…`,Linux `~/.config/microsoft-edge/…`)。
  允许键仍是 `allowed_origins: [chrome-extension://ID/]`(Edge 也用这个形式)。
- 发布走 Edge Add-ons 商店。

剩下的只有真机冒烟(在真 Edge 里加载、点一次付款确认)——和 Chrome 一样属于"真机 E2E 未验证"。

## Firefox —— 已做移植骨架,真机未验证

Firefox 是 WebExtensions,和 Chromium 大同小异,但有几处**必须**处理,否则会**悄悄**少东西:

- **manifest**:单独一份 [`manifest.firefox.json`](../apps/extension-chromium/manifest.firefox.json),
  多了 `browser_specific_settings.gecko.id`(没有它装不上、原生消息也对不上)和
  `strict_min_version: 128`(下面 world:MAIN 的原因)。内容脚本集、权限集和 Chrome 那份**必须一致**——
  由 `manifests.test.mjs` 钉住(漏一个 `guard-page.js`,fetch 门就没了,而没有东西会报错)。
- **打包**:`package-store.sh --firefox` 把 `manifest.firefox.json` 作为包里的 `manifest.json`,其余文件
  和 Chrome 完全一样。
- **`chrome.*` 命名空间**:Firefox 同时提供 `chrome`(回调风格)和 `browser`(Promise 风格)。现有代码
  用的是 `chrome.*` 回调风格,Firefox 认。所以**没有**为此改代码——如果将来要用 Promise 风格,再引
  `webextension-polyfill`,那时代码单源、两边都跑。
- **`world: "MAIN"`(E2.1 的 fetch 门)**:Firefox 到 **128** 才支持 manifest 里的 `world: "MAIN"` 内容
  脚本,所以钉了 `strict_min_version: 128`。更老的 Firefox 上,fetch/XHR 门这一层不会加载——DOM 门
  (submit/click)和 DNR 仍在。这是一条**如实的降级**,不是静默缺失。
- **`declarativeNetRequest`**:Firefox 支持,但动态规则的配额和细节与 Chromium 有出入;名单主机拦截
  在 Firefox 上要按其配额上限校准(未做,真机校准项)。
- **原生消息 host**:模板不同——Firefox 用
  [`com.agentguard.native.firefox.json`](../apps/extension-chromium/native-host/com.agentguard.native.firefox.json)
  的 `allowed_extensions: [gecko-id]`(不是 `allowed_origins`)。`install-host.sh --browser firefox <gecko-id>`
  装它。还有一处**宿主侧**的关键差异:Firefox 启动 host 时传的调用方标识是**扩展的 gecko id**,而
  Chromium 传的是 `chrome-extension://ID/`。所以装机脚本写进 `allowed-origin` 文件的串按浏览器不同,
  宿主(`guard-nm-host` 的 origin 校验)比对的就是浏览器实际传进来的那个——这条是按 MDN 文档写的,
  **没在真 Firefox 上跑过**,是发布前必须实测的一项。

**Firefox 未验证清单**:真机加载、world:MAIN fetch 门是否真拦、DNR 配额、native host 的 gecko-id
origin 是否如文档所述。骨架(manifest、host 模板、装机路径、打包、防漂移测试)都在,真机那一步没做。
这几条已经落成一份可执行的验收清单 [`acceptance-firefox.md`](./acceptance-firefox.md)(F1–F8),并作为
release-gate 的一项"需真机"证据(`AGENTGUARD_EVIDENCE_ACCEPTANCE_FIREFOX`)登记在案——在真 Firefox
上走完并留证据前,它一直显示为未验证。

## Safari —— 另一个量级,本环境做不了

Safari Web Extension **不是**换个 manifest 就行的:

- 它必须被一个 **Xcode 工程**包成一个 macOS/iOS **应用**(`safari-web-extension-converter` 生成壳子),
  通过 App Store 或签名应用分发——不能像 Chromium/Firefox 那样加载一个 zip。
- **原生消息完全不同**:没有 stdio native messaging host。Safari 走
  `SafariWebExtensionHandler`(一个 App Extension,`NSExtension` 里的 Swift 类),扩展用
  `browser.runtime.sendNativeMessage` 打到它——`install-host.sh` 那套 manifest 目录 + stdio 二进制在
  Safari 上**完全不适用**。`guard-nm-host` 得改成(或旁边再写)一个 Swift 的 handler。
- `world: "MAIN"` 与 DNR 在 Safari 上的支持度还要再核。

**结论:Safari 是设计项,不是能在这个云环境里构建/验证的东西**(要 macOS + Xcode + Apple 开发者账号)。
硬塞一个"看起来像 Safari 扩展"的目录进仓库,就是这个项目一直在反对的"实现一个不足以支撑其主张的
机制"。所以这里只给出上面这份如实的形状说明,不放半成品。真要做,它是一条独立的、以 Xcode 工程为
中心的工作线,和 iOS 那条(`ios-webshield` 现在是脚手架)天然合并。

## 能力对照(哪层防护在哪个浏览器成立)

| 防护层 | Chrome | Edge | Firefox | Safari |
|---|---|---|---|---|
| 扫描(注入/PII/陷阱/付款 CTA) | ✅ | ✅ | ✅(chrome.* 认) | 设计项 |
| DOM 门:submit/CTA 点击执行前拦 | ✅ | ✅ | ✅ | 设计项 |
| fetch/XHR 门(world:MAIN,E2.1) | ✅ | ✅ | 🟡 仅 FF≥128,否则如实降级 | 设计项 |
| DNR 名单主机拦截 | ✅ | ✅ | 🟡 配额待校准 | 设计项 |
| 宿主签名审计(native messaging) | ✅ | ✅ | 🟡 gecko-id origin 待真机验 | ❌ 需 Swift handler |

✅ = 机制在、结构测试钉住;🟡 = 机制在但有如实标注的限制/未校准;❌ = 未做。所有 ✅ 都仍受同一条
总限制:**真机端到端未验证**——这些浏览器扩展在真环境里的行为,本云环境跑不到。
