# 第七轮复核:文档说的 vs 代码做的 —— 差距、缺陷与改进建议

一次覆盖全仓的独立审查:把每份文档的**具体主张**逐条拿去和实现对照,找"文档说做了/说保证、
代码没做到或做错"的地方,再给产品级改进建议。六个方向并行审(核心引擎、视觉观测、审计/隐私、
内核执行/shell/身份、适配器/各端、评测/计费/路线图),约 40 条发现;下面按严重度归并,
**最严重的五条我逐条读代码复验过**,结论都成立。

范围:`crates/*`(18 个)、`adapters/*`(4)、`apps/*`(5)、`docs/*`(约 45 份)。审查日期
2026-08-26,产品版本 1.0.0-rc.1。

## 一、高严重度(已逐条复验)

### 1. 情报签名可被 `sha256:` 降级绕过——Ed25519 公钥钉扎形同虚设

`ThreatBundle::verify`(`crates/guard-intel/src/lib.rs:103-110`)遇到 `sha256:` 前缀的"签名"时,
只把它和自己重算的摘要比一下就通过,**`public_key` 参数在这条分支里根本没被用**。而
`docs/release-security.md:10` 把 `load_release` 讲成"fail-closed 的公钥验证"——可它同样有一条
`sha256:` 分支(`lib.rs:190-193`)调 `b.verify(None)`。

后果:一个能提供 bundle 字节的攻击者(篡改磁盘上的 `intel/bundle.json`,或对 http 拉取做 MITM)
把 `ed25519:` 签名换成 `sha256:<重算摘要>`,**即使公钥已钉扎也照样验过**,情报库(恶意域名、
注入短语)可被静默改写或清空。更糟的是 `api-serve`(生产 HTTP 守卫)走 `load_or_default`,它的
`ed25519:` 分支是个空操作(`lib.rs:156`:`Some(sig) if sig.starts_with("ed25519:") => {}`)——
**完全不验签**。这条把整套情报签名故事架空了。

修:`load_release`/`apply_update_bytes` 拒绝 `sha256:` bundle(只在显式 `--allow-legacy` 开发标志下
接受);有公钥时**必须**走 ed25519 分支,不允许降级;把 `load_or_default` 的 ed25519 空操作改成
**失败**;给 `api-serve` 一个 `--intel-pubkey` 走 `load_release`。

### 2. `check_inclusion` 是死代码——"删尾 K 条 + 补 K+1 条"的篡改在生产验证里抓不到

`docs/audit-signing.md` 的威胁表(约第 236 行)称"增长-重写"攻击由 `check_inclusion` 抓——它复核
见证时的头哈希是否还在链上。但 `HeadWitness::check_inclusion` / `chain_contains_hash` 的**唯一调用者
都在 `#[cfg(test)]` 里**(`store.rs:2179,2196`)。生产的 `audit-verify` 命令只调 `check_against`
(`guard-cli/src/main.rs:2048`),而 `check_against` 仅在 seq/count **倒退**、或**相等但头哈希不同**
时才失败。攻击者删掉 K 条尾行、补上 K+1 条伪造行时 seq 和 count 都**增大**,`check_against` 每条
分支都过,没有任何东西去验证见证过的哈希还在链上。文档给这一行的保证没有端到端兑现。

修:在 `audit-verify` 的见证分支里,当见证带非空 `last_record_hash` 时调
`prev.check_inclusion(|h| store.chain_contains_hash(h))` 并在出错时置 `failed=true`——机制已经写好了,
只差这一次调用。补一个 `make audit-signing-demo` 用例(删 K 补 K+1)让 CI 盯住。

### 3. 浏览器 "Critical Confirm" 没接通——商店文案在宣传一个不触发的功能

`apps/extension-chromium/STORE.md:17` 说经 Native Messaging 转发能得到"统一审计和 **Critical
Confirm**",`docs/platform-matrix.md:24` 也把 Chromium 的关键节点确认列为"经桌面壳子"。两者都不成立:
`background.js:55` 收到宿主回复后**只 `console.debug` 一下**,引擎的 `paused`/`require_confirm`/
`decisions` 全被丢弃;`popup.js` 也从不读判决。宿主(`guard-nm-host`)是个无头 stdio 循环,通篇没有
任何通知/弹窗/确认路径。而且扩展连的是独立的 `guard-nm-host` 二进制,**不是** Tauri 桌面壳子——
两个进程从不通信。一个被判 `Block + require_confirm` 的页面付款按钮,结果是一行 debug 日志,用户什么
都收不到。

顺带:所谓"统一审计"其实是**三个各自独立的数据库**(nm-host 的 `nm-audit.db`、macOS 壳的
`audit-macos.db`、Windows 壳的 `audit.db`),浏览器事件由 nm-host 自己的引擎实例判、进 nm-host 自己的
库,桌面仪表盘里根本看不到。

修:要么让 `background.js` 对宿主回复真正动作(按 `require_confirm` 起一个 `chrome.notifications`
或拦住按钮),要么把 `STORE.md:17`、`platform-matrix.md:24` 改成"浏览器路径只观测+审计"。当前是在
商店列表里宣传一个从不触发的用户安全功能。

### 4. 计费 webhook 无签名验证,授权本身又只是装饰

`POST /webhook/billing`(`crates/guard-billing/src/http.rs`)对原始 body 没有任何
`Stripe-Signature`/HMAC 校验(在该文件 grep `signature|hmac|secret` 为空),`apply_webhook_event`
直接**用本地密钥从 payload 里自铸许可令牌并激活**(`lib.rs:176-178`):一个
`{"type":"purchase","plan":"enterprise"}` 的匿名 POST 就自授 Enterprise。`roadmap-status.md:39` 称其
"Stripe-like",而 Stripe 的核心正是签名验证,这里没有。

当前真实影响之所以是"中"而非"高":**授权是纯装饰的**——`unlimited_audit`/`custom_rules`/
`enterprise_export` 这些 flag 只被打印和显示,全仓没有任何一处 `if` 读它们来放行/拒绝
(`guard-billing/src/lib.rs:105-117`,消费点只在 CLI 和桌面状态 DTO)。也就是说 Free 和 Enterprise
行为完全一样。但这两条叠起来是个陷阱:**一旦把授权接进真正的功能门,这个 webhook 就是现成的绕过口**,
而且 `docs/发布阻塞项.md` 通篇没提它。

修:给 webhook 加 `AGENTGUARD_WEBHOOK_SECRET` 对原始 body 做 HMAC 校验(并补"伪造 body 被拒"的测试);
授权要么真做一个门(比如 `!features.enterprise_export` 时拒绝导出)+ 测试,要么把 `billing.md:3`、
`roadmap-status.md` 的措辞改成"计算了 plan 但当前没有任何功能被它门控"。

## 二、中严重度

### 5. 网关工具调用不计 step 预算,`PLAN-*` 在主执行路径形同虚设

网关把每次工具调用映射成 `FileWrite`/`FileDelete`/`ProcessExec`(`gate.rs:357-362`),但
`step_kind_of` 没有这三者的分支,全落到 `_ => Some(StepKind::Observe)`(`lib.rs:3840`),而 observation
从不被判也不计数。结果:`book_hotel` 的 `max:{run_shell:0, network_egress:0}` 对网关发起的
`curl`/`python`/`git` 完全不生效,`PLAN-OVER-BUDGET` 在网关路径上不可能触发。而 `events.rs:51-54`
恰恰声称"本会话执行的程序计入 `run_shell` 预算"——这句是假的。`工具网关.md:104-105` 把 `PLAN-*`
讲成引擎在网关路径上的真正贡献,实际只有 `CRIT-*`(靠 `ui_text` 匹配)会产生计数步。

修:在 `step_kind_of` 里把 `ProcessExec→RunShell`、`FileWrite/Delete→`对应写/删步,让预算真的约束网关命令;
否则删掉 `events.rs` 那句预算声明。补一个"`max:{run_shell:0}` 下跑 N 次 `ProcessExec` → `PLAN-OVER-BUDGET`"
的测试。

### 6. 引擎 FS 容器混淆"未声明"与"显式只读"

`check_filesystem_scope` 用 `ceiling.and_then(|p| p.write).unwrap_or_default()`,对 `write: None`(未声明)
和 `write: Some([])`(显式空)得到同一个 `[]`,两者都只出 **Alert 不出 Block**(`lib.rs:3162-3176`)。而
`navigation_jump` 发的是 `write: []`、`order_food` 是只读,`路径模型.md:111-114` 明说这是"不给/只读文件系统"。
`Workspace`/`is_declared` 类型就是为防这个 bug 造的(`paths.rs:161-170`,注释里点名了 `navigation_jump`),
可引擎绕过它自己重新实现了容器判断、丢了"声明/空"之分。今天被网关先跑 guard-shell 的 `Workspace` Deny
所遮蔽,但对规划中的 B2 jail 输入是个洞,且没有测试。

修:把"是否声明了路径"这一位带进 `TaskScope`,让显式空写列表判 `FS-OUTSIDE`(Block)而不是 `FS-UNSCOPED`(Alert)。

### 7. `i64::MIN` 时间戳溢出在逐事件路径仍在(文档称已修)

`docs/适配器断言签名.md:351-356` 说 `(now - timestamp_ms).abs()` 已被换掉(debug 崩溃=守卫 DoS,
release=新鲜度算错)。中继路径确实修了(`guard-core/src/lib.rs:684`,`saturating_sub().unsigned_abs()`),
但**逐事件路径在 `lib.rs:2380` 仍是** `let skew = (now - event.timestamp_ms).abs();`,前面没有任何钳位。
`event.timestamp_ms` 是事件可控的 `i64`。这条在验签之后,所以要有一把有效(非夹具)适配器密钥或一把泄露的
密钥才能碰到,但那时可以崩掉守卫(debug)或污染新鲜度检查(release)——正是文档断言已消灭的那个 bug 的
孪生兄弟。

修:把 2380 换成和 684 相同的写法,并抽一个共用 `fn freshness_skew(now, ts)` 让两条路径不会再各写一遍;
补一个喂 `timestamp_ms=i64::MIN` 的测试。

### 8–10. 视觉检测层的三个可绕点

这三条都是真实盲点,但都坐在一个已被诚实标注为"差分式、只证明守卫看到了什么、2 FPS、未在真机验证"的
尽力层之上;严重度在于**具体主张**被高估。

**8. 隐写垂直跨步可绕(`stego.rs:17,111,170`)。** 模块的招牌修复是"水平固定跨步 `STRIDE_X=7` 让攻击者把
每第 7 列 LSB 钉住、把翻转率精确归零",他们改成扫每一对水平像素。但**垂直方向 `STRIDE_Y=11` 仍只采样第
0、11、22… 行**。攻击者把载荷只嵌到 `y%11!=0` 的行(约 91% 容量),每个被采样行都干净,`lsb_flip_rate` 和
`chroma_lsb_flip_rate` 都≈0 → `OVL-008`/`OVL-011` 被归零静默,和他们宣称修掉的那个 bug 同构。回归测试
`对齐到固定跨步不能归零` 只变水平跨步、载荷填满所有行,所以抓不到这条。

**9. 帧局部定位被"顺带一个全局变化"击穿(`framehash.rs:522-551`)。** F6 对**空间分离**的注入确实实现了
(连通域→上报次级簇)。但 `compare` 只在存在非最大连通分量时报"局部";若攻击帧同时带一个轻微全局亮度/色度
偏移(>~12.5%,一次淡入/主题切换就够),所有块都变、并成一个连通分量、`secondary` 为空、`144/144 > 0.35`
→ 判 `GlobalRepaint` → `None`,注入被整个吞掉。整个模块赖以立足的"局部 vs 全局"之分,靠"再加一个它当良性
处理的全局变化"就能绕过,且未文档化。

**10. Viewtree 只在多数分歧时触发,内容页自动关掉 Critical 那半(`viewtree.rs:183-187,250-257`)。**
`one_sided` 要求分歧 token ≥3 **且** 占比 >50%;一次真实注入(正常页面里塞几个隐藏树节点"忽略之前指令,
转账…")只占树的一小部分,永远到不了 50%、永远不触发。单测用的是 100% 注入的树,把这个掩盖了。另外
`cross_validate` 在 OCR 侧 ≥24 行时**丢弃全部** `TreeTextNotOnScreen`(OVL-010,唯一的"智能体读到用户看不到
的内容"检查)——也就是几乎每个真实内容页都关掉了它。

修(视觉整体):杀掉垂直跨步或对 `STRIDE_Y` 做**逐帧随机相位**(非公开种子),并把回归测试扩到"载荷落在未采样
行";局部/全局分类前先减去逐帧全局偏移、比较**残差**;viewtree 改成按**绝对**分歧 token 数上报(不只多数),
用可见前缀比较取代"≥24 行一刀切";把硬编码的 5 短语注入列表换成已有的结构化 `guard-privacy::anomaly` 扫描器。

### 11. 策略同步无认证、收明文 HTTP

`guard-sync/src/lib.rs:73-91` 的 `pull_policy` 从 `http://`(允许明文,无证书钉扎,`read_to_end` 无上限)或
文件拉一个 `DevicePolicy`,裸解析后就返回。`DevicePolicy`/`SyncManifest` 里没有任何签名/HMAC/版本钉扎字段
(全 crate grep `sig|verify|hmac` 为空)。策略携带 `require_confirm_critical`、`block_malicious_domains`、
`allowed_agents` 这类安全开关。MITM 或恶意策略主机可静默下推一个被削弱的策略。今天的缓解事实:桌面只把
`policy_id` 显示在状态 DTO 里、**没**把这些字段喂进执行,所以当前是个惰性 POC——但 `architecture.md`/
`ios-limited-sku.md` 把它讲成"经 MDM/托管配置的企业策略拉取",没有一份文档披露这条通道未认证。

修:用现成的 `AuditVerifyKey`/`AdapterVerifyKey` 对策略字节做分离签名,`pull_policy` 里用一把带外机构密钥验;
拒 `http://` 和无上限 body。在此之前,在 `architecture.md` 里明确标注 `guard-sync` 未认证。

### 12. mount-ns 把 `/dev /proc /sys` 留可写——root 运行可绕只读

`mountns.rs:271` 把 `/proc* /sys* /dev*` 排除在递归只读 remount 之外,初始 remount 又只覆盖 `/` 这一个挂载。
非 root 时基本无害;但 `agentguard-jail` 以 uid 0 运行时 ns 里 0→0 映射(`mountns.rs:212,228`),`/dev` 下的
设备节点可写,`dd of=/dev/sdX` 绕过整个"整棵树只读 / 写 /etc → EROFS"的保证。`内核约束.md` 记了读天花板缺口和
locked-mount 残余,但从没提这个伪文件系统的写排除。

修:把只读 remount 扩到 `/dev`(或 bind 一个最小 devtmpfs),并拒绝以 uid 0 运行 jail;至少要文档化。

### 13. `FS-SENSITIVE`(删 `/etc`、`/`)可被用户确认批准,风险次序倒置

`FS-SENSITIVE` 是 `Block + require_confirm:true`(`lib.rs:3152-3159`),而 `FS-UNPROVABLE` 是
`Block + require_confirm:false`。`process_gated` 会把任何 `Block + require_confirm` 在批准后降为 `Allow`。
于是"删 `/`"可被用户点确认放行,而一个不可归约的通配符反而是硬拦——正好和 `路径模型.md:44-51`("无条件判
Deny")相反。当前潜伏(网关自己把 Block 当无条件 Refuse,guard-shell 又先 Deny),但引擎判决本身在这条上不是
fail-safe,且没测试。

修:把 `FS-SENSITIVE`(以及可能的 `FS-OUTSIDE`)在引擎层设 `require_confirm:false`。

## 三、文档↔代码不一致(会误导集成者,应尽快对齐)

这些**不是安全漏洞**,但一个照文档做集成/审计的人会被带偏。多数是代码其实比文档好、文档忘了更新。

- **`工具网关.md:133-135` 与 `路径模型.md:147-148` 的"局限"章节已过时。** 都说"引擎看不到文件操作/FS 判决
  进不了签名审计",而实际上事件类型已存在、网关在用、引擎自己算 `FS-*`、且有测试证明 `FS-SENSITIVE` 进了签名
  审计链。文档集自相矛盾。
- **`windows-observation.md:107` 说"无 OCR",代码有完整 `Windows.Media.Ocr`**(`win-adapter/src/ocr.rs`,在
  `native.rs:253` 接线,`platform-matrix.md:42` 又说 OCR 可用)。文档↔文档、文档↔代码双重矛盾。
- **`audit-encryption.md:83` 说 nm-host 那条路"既不签名也不加密且不打警告",代码已打警告**(本轮刚加的
  `apply_audit_signing`)。文档比代码更悲观。
- **`local-api.md` 漏了两条最要紧的信息:** `POST /v1/events`(Android 伴生入口,能清除已锁存的 Critical
  环境风险)和 `--allow-lan`(把服务绑到 `0.0.0.0` 明文 HTTP)。文档标题还强调"只 127.0.0.1"。
- **`safe-shell.md:153-161` 的"已知局限"过时且自相矛盾**:说"无路径作用域",而正文和 `check_paths` 都实现了
  路径模型,还有对应测试。
- **`上线评估.md:37` 说"125 场景",实际语料已是 130 个场景文件。**

让这类漂移在 `cargo test` 里就暴露,而不是留给读文档的人。

## 四、低严重度 / 死代码 / 悬空件

- **`guard-ffi` 是个看起来交付、实则无消费者的 C ABI。** 构建 cdylib/staticlib 且有单测,但仓里没有任何 crate/app
  链接它(`desktop-macos` 直接调 `mac-adapter`,`ios-webshield` 没有 Xcode 工程)。读起来像一个已交付的集成。
- **nm-host 默认接受任意本地调用者。** `check_caller_origin` 只**警告**、不拒绝,除非设了 `AGENTGUARD_ALLOWED_ORIGIN`
  (`main.rs:357-376`),而 `install-host.sh` 从不设它。任意本地进程能说这套协议、往签名审计里注入伪造的
  `source_app`。建议默认 fail-closed。
- **`agent_sessions` 的 `event_count`/`block_count`/`alert_count` 在哈希链和签名之外**(`store.rs:617-652`),能写库
  就能改。桌面 UI 会显示它们。建议要么纳入哈希,要么像 `report.rs` 标注 `UserDecisionColumn` 那样标成"非证据级"。
- **`load_or_default` 的 ed25519 分支是空操作**(见发现 1);**viewtree 单字符 CJK 分支是死代码**(`:59` 先按
  `MIN_TOKEN_LEN=2` 丢了 1 字符 token,注释描述的行为不会发生,无害)。

## 五、值得肯定的地方(避免只报坏消息)

这套代码库的**自我诚实度是真的**,不是姿态:

- **审计签名核心扎实。** Ed25519 逐记录/逐收据签名绑定 `key_id‖log_id‖seq‖record_hash` 且有域分隔,验证时从行
  重算每个哈希而非信任列;未签名/外键/乱序行严格失败;`user_decision` 与签名收据交叉核对;`append` 包事务 +
  WAL + busy_timeout;SQLCipher 用运行时 `PRAGMA cipher_version` 门控、设了口令就拒绝明文落盘。收据删除也被
  `receipt_count`/`last_receipt_hash` 锚住(这条**是**接好的)。
- **评测诚实度经得起查。** ContractGate 重分类是保守的(把上报 miss-rate 推向更差方向);唯一的 KNOWN_MISS
  仍被计成真 miss;coverage matrix 验证每条声称的规则**真的触发过**而非只是存在;`log_safe` 脱敏广、线性、幂等、
  能处理不可见字符。
- **各原生端"编译过但没在真机跑过"的披露是准确的。** Windows UIA/GDI、macOS SCK/AX ObjC 桥、Android
  KeyStore ECDSA 都是真实现不是桩;iOS 就是个 40 行 demo,文档也这么说。
- **本轮刚做的 Landlock 读天花板:纯逻辑 `build_rule_plan` 正确(deny-by-default,9 个含变异的单测),诚实
  caveat 也准确**——系统调用路径在本容器 seccomp 下跑不到、会落回没有读天花板的 mount-ns,代码和文档都如实说了。
- **safe shell 没找到新的元字符/引号绕过**:过滤器忠实实现了文档的构造列表、跑在允许列表之前,之前几轮的绕过都
  修了且有回归测试。

## 六、产品级改进建议(比单条修复更高一层)

**1. 认证是这个产品的横切弱点,建议做一个统一的"入站信任"策略。** 情报签名(发现 1)、策略同步(11)、计费
webhook(4)、nm-host 调用者(§四)、localapi 的 LAN 开关——五个入站面各有各的认证缺口,而且默认都偏开放。
建议定一条全局原则:**任何跨信任边界的入站数据,默认 fail-closed,要么带可验证签名、要么拒绝**,并像审计签名
那样为它写一份威胁模型文档。这比逐个打补丁更能防住"下一个入站面又忘了验"。

**2. "宣称 vs 实现"的漂移是系统性问题,不是个别笔误。** 发现 3(浏览器确认)、5(网关预算)、以及六处文档漂移
都是同一形状:一句主张在某一层成立、在实际生效的那层不成立。这个项目已经有很强的自省机制(coverage matrix、
release-gate、多轮复核),建议把它延伸到**主张层面**:给每个面向用户/集成者的能力声明(商店文案、platform-matrix
的每个格子、端点表)配一个"它由哪段代码兑现 + 一个证明它真触发的测试"的链接,没有就在 CI 里标红。这正是
coverage matrix 对规则做的事,值得推广到功能主张。

**3. 网关是主要执行路径,但引擎在它上面只贡献了 `CRIT-*`。** `PLAN-*`(预算)、B1(文件容器)在网关路径上都被
遮蔽或不生效(发现 5、6)。当前靠 guard-shell 先 Deny 兜底,但这意味着"引擎独立执行"这个卖点在最常走的路径上
其实是 shell 层在扛。建议把 step-kind 映射和 FS 容器判断在网关路径上真正接通,让引擎的贡献名副其实。

**4. 检测层(vision)的可绕点都源于"公开的固定常量"。** `STRIDE_X/Y`、各阈值、5 短语注入列表——攻击者知道常量
就能构造绕过(发现 8、9、10)。两个方向:一是把采样相位/阈值做**逐帧随机化**(非公开种子),让"对齐到跨步"这
类攻击失去固定靶子;二是把硬编码模式匹配换成**结构化、模型无关**的异常扫描(`guard-privacy::anomaly` 已经有了),
减少"换个说法就绕过"。同时诚实地承认:这一层是差分启发式,不该被当成强保证——文档已经这么说了,产品文案也应
保持一致。

**5. 计费/授权:要么真做,要么删。** 现在是"webhook 能自铸令牌 + 令牌不门控任何东西"的组合,既是未来的安全陷阱、
又是一个不存在的卖点。建议先把 `发布阻塞项.md` 里加一条(webhook 未认证、不得暴露),再决定授权是真做一个门还是
改文案。
