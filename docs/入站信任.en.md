# Inbound Trust: One Design That Closes Six Inbound Faces (X-1)

> Status: **Designed + implemented**. One cross-cutting recommendation from the seventh review was that
> “authentication is a cross-cutting weakness in this product.” P0–P3 made all six inbound faces fail-closed,
> one by one. This document abstracts them into **one shared principle**, identifies which code can still be shared
> and what **should not** be forcibly unified, and defines an anti-regression consistency check. The three
> implementation items in Section 6—a single `constant_time_eq`, the `InboundOutcome` vocabulary, and the inbound-
> face inventory test—have been implemented in X-1 (crate `guard-trust`); see “Implementation status” at the end of
> Section 6.

## Why this document exists

The seventh review said: intelligence signatures, policy synchronization, billing webhooks, nm-host callers, and
localapi’s LAN switch “each have their own authentication gap, and all default toward openness.” After fixing them
one by one (see the “Implemented in” column below), the real risk is no longer “which face has not been fixed,” but
that **the next inbound face will again forget verification**. If every new inbound channel depends on its author
remembering “this must fail closed,” the property will eventually be omitted from a new face. This is the same shape
as a defect repeatedly found in this project: attacker-asserted input is used in the direction of granting access.

This document therefore establishes not another piece of code, but **a principle that can be checked, tested, and
cited in review**.

## Terminology: what counts as an “inbound face”

An **inbound face** is a location that takes external data across a **trust boundary** and **uses it to make a
security-relevant decision**. Both criteria must hold:

1. The data comes from a side the guard **does not control** (a network peer, another local process, a disk file
   writable by someone else, or an observed application/web page).
2. The data **changes guard behavior** (allow/deny, clear risk, grant a capability, or modify configuration).

An input that satisfies (1) but not (2), such as data read only for display, does not qualify. Neither does state
generated by the guard itself, which satisfies (2) but not (1).

## 1. Current state of the six inbound faces (after P0–P3)

| # | Inbound face | Trust boundary | Verification primitive | Current behavior (fail-closed or not) | Implemented in |
|---|---|---|---|---|---|
| 1 | Intelligence `ThreatBundle` | Disk file / CDN (MITM possible) | **Ed25519** over SHA-256 (`guard-intel::verify`) | Providing a public key requires authenticity: `sha256:`/unsigned is always rejected; `load_release` is strict; `load_or_default` is development-only and warns | P0-A |
| 2 | Billing webhook `POST /webhook/billing` | Network peer | **HMAC-SHA256** (`guard-billing::verify_webhook_signature`, handwritten `hmac_sha256` + `guard_trust::constant_time_eq`) | Validates `X-AgentGuard-Signature`; **no secret configured → reject every POST (503)** | P0-D |
| 3 | `DevicePolicy` synchronization | Disk / HTTP(S) | Detached **Ed25519** signature (`guard-sync::pull_policy_verified`, reusing guard-intel) | Production path requires signature verification; rejects plaintext `http://`; enforces `MAX_POLICY_BYTES` | P1-8 |
| 4 | nm-host caller identity | Local process (direct exec) | **Identity-string comparison** (`argv[1]` origin, `decide_caller_origin`) | Expected origin comes from env / `allowed-origin` file; **not configured → refuse to start** | P3 |

`guard-localapi::constant_time_eq`). **X-1 consolidated it into one implementation**,
`guard_trust::constant_time_eq`, used by both callers. Comments now mark which disposition category each of the six
faces belongs to (see the implementation status in Section 6).

## 2. The shared principle (**five rules of inbound trust**)

Inbound data must satisfy the following five rules before it is used in any security decision. These are **policy**,
independent of the cryptographic primitive used.

1. **Verify first, use second.** Complete verification before feeding data into any path that changes behavior.
   Verify a webhook before applying it, verify intelligence before `is_malicious_domain`, and verify `/v1/events`
   over the **raw bytes** returned by `parse_envelope`.

2. **Unconfigured means reject (fail-closed), not allow.** If no trust anchor is available for verification (no
   public key, no secret, or no expected origin), **reject** the data or refuse to start rather than “trust it this
   time.” This is the most consistent property across P0–P3: no intel public key → built-in baseline without loading
   disk; no webhook secret → 503; no nm-host origin → exit.

3. **Never degrade silently.** Whether refusing or degrading, **say so** through stderr, an explicit error code, or
   logs. Never appear normal while skipping verification. The most expensive gaps in the seventh review were silent
   downgrades: intel’s no-op sha256, nm-host’s warning-only behavior, and a webhook with no verification.

4. **Compare in constant time.** Equality comparisons for tokens, HMACs, and digests must be constant-time so they do
   not expose a timing side channel.

5. **Verify the exact bytes supplied by the attacker, not a retelling of them.** `/v1/events` verifies raw body bytes
   from the wire, not JSON serialized again after parsing. Intelligence verifies `signing_bytes()`. Audit validation
   uses a hash **recomputed** from the row, not the value in its claimed column. Checking a different representation
   from the object intended for verification is a classic bypass entry point.

### A derived rule requiring judgment: **degrade vs refuse**

Rule 2 says “reject when unconfigured,” but face 6 (`/v1/events`) **degrades to unsigned** rather than rejecting when
verification fails. This is not contradictory. The rule is:

> **Unverified inbound data may be accepted (degraded) only when its worst possible effect pushes state in a more
> conservative direction. If it can push state in a more permissive direction (allow, clear risk, grant, or change
> configuration), it must be rejected.**

An unsigned `/v1/events` survey can **only add risk and cannot clear risk** (`env_surveyed` and similar latches are
removed only for verified adapter assertions), so accepting an unsigned survey is safe: at worst it makes the guard
more cautious. Conversely, accepting intelligence, policy, webhook, or bearer input can **relax** behavior, so these
must be rejected rather than degraded. **This directional judgment must be answered explicitly for every new
inbound face and recorded in that face’s comment.**

## 3. Threat model (for each face: attacker capability, what verification stops, and what it does not)

| Face | Attacker capability | What verification stops | What it **does not** stop (explicitly) |
|---|---|---|---|
| 1 Intelligence | Modify disk bundle / MITM plaintext fetch | Intelligence with forged/downgraded signatures is rejected; disk is not loaded without a public key | The release registry’s **private key is a public repository fixture**—it must be replaced with `intel-keygen` before a real release; plaintext HTTP fetch remains allowed (operations chooses HTTPS) |
| 2 Webhook | Anonymous POST that mints its own entitlement | Unsigned or incorrectly signed POST is rejected | HMAC is **handwritten** rather than an audited library; entitlement currently gates only `audit-export` |
| 3 Policy sync | MITM / malicious policy host pushes a downgraded policy | Unsigned, incorrectly signed, plaintext HTTP, and oversized bodies are rejected | Desktop currently **does not feed policy into enforcement** (lazy POC), so the channel has no immediate effect until connected; it is made correct for that future day |
| 4 nm-host caller | Any local process directly execs the host | Host does not start without configured origin and exits on mismatch | A local process that can **read** the `allowed-origin` file or env can imitate the origin. This check protects against “any random process,” not “a process that can already read your configuration” |
| 5 Bearer | Local/LAN token guessing | Weak token refuses startup; non-loopback is denied by default; constant-time comparison | `--allow-lan` uses **plaintext HTTP**; a leaked token grants full access |
| 6 `/v1/events` | Forge companion survey to clear risk | Unsigned survey **cannot clear** risk; timestamp overflow fixed (P1-3) | A holder of a **leaked** or **non-fixture** adapter private key can produce assertions that verify (an inherent assumption of signatures) |

One rule runs through the table: **a signature mechanism proves that these bytes came from the key holder; it does
not prove that the key holder is trustworthy or that the private key has not leaked.** The release registry’s public
fixture private key (`agent.keys.publicly_known` in preflight, deliberately retained and mandatory to replace before
release) is the largest current example. It is **independent** from whether verification logic itself is correct.

## 4. What can be shared and what should not be forcibly unified

### What should be shared (extracted in X-1)

- **One constant-time comparison implementation.** `guard-billing::ct_eq` and
  `guard-localapi::constant_time_eq` were separate implementations. X-1 extracted
  `pub fn constant_time_eq(&[u8], &[u8]) -> bool` into a **new minimal zero-dependency crate**, `guard-trust`, and
  both callers now use it. A new crate was chosen instead of placing it in `guard-privacy` because `guard-billing`
  previously depended on no `guard-*` crate and should not acquire `guard-privacy`’s transitive dependency graph for
  a six-line function. **The benefit is more than deduplication**: one implementation needs one audit and one test,
  and one copy cannot later be “optimized” into `==` while the other remains safe.
- **A type that makes the “degrade vs refuse” judgment explicit.** A small enum plus documentation makes each
  inbound face state its category in code. X-1 implemented this as `InboundOutcome<T>` and `OnUnverified` in
  `guard-trust`, with comments on all six faces:

  ```rust
  /// How inbound data should be handled after verification. The choice follows the directional rule in Section 2 and must be justified on **that face**.
  pub enum InboundOutcome<T> {
      /// Verified; may be used for decisions in either direction.
      Verified(T),
      /// Unverified, but accepting it can at worst make behavior more conservative (for example, "a survey that can only add risk"). Explain why this is safe.
      DegradedSafe { value: T, why: &'static str },
      /// Unverified and may relax behavior — refuse it. Include the next step for operators.
      Refused(String),
  }
  ```

  This does not rewrite all six faces into one function. It gives them a **shared vocabulary**, making the chosen
  category and whether that choice is correct immediately visible in review.

### What should **not** be unified (doing so would make things worse)

- **Do not forcibly standardize cryptographic primitives.** Each of the four primitives has a non-interchangeable
  reason. Adapters use **ECDSA-P256** because their private keys must remain inside Android/iOS **hardware keystores**.
  Intelligence/policy uses **Ed25519** because signing is offline, unconstrained by hardware, and simple to implement.
  Webhooks use **HMAC** because a real provider such as Stripe/Paddle requires matching **its** signature scheme.
  Forcing one scheme would either remove hardware-keystore protection or become incompatible with providers. One
  lesson of the previous review was “implementing a mechanism too weak to support its claim”; forcing an ill-fitting
  primitive for the sake of uniformity is the same error in the opposite direction.
- **Do not put all six faces into one giant `verify_inbound()` function.** Their trust anchors come from different
  sources (env, files, registries, and request headers), and their failure dispositions differ (refuse startup vs
  degrade vs 401). The shared parts are **principle and vocabulary**, not one control flow.

In short: **unify policy, not mechanism.**

## 5. Anti-regression: make CI sound when “the next inbound face forgets verification”

P2 added `端点表与实际路由一致` (doc↔code). The X-1 counterpart is an **inbound-face inventory** test:

- Maintain an explicit inventory—a table or constants in a test—of every known inbound face.
- Assert that each face has (a) a fail-closed regression test whose name is registered in the inventory and (b) one
  of the Section 2 disposition types in code.
- Adding a new inbound face without registering it, or without a fail-closed test, turns the test red.

This test **cannot** automatically discover that a new inbound face was added; doing that requires taint analysis
and is out of scope, and the boundary must be stated honestly. What it can do is pin down the fail-closed guarantee
once a face is registered, preventing later changes from silently removing it—just as coverage-matrix ensures each
rule has been triggered by some scenario. This is also an instance of cross-cutting recommendation X-2 (claim-to-
test mapping) applied to a security property.

## 6. Implementation recommendations (small, incremental, and design-first if needed)

Ordered by small change and clear benefit; each can be done independently:

1. **Extract `constant_time_eq` to one place**, move both callers to it, and test equal same-length, unequal same-
   length, and different-length inputs. This is pure refactoring and deduplication with zero behavior change, so it
   comes first.
2. **Introduce the `InboundOutcome` vocabulary** (or an equivalent documentation convention). Initially, only label
   which category each of the six existing faces belongs to in comments, without changing control flow.
3. Add the **inbound-face inventory test** from Section 5, registering the six existing fail-closed tests.
4. Schedule each face’s **residual work** from the last column of Section 3 independently—especially the mandatory
   pre-release `intel-keygen` / `agent-keygen` key rotation. That is a release-process issue, not a code issue, and is
   tracked by `docs/发布阻塞项.md` / preflight.

**Acceptance criteria** if this design is implemented: `constant_time_eq` has one tested implementation; the
disposition category of all six inbound faces is immediately visible in code; an inventory test exists and removing
any face’s fail-closed test makes it fail; and this document matches the actual inbound-face inventory (which can be
included in the Section 5 test).

### Implementation status (X-1 implemented)

The first three items are implemented in the new zero-dependency crate `crates/guard-trust`:

1. ✅ **Single `constant_time_eq`** — `guard_trust::constant_time_eq`; both `guard-billing` and `guard-localapi`
   callers use it and the two earlier implementations are deleted. Tests:
   `常数时间比较_等长相等 / _等长不等 / _长度不同一律不等`.
2. ✅ **`InboundOutcome<T>` + `OnUnverified` vocabulary** — verification entry points for all six faces have
   comments marking them `Refuse` or `DegradeSafe` (five refuse, one degrades, directionally consistent with
   Section 2).
3. ✅ **Inbound-face inventory test** — `INBOUND_FACES` constant + tests `清册每个面都有fail_closed测试` (reads
   source files for all six faces and asserts that each registered fail-closed test function still exists; deleting
   or renaming one → red) and `清册方向性符合设计`. Anti-vacuity pins the inventory to six faces, so adding a face
   without registration fails. **Explicit boundary:** it **cannot** automatically discover a new inbound face (that
   would require taint analysis); it only guarantees registered faces cannot silently disappear.

Item 4—residual work per face, especially pre-release `intel-keygen` / `agent-keygen` key rotation—remains a release-
process issue tracked by `docs/发布阻塞项.md` / preflight and is outside the X-1 code scope.

Acceptance cross-check: one tested `constant_time_eq` implementation ✅; dispositions for all six faces visible in
code ✅; inventory test exists and is sensitive to removal of a test (mutation validation performed by renaming
`明文http被拒`, which turned the inventory test red) ✅; document and actual inventory agree, pinned by the anti-
vacuity assertion above ✅.

## Appendix: what this design **does not** claim

- It does not claim that all six faces “are now unified.” They are currently **individually** fail-closed, sharing
  only principles and vocabulary. The common code extracted by X-1—constant-time comparison, disposition vocabulary,
  and inventory test in `guard_trust`—is a **vocabulary and anti-regression pin**, **not** a unified verification
  control flow. Each face still uses its own trust-anchor source and failure disposition (see “What should not be
  unified” in Section 4).
- It does not claim that signature verification prevents private-key leakage or publication of fixture private keys.
  That is the independent issue emphasized throughout Section 3.
- It does not claim automatic discovery of new inbound faces. The Section 5 inventory is manually maintained, and
  this boundary is explicit.
