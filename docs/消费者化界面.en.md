# Consumer-Facing UI (E16): Do Not Expose Raw Technical Terms to Users

The product is for people. Before this round of work, actual UI copy included “Recent detections:
`invisible_injection, prompt_injection` · page title,” “Triggered rule: INTEL-DOMAIN,” “Forward to desktop
(Native Messaging),” and “Permission guidance (TCC).” The task selector showed `book_hotel`, while the confirmation
overlay was titled “pre-execution interception” and hard-coded entirely in Chinese. These terms are precise for
people who write the code and noise for users.

## What changed

**1. The plain-language dictionary is the single source of truth**
(`apps/extension-chromium/guard-strings.js`). Every finding kind, blocking rule ID, and pre-execution gate maps to
a “plain-language title + one-sentence explanation (+ the consequence of each of the two buttons),” with complete
English, Simplified Chinese, and Traditional Chinese entries. The popup and in-page confirmation layer both use
this dictionary. Technical identifiers (`INTEL-DOMAIN`, `payment_cta`) appear only in the expandable “Why was this
blocked?” details, preserving a path for troubleshooting and feedback.

**This is not merely a copy convention; it is a tested property**
(`apps/extension-chromium/scripts/strings.test.mjs`):

- every literal `kind:` in the content.js source must have dictionary entries in all three languages (adding a
  detection without plain-language copy makes the test fail);
- every `*_RULE_ID` constant in guard-schema’s `events.rs` must have dictionary entries in all three languages;
- every kind blocked by guard-gate must have confirmation-layer copy (title/body/allow consequence/cancel consequence);
- all three language packs must have identical key sets, and the Chinese packs may not retain untranslated English.

**2. Confirmation overlay (the product’s most important ten seconds):** the title uses plain language such as
“This step is about to make a payment”; both buttons explain their consequences. “Not now” is the visually primary
button, receives default focus, and is activated by Esc, making the safer choice easiest. “Allow once” is a
secondary button with red text. Its language follows the popup setting (the entire layer was previously hard-coded
in Chinese).

**3. Popup information architecture:** the first view says “Protecting this page · Today: X findings · Y blocked.”
The recent list uses plain language and relative time. A blocked-list entry begins with plain language such as
“Known malicious website,” while the rule ID moves into details. Language and desktop connection settings move
under “Settings.” The empty state changes from “No detection records” to the explanatory “Everything looks good…
when an action looks risky, AgentGuard will stop and ask first.”

**4. Layered desktop shell:** simulated injection, AX/SCK probe polling, enterprise policy, and raw decision logs
move into a collapsed-by-default “Developer panel.” Tasks receive plain-language names (“Book a hotel,” while the
value remains the profile id). Terms such as the “Phase 2” subtitle, “TCC,” “Reload Threat Intel,” and “Critical
Confirm” are replaced with plain language. English remnants in the zh pack, such as Optional PII, are completed.

## E17: Plain-language onboarding, accessibility, and notifications

**Onboarding page** (`onboarding.html`, opened automatically on first install without interrupting upgrades): three
cards explain what it protects, and an interactive demonstration shows a confirmation overlay before the user meets
one in practice. The demo uses the **real renderer + real dictionary** (guard-modal.js / guard-strings.js), not a
screenshot, so dictionary changes automatically reach the demo. It ends by explaining where the popup is, that the
desktop connection is optional, and that “findings remain on this device by default.”

**Shared overlay renderer** (`guard-modal.js`, extracted from content.js and shared by the content script and the
onboarding demo): role=alertdialog + aria-modal + reflected ariaLabel/ariaDescription (without the prohibited string-
attribute API). On open, focus lands on “Not now”; Tab/Shift+Tab cycle within the overlay; Esc means “Not now”; and
focus returns to the triggering element after close. Dark mode includes a complete palette because an overlay that
floats over arbitrary web pages cannot borrow the page’s colors.

**Notifications:** titles use the trilingual dictionary. The body leads with the rule’s plain-language name, such
as “Payment/transfer confirmation,” followed by the engine message, with the technical ID moved to parentheses at
the end. It no longer begins with `[CRIT-001] …`. Host decision records in the popup receive the same treatment.

## E18: Review follow-ups

- **Badge lifecycle:** opening the popup clears the badge because a viewed alert should not remain. The Critical
  pause badge “‖” is the exception: its reminder stays until the pause ends. Previously, “!” remained forever after
  being lit and users had no way to clear it.
- **Shell dictionary completeness test** (`eval/shells-i18n.test.mjs`, included in `make check-shells`): all three
  languages have identical keys; every data-i18n reference in index.html and every t("...") reference in main.js
  exists; all four values of the dynamic `action.*` key exist; and Chinese has no English remnants. `t(missing_key)`
  renders the key name in the UI (which really happened on macOS before E16) without an error or crash, so only this
  kind of test or visual inspection catches it. Mutation validation has been performed (remove the guard.task entry
  and two tests fail).
- **Plain-language desktop timeline:** the first line says “Blocked/Warning/Allowed/Recorded” instead of the engine
  enum `Block`; rule_id moves to the meta line.
- **The popup can reopen onboarding** (Settings → View feature introduction), preserving access for users who missed
  first-install onboarding.
- **STORE.md rewrite:** the old copy still said “only the desktop app can block” (the state before E2), and its
  permission table omitted explanations for declarativeNetRequest and notifications, which would block store review.

## Visual smoke test: `make ui-preview`

Logic tests cannot pin down what users actually see, so a real rendering harness exists at `eval/ui-preview/`.
Headless Chromium renders confirmation overlays (payment blocking / out of scope) and the popup (with data / empty /
English / settings state). Screenshots are written to `eval/ui-preview/out/` (gitignored; visually compare them
after UI changes). It also asserts behavior: “Not now” really prevents the page handler, “Allow once” really replays
the action, and **visible** popup text contains no raw technical term (`innerText` respects visibility, so technical
identifiers must be hidden while details are collapsed and visible after expansion). Mutation validation confirms
that leaking one raw kind in the popup immediately fails two assertions.

This is a **development tool and is not part of release-gate**. The gate must be reproducible in a minimal container,
while this harness requires playwright + Chromium. Real-device acceptance (`acceptance-runbook.md`) is the release
evidence.

## Boundaries (without pretending)

- Dictionary coverage tests use **source-literal extraction** (regular expressions for `kind: "..."` /
  `*_RULE_ID = "..."`), not the type system. They cannot see a dynamically constructed kind. None currently exists
  in the repository; the extraction regex must be reviewed if one is added.
- The popup’s “Today’s findings/blocks” counters come from the bounded recent-list buffer. They count what the UI
  shows today, not records in the audit database.
- Raw desktop-shell decision logs in the developer panel still show `action [RULE-ID] message`. They are deliberately
  retained for developers.
- Tests cannot guarantee the **quality** or idiomatic character of trilingual copy. They guarantee only that it is
  present, complete, Chinese where expected, and free of raw technical terms.
