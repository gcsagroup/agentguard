# 入站信任：一條把六個入站面收口的設計（X-1）

> 狀態：**設計 + 已落地**。第七輪複核的橫切建議之一是「認證是這個產品的橫切弱點」；P0–P3 已經
> 把六個入站面**逐個**做成 fail-closed，這份文件把它們抽象成**一條共用原則**，指出還能共用什麼
> 程式碼、以及**不該**強行統一什麼，並給一個防回歸的一致性檢查。§六列出的三個落地項（單一
> `constant_time_eq`、`InboundOutcome` 詞彙、入站面清冊測試）已在 X-1 裡實施（crate `guard-trust`），
> 見 §六末尾的「落地狀態」。

## 為什麼要有這份文件

第七輪複核的原話：情報簽名、策略同步、計費 webhook、nm-host 呼叫者、localapi 的 LAN 開關——
「五個入站面各有各的認證缺口，而且預設都偏開放」。逐個修完之後（見下表的「落地在」欄），真正的
風險不是「還有哪個面沒修」，而是**下一個入站面又忘了驗**。一個產品如果每加一條入站通道都要靠
作者當時記得「這裡要 fail-closed」，那這條屬性遲早會在某個新面上漏掉——這正是這個專案反覆抓到
的那一類缺陷的形狀（攻擊者可自行斷言的輸入被用在授予方向上）。

所以這份文件要立的不是又一段程式碼，而是**一條能被檢查、被測試、被 review 時引用的原則**。

## 術語：什麼算「入站面」

一條**入站面**（inbound face）= 一處**跨信任邊界**把外部資料取進來、並**據此做安全相關決定**的
地方。判據兩條都要滿足：

1. 資料來自守衛**不控制**的一側（網路對端、本機別的程序、可被別人寫的磁碟檔案、被觀測的應用程式/網頁）。
2. 這份資料會**改變守衛的行為**（放行/拒絕、清除風險、授予能力、改設定）。

只滿足（1）不滿足（2）的不算（比如純展示用的讀取）；只滿足（2）不滿足（1）的也不算（守衛自己產生的
中間狀態）。

## 一、六個入站面的現狀（P0–P3 之後）

| # | 入站面 | 信任邊界 | 驗證原語 | 現在怎麼做（fail-closed 與否） | 落地在 |
|---|---|---|---|---|---|
| 1 | 情報庫 `ThreatBundle` | 磁碟檔案 / CDN（可 MITM） | **Ed25519** over SHA-256（`guard-intel::verify`） | 給了公鑰就要真實性：`sha256:`/未簽名一律拒；`load_release` 嚴格，`load_or_default` 僅開發且告警 | P0-A |
| 2 | 計費 webhook `POST /webhook/billing` | 網路對端 | **HMAC-SHA256**（`guard-billing::verify_webhook_signature`，手寫 `hmac_sha256` + `guard_trust::constant_time_eq`） | 校驗 `X-AgentGuard-Signature`；**沒配密鑰→拒收所有 POST（503）** | P0-D |
| 3 | 裝置策略 `DevicePolicy` 同步 | 磁碟 / HTTP(S) | **Ed25519** 分離簽名（`guard-sync::pull_policy_verified`，重用 guard-intel） | 生產路徑要簽名驗證；拒明文 `http://`；`MAX_POLICY_BYTES` 上限 | P1-8 |
| 4 | nm-host 呼叫者身分 | 本機程序（直接 exec） | **身分字串比對**（`argv[1]` origin，`decide_caller_origin`） | 預期 origin 來自 env / `allowed-origin` 檔案；**沒配→拒絕啟動** | P3 |
| 5 | localapi bearer 權杖 `/v1/*` | 本機 / LAN | **共用密鑰**（`constant_time_eq`） | 弱權杖拒啟動；非回環繫結預設拒（要 `--allow-lan`）；常數時間比對 | 前幾輪 |
| 6 | localapi `/v1/events` 介面卡斷言 | Android 伴生（經 `adb reverse`） | **ECDSA-P256**（`guard-core::verify_adapter_body`→`verify_message`） | 簽的是 body 原始位元組（在請求標頭）；驗不過**降級為「未簽名」**——見 §四 | 前幾輪 + P1-3（時間戳） |

四種原語（Ed25519、ECDSA-P256、HMAC-SHA256、身分/共用密鑰比對）；常數時間比較原來是兩處各寫
各的（`guard-billing::ct_eq`、`guard-localapi::constant_time_eq`），**X-1 已收成一處**
`guard_trust::constant_time_eq`，兩處都改用它。六個面現在都在程式碼裡用註解標出了它屬於哪個處置
類別（見 §六落地狀態）。

## 二、那條共用原則（**入站信任五條**）

一條入站資料在被用於任何安全決定之前，必須滿足下面五條。它們是**策略**，和用什麼密碼學原語無關。

1. **先驗證，後使用。** 在把資料餵進任何會改變行為的路徑之前完成驗證。webhook 在應用前驗簽、
   情報在 `is_malicious_domain` 之前驗簽、`/v1/events` 在 `parse_envelope` 拿到的**原始位元組**上
   驗簽——都是這一條。

2. **未設定 = 拒絕（fail-closed），不是放行。** 沒有可用來驗證的信任錨（公鑰沒給、密鑰沒設、
   預期 origin 沒配）時，**拒絕**這條資料 / 拒絕啟動，而不是「這次先信」。這是 P0–P3 改動裡最一致
   的一條：intel 無公鑰→內建基線不載入磁碟、webhook 無密鑰→503、nm-host 無 origin→退出。

3. **不靜默降級。** 無論拒絕還是降級，都要**說出來**（stderr / 明確的錯誤碼 / 日誌），絕不「看起來
   正常但其實沒驗」。第七輪複核裡最貴的幾個洞都是**沉默**的降級（intel 的 sha256 空操作、nm-host
   的僅警告、webhook 的完全不驗）。

4. **比較用常數時間。** 權杖 / HMAC / 摘要的相等比較必須是常數時間的，不給計時側通道。

5. **驗證的是攻擊者提供的**那份確切位元組，不是它的轉述。** `/v1/events` 驗的是線上 body 的原始
   位元組（不是解析後重新序列化的 JSON）；情報驗的是 `signing_bytes()`；稽核驗的是從行**重算**的
   雜湊而不是信列裡的值。把「要驗的東西」和「實際驗的東西」錯開一層，是繞過的經典入口。

### 一條衍生的、需要判斷的規則：**降級 vs 拒絕**

第 2 條說「未設定就拒絕」，但第 6 面（`/v1/events`）在**驗不過**時是**降級為未簽名**、不是拒絕。
這不矛盾，規則是：

> **一份未經驗證的入站資料，只有在它最壞只能把狀態推向「更保守」時，才可以被接受（降級）；只要它
> 可能把狀態推向「更寬鬆」（放行、清風險、授予、改設定），就必須拒絕。**

`/v1/events` 的調查在未簽名時**只能加風險、不能清風險**（`env_surveyed` 之類只在驗過的介面卡斷言下
才移除鎖存），所以接受一份未簽名調查是安全的——它頂多讓守衛更緊張。反過來，情報 / 策略 / webhook /
bearer 一旦被接受就**放寬**了行為，所以它們必須拒絕而非降級。**這條方向性判斷應當在每個新入站面
落地時顯式回答，並寫進該面的註解。**

## 三、威脅模型（每個面：攻擊者能做什麼、驗證擋住了什麼、沒擋住什麼）

| 面 | 攻擊者能力 | 驗證擋住的 | **沒**擋住的（如實） |
|---|---|---|---|
| 1 情報 | 改磁碟 bundle / MITM 明文拉取 | 偽造/降級簽名的情報被拒；無公鑰不載入磁碟 | 發佈登錄檔的**私鑰是儲存庫夾具**（公開）——真發佈前必須 `intel-keygen` 換掉；明文 http 拉取仍允許（靠 https 由維運選） |
| 2 webhook | 匿名 POST 自鑄授權 | 無簽名/錯簽名 POST 被拒 | HMAC 是**手寫**的（非經稽核的函式庫）；授權本身還只門控了 `audit-export` 一處 |
| 3 策略同步 | MITM / 惡意策略主機下推降級策略 | 無簽名/錯簽名/明文 http/超大 body 被拒 | 桌面目前**沒把策略餵進 enforcement**（惰性 POC）——接上前這條通道沒有即時影響，但做對是為了那一天 |
| 4 nm-host 呼叫者 | 本機任意程序直接 exec 宿主 | 沒配 origin 不啟動；origin 對不上退出 | 一個能**讀到** `allowed-origin` 檔案或 env 的本機程序可以照著偽裝 origin——這道檢查防的是「隨便一個程序」，不是「已經能讀你設定的程序」 |
| 5 bearer | 本機/LAN 猜權杖 | 弱權杖拒啟動；非回環預設拒；常數時間比對 | `--allow-lan` 下是**明文 HTTP**；權杖一旦洩漏就是全權 |
| 6 `/v1/events` | 偽造伴生調查以清風險 | 未簽名調查**清不了**風險；時間戳溢位已修（P1-3） | 一把**洩漏的**或**非夾具的**介面卡私鑰持有者可以發驗得過的斷言（簽名機制的固有前提） |

貫穿全表的一條：**簽名機制只解決「這份位元組出自持鑰方」，不解決「持鑰方是不是可信 / 私鑰是否洩漏」。**
發佈登錄檔的夾具私鑰公開（preflight 的 `agent.keys.publicly_known`，故意保留、發佈前必換）是這條的
最大現存實例，和驗證邏輯本身是否正確是**兩件獨立的事**。

## 四、能共用什麼、不該強行統一什麼

### 應當共用（已抽出，X-1）

- **一處常數時間比較。** 原來 `guard-billing::ct_eq` 和 `guard-localapi::constant_time_eq` 是兩份
  各寫各的實作。X-1 抽成了一個**新的最小零依賴 crate** `guard-trust` 裡的
  `pub fn constant_time_eq(&[u8], &[u8]) -> bool`，兩處都改用它。選新 crate 而不是塞進 `guard-privacy`，
  是因為 `guard-billing` 本來不依賴任何 `guard-*`，不該為一個 6 行函式被拖進 `guard-privacy` 的
  傳遞依賴。**收益不只是去重**：一處實作意味著它只需要被稽核一次、被測一次，不會有一處哪天被人
  「最佳化」成 `==` 而另一處沒有。
- **一個把「降級 vs 拒絕」判斷顯式化的型別。** 一個小列舉 + 文件，讓每個入站面在程式碼裡寫出它屬於
  哪一類（X-1 已在 `guard-trust` 落地為 `InboundOutcome<T>` 與 `OnUnverified`，六個面都加了註解）：

  ```rust
  /// 一條入站資料驗證之後該怎麼處置。選哪個由 §二的方向性規則決定，並在**該面**註明理由。
  pub enum InboundOutcome<T> {
      /// 驗過，可用於任何方向的決定。
      Verified(T),
      /// 沒驗過，但接受它最壞只會更保守（如「只能加風險的調查」）。附上為什麼安全。
      DegradedSafe { value: T, why: &'static str },
      /// 沒驗過且可能放寬行為——拒絕。附上給維運的下一步。
      Refused(String),
  }
  ```

  這不是要把六個面重寫成一個函式，而是給它們一個**共同的詞彙**，讓 review 時能一眼看出某個面
  選了哪一類、以及那個選擇對不對。

### **不**該統一（會讓事情更糟）

- **不強行統一密碼學原語。** 四種原語各有其不可替換的理由：介面卡用 **ECDSA-P256** 因為私鑰要在
  Android/iOS 的**硬體金鑰庫**裡不出硬體；情報/策略用 **Ed25519** 因為是離線簽名、無硬體約束、
  實作簡單；webhook 用 **HMAC** 因為接真實 provider（Stripe/Paddle）時得對上**它們的**簽名方案。
  強行讓它們走同一套會要麼削掉硬體金鑰庫、要麼和 provider 對不上。上一輪複核的教訓之一正是
  「實作一個不足以支撐其主張的機制」——為了「統一」而套一個不合身的原語是同一個錯誤的反方向版本。
- **不把六個面塞進一個 `verify_inbound()` 巨函式。** 它們的信任錨來源（env、檔案、登錄檔、請求標頭）、
  失敗處置（拒啟動 vs 降級 vs 401）各不相同。共用的是**原則和詞彙**，不是一個控制流。

一句話：**統一策略，不統一機制。**

## 五、防回歸：讓「下一個入站面又忘了驗」這件事在 CI 裡響

P2 已經加了一條 `端点表与实际路由一致`（doc↔code）。X-1 的對應物是一條**入站面清冊**測試：

- 維護一個顯式清單（一張表 / 一個測試裡的常數），列出所有已知入站面。
- 一條測試斷言：清單裡每個面都有（a）一條 fail-closed 的回歸測試（名稱登記在清單裡），（b）在程式碼裡
  走了 §二的處置型別之一。
- 加一個新入站面卻沒把它登進清單、或沒配 fail-closed 測試 → 測試變紅。

這條測試**不能**自動發現「你新加了一個入站面」（那需要汙點分析，超出範圍，要如實說明這條邊界）；
它能做的是：一旦某個面被登記進清單，它的 fail-closed 保證就被釘住，不會被後續改動悄悄摘掉——
就像 coverage-matrix 對「每條規則都被某個情境觸發過」做的那樣。這也是橫切建議 X-2（主張↔測試映射）
在安全屬性上的一個實例。

## 六、落地建議（小、可增量、可先只做設計）

按「改動小、收益明確」排序，每條獨立可做：

1. **抽 `constant_time_eq` 到一處**，兩個呼叫點改用它，加一條測試（等長相等/不等/不等長都覆蓋）。
   —— 純重構 + 去重，零行為變化，最先做。
2. **引入 `InboundOutcome` 詞彙**（或等價文件約定），先只給現有六個面在註解裡標出它們屬於哪一類，
   不改控制流。
3. **入站面清冊測試**（§五），把現有六條 fail-closed 測試登記進去。
4. 每個面的**殘餘**（§三最後一欄）各自單獨排程——尤其發佈前必須做的 `intel-keygen` / `agent-keygen`
   換金鑰，那不是程式碼問題，是發佈流程問題，已在 `docs/发布阻塞项.md` / preflight 裡盯著。

**驗收標準**（這份設計若落地）：`constant_time_eq` 只有一處實作且被測；六個入站面在程式碼裡都能一眼
看出其處置類別；清冊測試存在且刪掉任一面的 fail-closed 測試會讓它變紅；這份文件和實際入站面清單
一致（可併進 §五那條測試）。

### 落地狀態（X-1 已實施）

前三項已實作，都在新 crate `crates/guard-trust`（零依賴）：

1. ✅ **單一 `constant_time_eq`** —— `guard_trust::constant_time_eq`，`guard-billing`、`guard-localapi`
   兩處呼叫點都改用它；原來兩份實作已刪。測試 `常数时间比较_等长相等 / _等长不等 / _长度不同一律不等`。
2. ✅ **`InboundOutcome<T>` + `OnUnverified` 詞彙** —— 六個入站面的驗證入口都加了註解，標出它屬於
   `Refuse` 還是 `DegradeSafe`（五拒一降，方向性符合 §二）。
3. ✅ **入站面清冊測試** —— `INBOUND_FACES` 常數 + 測試 `清册每个面都有fail_closed测试`（讀六個面的
   原始檔，斷言登記的 fail-closed 測試函式還在；刪/改名任一條 → 紅）與 `清册方向性符合设计`。
   反空洞：清冊釘死為六個面，新增面不登記就紅。**邊界如實**：它**不能**自動發現新入站面（那要
   汙點分析），只保證已登記的面不被悄悄摘掉。

第 4 項（各面殘餘，尤其發佈前的 `intel-keygen` / `agent-keygen` 換金鑰）仍是發佈流程問題，由
`docs/发布阻塞项.md` / preflight 盯著，不在 X-1 程式碼範圍內。

驗收對照：`constant_time_eq` 一處實作且被測 ✅；六面處置類別程式碼可見 ✅；清冊測試存在且對刪測試
敏感（已做變異驗證：改名 `明文http被拒` → 清冊測試變紅）✅；文件與實際清單一致（靠上面這條清冊
測試的反空洞斷言釘住）✅。

## 附：這份設計**不**聲稱什麼

- 不聲稱六個面「現在就已經統一」了——它們現在是**各自** fail-closed 的，共用的只有原則和詞彙。
  X-1 已抽出的共用程式碼（`guard_trust` 裡的常數時間比較、處置詞彙、清冊測試）是**詞彙和防回歸釘子**，
  **不是**一個統一的驗證控制流——六個面各自的信任錨來源和失敗處置仍然各走各的（見 §四「不該統一」）。
- 不聲稱簽名驗證能防私鑰洩漏或夾具私鑰公開——那是 §三反覆強調的獨立問題。
- 不聲稱能自動發現新入站面——§五的清冊是人工維護的，這條邊界是顯式的。
