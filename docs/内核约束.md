# 内核约束（B2）

`crates/guard-jail`，二进制是 `agentguard-jail`。设计依据是
[interception-design.md](./interception-design.md) 的 B 层。

## 这是"AgentGuard 不是沙箱"第一次不再完整成立

| | 协作式（A1 网关） | 内核执行（这里） |
|---|---|---|
| 谁来拒绝 | 守卫，因为它是执行者 | **内核** |
| 对不配合的智能体 | 无效 | **有效** |
| 覆盖范围 | 走网关的调用 | AgentGuard 启动的进程及其所有子进程 |
| 平台 | 跨平台 | **只有 Linux** |
| 约束什么 | 网关掌管的那几个工具 | **文件系统**,以及**可选的 TCP 出口端口**(E1;不含 UDP、进程、IPC) |

一个直接 `std::process::Command` 的智能体绕得过 A1，绕不过 B2——只要它是 `agentguard-jail`
启动的。

## 验证过的行为

集成测试（`crates/guard-jail/tests/内核真的在拦.rs`）每条都从 **jail 外面**用文件系统状态核对，
因为只看退出码的话，一个什么都没做的 jail 也能通过：

| 尝试 | 结果 | 外部核对 |
|---|---|---|
| 写授权内 | 成功 | 文件存在且内容正确 |
| 写授权外（父目录） | `EROFS` | 文件未创建 |
| 写 `/etc` | `EROFS` | 未创建 |
| 删 `/etc/hosts` | 失败 | 文件仍在 |
| 写 `~/.ssh` | `EROFS` | 未创建 |
| 读 `/etc/hosts` | 成功 | —— |
| 跑 `/bin/ls` | 成功 | —— |
| 没有天花板 | 整个文件系统只读 | 未创建 |
| 矛盾的 profile | **一个进程都不启动** | 未创建 |

## 两条不能搞错方向的规则

**一、约束不了就不启动。** 没有任何可用后端时 `launch()` 返回错误，**不启动任何进程**。一个
"约束不了就不约束地跑"的 jail 比没有 jail 更糟，因为使用者以为进程被关住了。

Landlock 规则集下发现在实现了（`crates/guard-jail/src/landlock.rs`），而且同样 fail-closed：
`create_ruleset` / `add_rule` / `restrict_self` 任何一步失败，`pre_exec` 就失败、子进程绝不 exec，
不会退化成不约束地跑。

**二、矛盾的 profile 拒绝启动。** 写授权落在 `/etc` 上不是配置疏忽，是把约束的意义抵消掉。
部分生效的约束在使用者看来和完全生效没有区别，所以不"尽力执行"。

## 后端，以及为什么要排序

| 后端 | 需要什么 | 说明 |
|---|---|---|
| Landlock | 内核 5.13+ 且 `landlock_*` 没被上层 seccomp 挡掉 | 优先。**不改变进程看到的文件系统** |
| mount namespace | user + mount namespace 可用 | 约束一样硬，但进程会看到一个不同的挂载树 |
| 无 | —— | 拒绝启动 |

Landlock 优先不是因为它更强，而是因为它不改变文件系统视图——mount namespace 里的进程如果
不知道自己在 namespace 里，会以各种意想不到的方式受影响。

**"内核版本够"不等于"这个机制可用"。** 写这段代码的容器内核是 6.18（Landlock 早就有了），而
`landlock_create_ruleset` 返回 `ENOSYS`，因为上层 seccomp 把它挡掉了。所以探测必须**真的试一次**，
不能查版本号。同理，mount namespace 的探测是在一个子进程里真的 `unshare` 一次——`unshare` 不可逆，
在探测里改掉当前进程的命名空间，会让后面所有逻辑跑在一个和它以为的不同的环境里。

## profile 生成是平台无关的

设计文档说 B2 要"Linux 优先，因为**生成 profile 的逻辑**才是值得做对的部分"。`profile.rs` 就是
那部分：输入 `TaskScope.paths`，输出"哪些可读、哪些可写、其余一律拒绝"。Landlock、mount namespace、
将来 macOS 的 SBPL、Windows 的受限令牌，消费的是**同一份 profile**。

三条性质从 `narrow()` 继承而来，不是这里重新实现的：没声明就是只读（不是允许一切）；grant 是
交集永不是并集；越界请求被记录成 `SCOPE-OVER-REQUEST`。

`essential_read` 里刻意**没有** `/home`、`/root`、根目录：不给动态链接器和 `/proc` 的话进程连
自己都起不来，而一个起不来的进程和一个被约束住的进程在使用者看来都是"东西坏了"——那种坏法
会让人把约束关掉。但把 `/home` 放进去等于没有约束。

## 写这个后端时的真 bug

第一版在 `unshare(CLONE_NEWUSER)` **之后**才调 `getuid`。进入一个还没有映射的 user namespace
之后，进程看到的自己是 overflow uid（65534/nobody），于是它试图把 ns 内的 0 映射到 65534——
一个它并不拥有的外部 uid——内核返回 `EPERM`。

`EPERM` 读起来像"权限不够"，实际是"你问错了问题"。这个 bug 在一个用 Python 写的探针里不会
出现，因为探针的写法不同（那里在 fork 前就取了 uid）。只有把顺序写对才行。

同一处还有第二个：`setgroups=deny` 的写入失败被 `let _ =` 忽略了，于是真正的原因会被后面
`gid_map` 的 `EPERM` 掩盖。现在它是一个会报错的步骤。

`AGENTGUARD_JAIL_DEBUG=1` 会打印九个步骤各自的结果，那是定位这类问题唯一有效的办法。

## 怎么用

```
# 看这台机器有哪些后端
agentguard-jail --probe

# 在天花板约束下启动
agentguard-jail --plans policies/task-plans.yaml --task book_hotel -- /bin/bash
```

不给 `--plans` 也能跑，但那是**整个文件系统只读**，不是不约束。

## B2 没有做到的事

**只有 Linux。** macOS 的 `sandbox-exec`、Windows 的受限令牌 + Job Object 是 B3，没做。Android
在没有 root 的情况下做不到，永远。

**~~只约束文件系统。~~ 现在也能(可选地)约束 TCP 出口(E1,见下节)。** 一个被关住的进程
默认仍可 fork、用 IPC、开 UDP(含 DNS/QUIC);网络方面,只有当任务声明了 `scope.net` 时,
出站/监听的 **TCP 端口**才被内核限住。没声明 `scope.net` 就和以前一样——网络不管。

**只约束 AgentGuard 启动的进程。** 使用者自己起的智能体在约束之外——约束是在启动时落下的。

**提权可以逃出去。** Landlock 和 user namespace 约束的是进程，不是 root。

**mount-ns 作为 root 跑时 `/dev` 仍可写(第七轮复核发现 12,已默认拒绝)。** mount-ns 后端把
文件树 remount 成只读时**跳过** `/dev`、`/proc`、`/sys`(伪文件系统);非 root 下这基本无害,
但以 uid 0 运行时新 user namespace 里 0 映射到 0,`/dev` 下的块设备可写,`dd of=/dev/sdX`
就绕过了整棵树的只读约束。因此 `launch()` **默认拒绝以 root 运行 mount-ns 后端**(`JailError::
RootMountNamespace`);明确接受这个风险的运维可设 `AGENTGUARD_JAIL_ALLOW_ROOT=1`(会打警告)。
Landlock 后端不受影响(它按路径约束,不靠 ns 里的 uid 映射),所以 root + Landlock 仍可跑。
更彻底的做法(把只读扩到 `/dev`)有破坏被约束程序的功能风险,留作可选加固,没做。

**授权目录内部不受约束。** jail 是一道边界，不是一次判断。授权目录里的删除是允许的——这既是
它的意义，也是它的极限。

## 这一层实际强制了什么(第六轮复核之后重写)

上面那些表格描述的是**意图**。一次独立复核证明其中三条与实现不符,而两条已经修好、一条
如实降级。

### 修好的两条

**一、被约束进程曾经可以自己撤销只读。** jail 里的进程在自己的 user namespace 里是 ns-root
并持有全部 40 个 capability,而只读挂载没有被 lock。一次裸 `mount(MS_REMOUNT|MS_BIND, "/")`
就把整棵树变回可写 —— 三行代码,root 与非 root 启动都成立:

```text
CapEff:    000001ffffffffff          <- ns 内全部 capability
raw remount / -> 0 errno 0           <- 撤销只读成功
写只读区 -> 成功
```

顺带纠正本文档原来那句"提权可以逃出去……约束的是进程,不是 root":它会让读者以为"只要
agent 不是 root 就关得住"。**不需要任何提权。**

现在 `exec` 之前会装一个手写的 seccomp 过滤器,拒掉整个挂载家族和重开 userns 的路径:
`mount` / `umount2` / `pivot_root` / `move_mount` / `open_tree` / `fsopen` / `fsconfig` /
`fsmount` / `mount_setattr` / `unshare` / `setns`。**装不上就拒绝启动。**

**二、只读不是递归的。** `mount(2)` 的 `MS_REMOUNT` 忽略 `MS_REC`,所以原来对 `/` 的单次
remount 只让 `/` 这一个挂载变只读。任何独立挂载的目录保持可写 —— 生产上常见的独立 `/home`、
`/var`、tmpfs `/tmp`、附加磁盘。本文档表格里"写 ~/.ssh → EROFS → 未创建"那一行,在家目录
位于独立挂载时是**假的**(实测私钥被覆盖、后门 authorized_keys 被写入)。

现在枚举 `/proc/self/mountinfo` 逐个 remount(由深到浅)。**一条如实的残余限制**:从外层
命名空间继承来的 locked 挂载改不了(本容器里的 `/opt/claude-code` 就是),这种情况会打一条
警告点名该挂载点,而不是静默跳过。

### 第三条:读约束——从"未实现"到"在 Landlock 后端实现,但落地路径在本容器测不到"

**问题原样保留(这是它当初为什么被降级)。** `Profile::read` 的文档说"空表示什么都不能读",
本文档说"其余一律拒绝"—— 而 mount-ns 后端从头到尾**不消费** `profile.read`。整棵文件系统在
DAC 允许范围内全可读(实测读到了 `/etc/shadow` 和 `/root`)。能执行读天花板的机制是 Landlock,
因为它是一个按路径**拒绝**访问(含读)的 LSM;mount namespace 做不到,它只能把树变只读。

**现在 Landlock 后端把读天花板实现了**(`crates/guard-jail/src/landlock.rs`):

> 规则集 `handled` 同时治理读和写(`HANDLED_ALL = READ_SET | WRITE_SET`)。**不在任何一条
> `path_beneath` 规则里被授予的路径就被拒——包括读。** 授予的只有:系统运行时根
> (`/usr` `/lib` … `/etc` `/proc` `/sys` `/dev`,程序不能读它们就起不来)、目标二进制自己所在
> 的目录、以及 profile 声明的读/写授权。`/root/.ssh`、别的用户的家目录、声明之外的项目目录都
> 不在其中,于是被拒。

**这是一个用户数据的读天花板,不是全盘的。** `/etc` 在运行时根里(动态链接器要读它),所以
`/etc` 下的东西仍可读;要连 `/etc` 也按需授予,得先知道目标程序到底读哪些运行时文件,那是
另一件事。文档不该把它说成"读不到任何东西",它是"读不到你声明范围之外的用户数据"。

**一条不能含糊的诚实边界:这段代码的系统调用路径在本容器里一次都没跑过。** 容器内核有
Landlock,但上层 seccomp 把 `landlock_*` 挡了(`probe` 实测 `ENOSYS`)。所以:

- **安全逻辑**(哪个路径拿到哪些权限、读天花板到底漏不漏)抽进纯函数 `build_rule_plan`,在
  本容器里有 9 条单元测试完整覆盖,并做了变异验证:把 `/root` 混进运行时根 → 读天花板测试
  立刻变红;把写授权的读位抹掉 → essential_write 可读性测试立刻变红。**逻辑是被钉住的。**
- **系统调用序列**(`create_ruleset` / `add_rule` / `restrict_self`)尽量薄且 fail-closed,但它
  在一台 `landlock_*` 可用的机器上是否真的拒掉越界读,**我在这里没能实测**。这一步的正确性
  依赖 ABI 常量和调用序列写对,而不是依赖一次通过的测试。

**还有一条部署现实:在本容器上,读天花板仍然不生效。** 因为 Landlock 在这里 `ENOSYS`,
`best_available()` 落到 mount-ns 后端,而 mount-ns 后端没有读天花板。读天花板只在一台
`landlock_*` 没被 seccomp 挡掉的机器上成立。`agentguard-jail` 在只有 mount-ns 可用时打印的
"N 个可读"仍然是**声明的**授权、不是被强制的边界,这一点没变。

## 网络出口天花板（E1，opt-in、内核强制）

消费者最怕的一件事不是智能体删文件,是它**把数据发出去**、或**替你按下付款**。文件系统天花板
拦不住这个——一个被关在只读目录里的进程照样能 `connect()` 出去。E1 把那条"唯一不依赖被约束方
配合"的边界从文件系统扩到**网络出口**。

### 怎么声明

任务计划的 `scope.net`(和 `scope.paths` 放在同一份声明里,理由一样:引擎推理的和内核执行的必须
是同一句话):

```yaml
book_hotel:
  scope:
    net:
      connect_tcp: [443]   # 只许出站连 443,其余 TCP 出站一律拒
      bind_tcp: []         # 一个监听端口都不许
```

* `connect_tcp: []`(空列表)= 明确的"不许开任何出站 TCP",和 `paths: {write: []}` 是"只读"
  同一种明确的"不给"。
* **不声明 `net` 整节** = 网络不管(现状)。

### 为什么默认不是"拒网",而 `paths` 默认是"只读"

方向看着反了,是**有意**的。Landlock 的网络约束是 ABI v4(内核 6.7,2023 年底)才有的;文件
约束早在 5.13 就有。如果把"默认拒网"做成强制,jail 会在内核 6.1–6.6(有文件约束、没网络约束)
上**整个拒绝启动**——用一个还没普及的能力废掉一个已经能用的边界。所以网络天花板是**声明才强制**,
文件天花板仍然默认只读。

### fail-closed:内核给不了就拒,绝不静默敞开

这是最要紧的一条。声明了 `scope.net`、但:

* 这台机器 Landlock ABI < v4(内核太旧)→ **拒绝启动**(`landlock::enter` 里查 ABI,返回 `Err`,
  `pre_exec` 失败,子进程绝不 exec)。
* 可用后端是 mount-ns 而非 Landlock(mount-ns 管不了网络)→ **拒绝启动**
  (`JailError::NetUnenforceable`)。

两条都不会退化成"文件系统关住了、网络其实敞开着"跑——那正是一份读起来像保护、实则漏一半的
profile,和上一轮复核抓的"沉默降级"是同一个错误。

### Landlock 网络覆盖什么、**不**覆盖什么（如实）

Landlock 网络只治理 **TCP 的 `bind` 和 `connect`,而且只到端口号**：

* 覆盖:"不许开出站 TCP"、"只许连 443"、"只许监听 8080"。
* **不**覆盖:按**主机/IP**过滤——端口 443 连 `evil.example` 和连 `stripe.com` 一样放行(那是
  `scope.hosts` 在**协作式**路径上判的,不是内核这层)、**UDP**(含 DNS、QUIC)、原始套接字、
  已建立连接上的收发。要"只能连某主机"或"连 DNS 都禁",需要网络命名空间 + 强制代理,是另一层,
  没做。

所以 `scope.net` 和 `scope.hosts` 是**互补**:`hosts` 细(到主机名)但协作式(绕过引擎直接
`connect` 就没用),`net` 粗(到端口)但非协作式(内核拦,绕不过)。一句话:**能拦住"绕过引擎
直接联网"的,只有 `net` 这层;能说清"该发给谁"的,是 `hosts` 那层。**

### 同一条诚实边界:syscall 路径在本容器测不到

和文件天花板完全一样。网络的**安全逻辑**(哪个端口拿到 connect 位、哪个拿 bind 位、空天花板是否
治理两类)在纯函数 `build_net_plan` 里,本容器 5 条单元测试完整覆盖并做了变异验证(把"治理
bind+connect 两类"改成只治理 connect → 测试立刻变红)。**syscall 序列**(v4 `create_ruleset` +
`LANDLOCK_RULE_NET_PORT`)尽量薄且 fail-closed,但它在一台 ABI≥v4 的真机上是否真的拒掉越界
`connect`,本容器(seccomp 挡了 `landlock_*`)没能实测——这一步的正确性依赖 ABI 常量和调用序列
写对,不依赖一次通过的测试。真机端到端验收未做,如实列在这里。
