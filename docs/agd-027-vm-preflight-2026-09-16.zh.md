# AGD-027：VM 就绪前提与持久提交分项

日期：2026-09-16。当前工作基线 `442f401`。结论：修复了性能脚本把 Docker 版本响应当作 Linux VM 已运行的问题；产品代码与审计同步要求没有改变，读取性能仍未通过。复核还发现两份采样计划的轮次字段相互矛盾，两批均不计正式验收通过。

## VM 前提的实际缺陷与修正

[原预算](agd-002-performance-baseline-2026-09-09.zh.md)明确排除 VM 冷启动，并要求 Docker VM 已运行。原脚本只查询 Docker 版本。本机 Docker 日志显示：07:28:32.578 UTC 在创建容器时才从已空闲 40 分钟的状态启动 VM，07:28:33.600 才启动完成；该轮隔离网关启动耗时 2,789.28 ms，原始失败保留，不能事后减去一段耗时当成通过。

Docker 官方说明，Resource Saver 会在空闲时停止 Linux VM，部分元数据命令仍可响应，不一定唤醒 VM。见[官方说明](https://docs.docker.com/desktop/use-desktop/resource-saver/)。本次结论同时依据本机启动日志，不仅依据文档推断。

新增 `docker-vm-preflight.mjs`：在正式计时前，用已有固定镜像执行一个无挂载、断网、只读、非 root 的短命容器，读取真实 Linux 启动身份、运行时长及隔离标志；成功后清理，再进入原三路由计时。超时或清理状态未知时拒绝继续。运行、清理和网关绑定相同的本地 Unix Socket。没有关闭省电模式、下载新镜像或留置常驻容器。此修正位于测试工具，不是网关运行时优化。

两轮就绪耗时分别为 2,354.51 ms 和 257.15 ms；内核运行时长分别为 1.93 秒和 16.41 秒，启动身份相同。这分别记录了本批实际冷启动后就绪和已运行状态。正式网关启动两轮均在原预算内，但读取仍有失败。

**计划缺陷：**两份 `comparison-plan.json` 的目的与 `order` 指向两轮开发候选，但复制了旧计划的 `rounds: 4` 及 release 说明。原件及摘要保持，最终核对器明确输出 `protocol_consistent: false`、两项计划冲突和 `performance_passed: false`。早期 `verification.json` 没有检查这项矛盾，仍保留作为核对器缺陷证据；以 `verification-final.json` 为本批结论。后续验收必须在采样前验证轮次一致性，不能补写原计划使失败消失。

## 持久提交与 WAL

复用只增加计时输出的诊断二进制，保持两次 FULL/fullfsync 提交及默认检查点，每轮 5 次预热后连续读取 300 次。两轮共 610 次读取、2,442 条实际审计；每次返回后在请求计时之外读取 WAL 索引计数，区分是否观察到回填增加或帧数回退。

| 诊断轮次 | 全部请求 p95 / ms | 未观察到检查点或复用的样本 / p95 | 观察到检查点或复用的样本 / p95 | 持久提交占比 |
| --- | ---: | --- | --- | ---: |
| 1 | 17.64 | 283 / 14.49 ms | 17 / 35.67 ms | 90.58% |
| 2 | 13.89 | 287 / 12.62 ms | 13 / 23.58 ms | 91.42% |

SQL 执行平均仅约 0.19／0.17 ms。17／13 是观察到计数转换的请求数，包含检查点之后的 WAL 复用，不是独立检查点次数；这是索引状态诊断，不是系统调用追踪。未观察到转换的请求仍超过 10 ms，所以仅改变检查点参数不足以解决问题。

SQLite 的 WAL 自动检查点可能增加个别提交耗时，FULL 则在每次提交时同步 WAL；见 [WAL 官方说明](https://www.sqlite.org/wal.html)和[同步配置](https://sqlite.org/pragma.html#pragma_synchronous)。本批未降低同步等级、取消执行前记录、延迟持久结果或改动历史数据库。
