# 浏览器执行前阻断（E2）

> 状态:**已落地(in-page 向量)**。把 Chromium 扩展从"事后通知"升级为"执行前拦截"——但只在
> 它**够得着**的地方,边界如实划清。

## 为什么"事后通知"改不成"执行前阻断"——除非换个位置

`background.js` 收到宿主判决时,那个 DOM 事件**已经发生**了:原生消息是异步的,宿主在事件之后
才看到它,没有东西可以 hold。这不是实现偷懒,是位置决定的——观察者拦不住它观察到的东西。

E2 的做法是**换位置**:拦截逻辑搬进**内容脚本**,它跑在页面里、是同步的。一个捕获阶段的
`submit` / `click` 监听器能在动作**真正发生之前** `preventDefault()` 把它按住,弹一个本地确认,
只有用户点"允许一次"才程序化重放放行。这条路径**不经过**那趟异步宿主往返,所以它能真的 hold。

## 拦什么

内容脚本(`content.js`)在捕获阶段同步判两类页面自身的动作,判决逻辑在纯模块 `guard-gate.js`:

| 触发 | 判据 | 处置 |
|---|---|---|
| 表单 `submit` | 表单里有"陷阱控件 + 非必要 PII"已填 | preventDefault → 本地确认 → 允许才 `form.submit()` |
| `click` / `submit` | 目标是付款/转账 CTA(文案匹配) | 同上 |
| 网络请求 / 导航 | 主机在宿主判定的拦截名单里 | declarativeNetRequest 在请求发出前 block(`background.js`) |

前两类是页面 DOM 动作,内容脚本同步拦;第三类是网络层,交给 DNR(MV3 里请求发出前拦的正确 API)。
每拦一次都 `sendMessage` 回 background,记进最近列表并转宿主进签名审计——一次执行前阻断和一次
判决一样,是该留痕的事件。

## 覆盖什么、**不**覆盖什么(如实)

覆盖:页面**自己的** DOM 提交/点击(付款 CTA、陷阱下的 PII 提交);以及命中主机名单的导航/请求。

**不**覆盖:

- 一段直接 `fetch()` / `XMLHttpRequest` 到付款 API 的脚本——它不产生 DOM 事件,除非目的地命中
  DNR 的主机规则。
- 跨源 iframe 里的动作(内容脚本按 manifest 只在主框架跑)。
- **任何原生 app 的动作**——浏览器扩展够不到。

一句话:这道门挡的是"在这个页面上把这一步走完",不是"这台机器上任何联网"。要拦"绕过页面直接
联网",那是 Linux jail 的 `scope.net`(E1)那一层,不是这里。

## fail 方向:两道门方向**不同**,都是有意的

- **内容脚本同步门:fail-closed 倾向。** 判决逻辑没加载(`self.AgentGuardGate` 缺失)时,`gateEvent`
  直接返回、不改变页面行为——它不会在"不确定"时假装拦住。但更要紧的是:它拦下时是**真的**拦下
  (preventDefault 已经执行),不依赖任何异步回应。
- **DNR 网络门:fail-open,且已声明。** DNR 装不上时记一条、不假装拦住。**故意**不做成 fail-closed:
  一个连不上 DNR 的扩展不该把用户整个浏览器都弄到上不了网。它是内容脚本同步门的**加**一层,不是
  唯一防线。

把这条写出来,是因为"某处 fail-open"如果不声明,就和"以为处处 fail-closed"一样危险。

## 验证到哪一步(诚实)

- **判决逻辑**(`guard-gate.js`:哪类 finding 该拦、DNR 规则怎么构造)是纯函数,`scripts/gate.test.mjs`
  在 node 里有 7 条单测,含反面用例(普通 finding 不拦,避免门变成噪音)和 DNR 规则去重/排序/稳定 id。
  进 `make check-extension-gate` 与 release-gate。
- **DOM 接线**(`content.js` 的捕获监听、重放)只做 `node --check` 语法检查——本环境没有真 Chrome。
- **真 Chrome 端到端未验证**:一次真实的付款提交在真浏览器里是否被这道门按住、"允许一次"重放是否
  精确等价,没在真机上跑过。这和 jail 的 syscall 路径、macOS 的 AX 推送是同一种诚实:安全逻辑用
  可测的纯函数钉住,平台接线那层如实标为未在真环境验证。
