# 浏览器执行前阻断（E2）

> 状态:**已落地(in-page 向量)**。把 Chromium 扩展从"事后通知"升级为"执行前拦截"——但只在
> 它**够得着**的地方,边界如实划清。

## 为什么"事后通知"改不成"执行前阻断"——除非换个位置

`background.js` 收到宿主判决时,那个 DOM 事件**已经发生**了:原生消息是异步的,宿主在事件之后
才看到它,没有东西可以 hold。这不是实现偷懒,是位置决定的——观察者拦不住它观察到的东西。

E2 的做法是**换位置**:拦截逻辑搬进**内容脚本**,它跑在页面里、是同步的。一个捕获阶段的
`submit` / `click` 监听器能在动作**真正发生之前** `preventDefault()` 把它按住,弹一个本地确认,
只有用户点"允许一次"才程序化重放放行。这条路径**不经过**那趟异步宿主往返,所以它能真的 hold。

## 拦什么

内容脚本(`content.js`)在捕获阶段同步判两类页面自身的动作,判决逻辑在纯模块 `guard-gate.js`:

| 触发 | 判据 | 处置 |
|---|---|---|
| 表单 `submit` | 表单里有"陷阱控件 + 非必要 PII"已填 | preventDefault → 本地确认 → 允许才 `form.submit()` |
| `click` / `submit` | 目标是付款/转账 CTA(文案匹配) | 同上 |
| **页面直发的 `fetch` / `XHR`** | URL 路径是付款形状(pay/checkout/charge/transfer…)且非只读方法 | 页面世界(`guard-page.js`)包裹后 await 确认才发,拒绝则 reject/abort(E2.1) |
| 网络请求 / 导航 | 主机被**引擎**判为恶意域(`INTEL-DOMAIN`) | 宿主把该主机放进响应的 `block_hosts`,`background.js` 装 declarativeNetRequest 规则,请求发出前 block(E5) |

前两类是页面 DOM 动作,内容脚本同步拦;第三类是网络层,交给 DNR(MV3 里请求发出前拦的正确 API)。
每拦一次都 `sendMessage` 回 background,记进最近列表并转宿主进签名审计——一次执行前阻断和一次
判决一样,是该留痕的事件。

## 覆盖什么、**不**覆盖什么(如实)

覆盖:页面**自己的** DOM 提交/点击(付款 CTA、陷阱下的 PII 提交);以及命中主机名单的导航/请求。

**~~一段直接 fetch()/XHR 的脚本~~ E2.1 已补上(在能抢到的前提下)。** 页面世界的 `guard-page.js`
包裹 `window.fetch` 和 `XMLHttpRequest`,对付款形状的出站请求在发出前 await 确认。仍**不**覆盖:

- 一段在我们之前就抓走了原始 `fetch` 引用的脚本(早于 `document_start`、或从干净 iframe 借来的
  `fetch`)——MAIN world 里页面和我们平权,谁都能改 `window.fetch`,所以这是**尽力而为**不是铁壁。
- 判据只看 URL 路径的付款形状、不看 body(body 因站而异、误判高,误拦比漏拦更容易让人关掉门),
  所以它拦"长得像付款的直发请求",不是"任何出站"。
- 跨源 iframe 里的动作(内容脚本按 manifest 只在主框架跑)。
- **任何原生 app 的动作**——浏览器扩展够不到。

一句话:这道门挡的是"在这个页面上把这一步走完",不是"这台机器上任何联网"。要拦"任何出站到
某主机",那是 DNR(按主机)和 Linux jail 的 `scope.net`(E1,内核按端口)那两层,不是这里。

### E5:引擎判决 → 浏览器网络层硬拦(把两层接上)

DNR 那一行以前是"如果宿主判定要拦某主机"——但**没有东西**在产生这个名单,`block_hosts` 是条空
接线。E5 把它接上了:引擎本来就会判"这个 url 的主机是恶意域"(`is_malicious_domain` → 一条
`INTEL-DOMAIN` 的 Block 判决),现在宿主(`guard-nm-host`)把那个主机名从判决里抠出来,放进响应的
`block_hosts`,`background.js` 据此装一条 DNR 规则。于是链条闭合:**引擎判恶意 → 浏览器在该主机的
下一个请求发出前就硬拦**,而不再只是弹一个事后通知。

抠主机名靠的是一个**共享契约**(`guard_schema::INTEL_DOMAIN_RULE_ID` + `MALICIOUS_DOMAIN_MSG_PREFIX`):
生产端(guard-core 发判决)和消费端(nm-host 解析)引用同一对常量,措辞一改两边一起改、编译期就
发现——不会一端悄悄改了另一端解析出空。只认结构化的 `INTEL-DOMAIN` rule_id、只取前缀后第一个词
(主机名不含空白,门追加的" (user denied…)"后缀被自然切掉)。这条抠取逻辑是纯函数,有单测含反面
用例(别的 rule_id 不抠、无前缀不抠、带门后缀也只取主机)。

**如实**:DNR fail-open(装不上不假装拦住,免得把浏览器弄到断网),真 Chrome/Firefox E2E 未验证;
恶意域清单目前来自内置情报基线(发布前 `intel-keygen` 换钥那条仍在 `docs/发布阻塞项.md` 盯着)。

### E2.1 的 fail 方向

- 命中付款形状 → **拦住等确认**:`fetch` 返回一个 await 决定的 Promise,拒绝则 reject;`XHR` 在
  确认前不真正 `send`,拒绝则 `abort`。请求在"允许一次"之前一个字节都没发。
- 内容脚本 15s 内没回应(极端情况)→ **fail-open 放行**,已声明:这一层是加的一道,不该因为它
  自己卡住就把用户的正常请求全掐死。真正的防线是多层叠加,不是这一层单点。

## fail 方向:两道门方向**不同**,都是有意的

- **内容脚本同步门:fail-closed 倾向。** 判决逻辑没加载(`self.AgentGuardGate` 缺失)时,`gateEvent`
  直接返回、不改变页面行为——它不会在"不确定"时假装拦住。但更要紧的是:它拦下时是**真的**拦下
  (preventDefault 已经执行),不依赖任何异步回应。
- **DNR 网络门:fail-open,且已声明。** DNR 装不上时记一条、不假装拦住。**故意**不做成 fail-closed:
  一个连不上 DNR 的扩展不该把用户整个浏览器都弄到上不了网。它是内容脚本同步门的**加**一层,不是
  唯一防线。

把这条写出来,是因为"某处 fail-open"如果不声明,就和"以为处处 fail-closed"一样危险。

## 验证到哪一步(诚实)

- **判决逻辑**(`guard-gate.js`:哪类 finding 该拦、DNR 规则怎么构造)是纯函数,`scripts/gate.test.mjs`
  在 node 里有 7 条单测,含反面用例(普通 finding 不拦,避免门变成噪音)和 DNR 规则去重/排序/稳定 id。
  进 `make check-extension-gate` 与 release-gate。
- **DOM 接线**(`content.js` 的捕获监听、重放)只做 `node --check` 语法检查——本环境没有真 Chrome。
- **真 Chrome 端到端未验证**:一次真实的付款提交在真浏览器里是否被这道门按住、"允许一次"重放是否
  精确等价,没在真机上跑过。这和 jail 的 syscall 路径、macOS 的 AX 推送是同一种诚实:安全逻辑用
  可测的纯函数钉住,平台接线那层如实标为未在真环境验证。
