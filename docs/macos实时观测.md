# macOS 观测实时化（E3）

> 状态:**已落地(树信号 push + 合并器);像素仍采样;真机未验证**。把 macOS 的 UI 树观测从
> 固定轮询改成"变了就抓",压小"边界"里那条"不是实时监控,轮询间隙内的动作可能看不到"。

## 问题:轮询间隙

macOS 的 UI 树原来每 2.5s 抓一次 AXUIElement 快照。一个在两次轮询之间出现、又在下次轮询前消失
的东西——一闪而过的确认框、一次快速的自动填充——可能整个落在间隙里,守卫看不到。

## 做法:AXObserver 推送 + 纯合并器 + 兜底轮询

三层,各司其职,边界清楚:

1. **AXObserver 推送**(`native/AgentGuardAX.m`,FFI 在 `ax_native.rs`)。注册前台应用的树变化通知
   (值变、焦点变、窗口建/毁、标题变)。变化**发生时**推一个信号过来,而不是等下一个轮询点。
   回调只做一件事:把一个原子计数 +1。尽量薄。

2. **纯合并器**(`ax_push.rs`,`PushCoalescer`)。不能每来一个通知就抓一次——一次输入会连发几十个
   `kAXValueChangedNotification`,逐个抓会把 CPU 打满(而"卡"和"看不到"一样会让人关掉守卫)。所以
   推送先进合并器:
   - **去抖** `DEBOUNCE_MS`(150ms):收到通知后等一小段安静再抓,把连发合并成一次,抓到稳定的树。
   - **延迟上限** `MAX_LATENCY_MS`(800ms):通知持续不断、安静永远等不到时,也强制抓一次,保证
     "变了到抓到"的延迟有上界。

3. **兜底轮询** `FALLBACK_FLOOR_MS`(3s)。推送在时,它只是"漏网兜底";推送**不在**时(observer 注册
   失败、非 macOS),它退化回轮询语义。**不因为上了推送就把轮询这条命去掉**——observer 断了也不会
   变成失明。

效果:一次树变化通常在 150ms 内被抓到(而不是最坏等一整个 2.5s 周期),持续变化至少每 800ms 抓
一次,完全没推送时至少每 3s 抓一次。

## 驱动怎么用

```rust
adapter.start_ax_push()?;              // 会话开始:注册 observer(失败则退回纯兜底轮询)
loop {
    let now = now_ms();
    let captured = adapter.maybe_capture_ax(now)?;  // 喂通知给合并器,该抓就抓
    // captured==true 时可顺带抓一帧像素做配对
    sleep(tick);
}
adapter.stop_ax_push();                // 会话结束
```

`maybe_capture_ax` 把"取通知计数 → 喂合并器 → 判该不该抓 → 抓 → 标记"合成一步,驱动只管定时调它。

## 两条如实的边界

**一、像素捕获仍然是采样的。** AXObserver 是**树**信号,不是**帧**信号。E3 压小的是**树**观测的
间隙,不是像素的。像素分析(隐写、帧摘要)仍按 1.5s 采样——一个只在像素里、不动 AX 树的变化
(比如一张贴上来的图),它的间隙没变。要把像素也做成事件驱动是另一件事(ScreenCaptureKit 的
内容变化回调),没做。

**二、真机未验证。** 合并器是纯逻辑,在本环境有 6 条单元测试完整覆盖(去抖、延迟上限、兜底、
抓完清账、冷启动),并可跑变异验证。但 **AXObserver 的注册和 Objective-C 回调只在 macOS 上编译**
(`check-macos-cfg` 把 Rust 那半边改写成 Linux 来做类型检查,`.m` 桥根本不参与本环境编译),真机上
一次真实的树变化是否确实触发回调、延迟是否落在预期窗口,**没在 macOS 上跑过**。这和 jail 的
syscall 路径、浏览器的 DOM 接线是同一种诚实:安全/时序逻辑用可测的纯函数钉住,平台接线那层如实
标为未在真环境验证。

一句话:这是**更快、且间隙有上界**,不是**零间隙**。
