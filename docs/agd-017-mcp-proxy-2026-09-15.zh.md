## 已完成的传输组件

新增 Unix 下游 `StdioClient`，限定 MCP **2025-06-18**。它接管已有子进程的三个管道，执行初始化、完整工具发现和文本工具调用；不负责启动第三方程序，也不授予执行权限。当前主网关没有连接这条路径，外部登记依然显示 `dispatch_supported:false`，不会向模型发布第三方工具。Windows 暂不提供该传输组件。

请求按整数 id 串行发送，没有重连和自动重试。写入、stdout 和 stderr 都是非阻塞操作，共用每次操作的总时限；初始化和初始化完成通知共用同一个时限。服务不读输入、不断输出或只返回半行时，仍能处理超时和取消。传输故障关闭管道子进程，后续调用拒绝；容器等外部执行单元必须由调用者另行清理和核实。

| 范围 | 当前限定 |
|---|---|
| 请求 | JSON 正文最多 32 KiB，换行另占 1 字节 |
| 响应 | 每行 JSON 最多 128 KiB，换行另占 1 字节 |
| 诊断输出 | 每会话累计最多 64 KiB；不保存、渲染或返回原始 stderr |
| 工具清单 | 最多 64 个、名称不重复；名称采用已有登记支持的 32 字节 ASCII 范围 |
| 时间与并发 | 单通道单请求，每次最多 30 秒；轮询间隔最多 40 毫秒 |
| 支持的结果 | 文本 content，可保留 object 类型的 structuredContent；RPC 错误仍是不可信响应 |
| 明确不支持 | 版本回退、分页、批量响应、服务端请求、异步通知、图像／音频／资源返回、会话重连和重放 |

JSON 解析拒绝重复键（包括嵌套对象）、错误 id、结果与错误同时出现、额外响应及无效 UTF-8。服务发送 `tools/list_changed` 时关闭通道；后续代理须重新连接、观测和复核，不能复用旧批准。`annotations`、`outputSchema`、`title` 等清单字段原样保留，不能把其中的只读提示当成授权。

`Failure.dispatched` 仅表示至少一个请求字节已写入管道。它不能证明服务执行，也不能证明服务没有执行。超时、断连及协议错误发生在派发后时，后续代理必须保留结果未知；有效 RPC 错误也不能单凭错误码推断没有副作用。

## 原始失败与修正

- `stdio-tests-01.log`：首轮 7/8 通过。“写入前超时”夹具用大块填管道，大块被拒时仍可能放下较小请求，且 SIGSTOP 发出后未等进程实际停止；实际通道正确记录为已写入字节。修正夹具，等待停止状态，再用单字节耗尽余量，验证同一超时与未派发断言。原失败保留。
- `workspace-01.log`：完整并发回归再次发现同一写满管道夹具的时序问题。改为服务在下一次 read 之前主动 SIGSTOP，父进程确认停止后再填管道，排除已有读取在途的可能性；继续保留“未派发”、总时限和进程回收断言。该次全仓运行不计通过。
- `stdio-clippy-01.log`：两个布尔表达式未满足严格 Clippy。改用相同语义的 `is_none_or`；未关闭警告或降低检查。
