# 主張↔測試映射（X-2）

> 狀態：**設計 + 已落地（20 條）**。第七輪複核的橫切建議之二：把 `guard-cli coverage`
> 那套「聲明必須對著儲存庫核實、無依據的聲稱是錯誤」的紀律，從**學術攻擊面**擴到**面向使用者的能力
> 聲明**——商店文案、平台能力矩陣、路徑模型、端點表裡那些「我們能做 X」的話。

## 為什麼要有這份文件

這個專案反覆抓到的一類缺陷，形狀都一樣：**一句話聲稱的能力，比它背後的程式碼強。** 平台矩陣曾經
說 Android 的 Critical Confirm「✅（notif）」，而那條通知權限宣告了卻從不在執行時申請；商店文案
可以寫「簽名、防竄改的稽核」，而「防竄改」到底被哪條測試證明過，沒人拴得住。`guard-cli coverage`
已經把這條紀律用在攻擊面上：每個 surface 聲稱的規則必須存在、情境必須通過，而且必須**真的命中**
那條規則，否則命令失敗。

X-2 是同一招換一個對象：**面向使用者**的聲明。區別在於對象不是論文攻擊面，而是使用者讀到的承諾；
不變的是那條原則——**一句對外的能力聲明，必須能指著一段程式碼說「這是兌現它的」，並指著一條測試
說「這證明它真的會觸發」；做不到的聲稱是錯誤，不是待辦。**

## 被機器核對的是什麼（以及**不是**什麼）

映射表在 `eval/capability-claims.yaml`，核對邏輯在 `crates/guard-eval/src/capability_claims.rs`，
入口是 `guard-cli capability-claims`（已進 `make capability-claims` 和 release-gate）。

每條聲明登記四樣東西：一句 `claim`、它印在哪裡（`source.doc` + 一段 `source.anchor` 錨文字）、
由哪段程式碼兌現（`mechanism`）、由哪條（些）測試證明（`proven_by`：測試函式名稱 + 原始檔）。

核對**兩件硬事實**，任一不成立就是錯誤：

1. **聲明真的印在那份使用者可見的文件裡。** `source.anchor` 必須作為子字串出現在 `source.doc`。
   這擋住兩個方向的漂移：映射表聲稱「我們宣傳了 X」而文件裡根本沒有 X；以及文件改了措辭、悄悄
   把某條能力刪了，而映射表還掛著它。
2. **每條證明測試真的存在。** `proven_by` 裡每條 `fn <名>(` 必須出現在它宣告的原始檔裡。刪掉 /
   改名一條證明測試而不更新映射，就變紅——和 `coverage.rs`、X-1 的入站面清冊是同一個釘子。

**不**被機器核對的是 `mechanism`（哪段程式碼兌現）。它是描述性的，和 `coverage.rs` 的 `mechanism`
一樣。把它也做成「符號必須存在於檔案裡」會給一層**假精確**：一個函式改了名稱不代表那條能力沒了，
真正釘住「能力還在」的是那條**測試**是否還在、是否還綠。所以這份映射把機器信任只押在兩處它能
可靠判真偽的地方，其餘留給人讀。

### 一條衍生紀律：錨文字要**具體到這條能力**

錨不能選泛詞（選「audit」就幾乎永遠命中，等於沒核對），要選一段**只有做出這條承諾時才會寫**的
措辭（如 `"signed, tamper-evident audit trail"`、`"label + icon dHash"`）。這樣「文件不再這麼說了」
才會真的讓它變紅。這條是 `coverage.rs` 裡「覆蓋必須是規則**被命中**、不只是**存在**」的同款要求：
讓核對貼著語意，而不是貼著字串的存在性。

## 邊界（如實）

- **這張表不能自動發現「你又對使用者承諾了一件事卻沒測」。** 那需要從文件裡做自然語言抽取，超出
  範圍。它是**人工維護**的清單；它保證的是**已登記**的聲明，其證明測試不被悄悄摘掉、其文案不被
  悄悄改沒。加一條新的對外承諾時，得**主動**把它登進 `eval/capability-claims.yaml` 並配測試——
  這條邊界是顯式的，和 X-1 入站面清冊、`coverage.rs` 語料庫同一性質。
- **`mechanism` 不被核對**（見上）。它對不上現實不會讓門禁變紅；要防它漂移，靠的是那條測試。
- **端點表另有專門的一致性測試。** `/v1/*` 路由與 `docs/local-api.md` 端點表的一致由 P2 的
  `端点表与实际路由一致` 直接比對，比錨文字更強，所以端點沒有重複登進這張表。

## 殘餘（尚未映射的使用者聲明）

誠實列出這張表**還沒**兜住、但文件裡確實對使用者說了的能力，作為後續排程：

- **平台矩陣裡尚未登記的限制標註**（例如 Windows overlay 只覆蓋自繪、Android Critical 只事後
  通知），它們的「限制」本身是承諾的一部分，值得各配一條「限制確實存在」的測試。瀏覽器執行前門、
  跨瀏覽器一致性及其邊界已登記，但真瀏覽器 E2E 仍是發布門禁。
- **隱私文案**（「預設不上傳瀏覽歷史」「發現預設留在本機」）：需要一條證明預設路徑不外傳的測試，
  目前是設定斷言而非端到端證明。
- **iOS 行**：文件已如實寫成全 ❌ / 「none」，沒有能力可兌現，所以也沒有可映射的正向聲明——這是
  一條「聲明為空」的誠實，不是缺口。
- **各平台打包/CI 聲明**（如「macOS 3 packaging tests」）：屬於建置產物層，和能力語意正交，單列。

這些不是被忽略，是被點名地留在表外，好讓「表裡 20 條都綠」不被誤讀成「所有對使用者的承諾都兜住了」。
