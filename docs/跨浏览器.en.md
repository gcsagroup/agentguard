# Cross-Browser Support: Chrome / Edge / Firefox / Safari (E4)

> In one sentence: **Edge is effectively free because it is Chromium; Firefox is a real port whose scaffold is
> implemented but not validated on a real device; Safari is a different order of work because it requires an Xcode
> wrapper and has a completely different native-messaging model, and it cannot be built or validated here.**

Three things determine the cost of porting a browser extension: the **extension API namespace**, **manifest /
packaging**, and **native-messaging host**. The sections below state exactly how far each browser has progressed and
what remains.

## Edge — directly usable (Chromium)

Edge is Chromium and loads the same MV3 extension. `chrome.*`, `declarativeNetRequest`, and `world: "MAIN"` content
scripts all work the same way. Therefore:

- **Extension package:** the same zip as Chrome (the output of `package-store.sh` without arguments).
- **Native-messaging host:** only the manifest directory differs. `install-host.sh --browser edge <extension-id>`
  installs it into Edge’s `NativeMessagingHosts` directory (on macOS, `…/Microsoft Edge/…`; on Linux,
  `~/.config/microsoft-edge/…`). The allow key remains `allowed_origins: [chrome-extension://ID/]`, which Edge also
  uses.
- Distribution goes through the Edge Add-ons store.

Only a real-device smoke test remains: load it in real Edge and perform one payment confirmation. Like Chrome, this
is “real-device E2E not validated.”

## Firefox — porting scaffold implemented, not validated on a real device

Firefox uses WebExtensions and is broadly similar to Chromium, but several differences **must** be handled or
functionality will **silently** disappear:

- **Manifest:** Firefox has a separate [`manifest.firefox.json`](../apps/extension-chromium/manifest.firefox.json).
  It adds `browser_specific_settings.gecko.id` (without it installation and native messaging cannot be matched) and
  `strict_min_version: 128` (because of world:MAIN below). Its content-script and permission sets **must match** the
  Chrome manifest. `manifests.test.mjs` pins this down: omitting one `guard-page.js` removes the fetch gate without
  producing an error.
- **Packaging:** `package-store.sh --firefox` places `manifest.firefox.json` in the package as `manifest.json`; all
  other files are identical to Chrome.
- **The `chrome.*` namespace:** Firefox provides both `chrome` (callback style) and `browser` (Promise style). The
  existing code uses callback-style `chrome.*`, which Firefox accepts, so no code was changed for this. If Promise
  style is adopted later, introduce `webextension-polyfill` then and keep one source that runs in both browsers.
- **`world: "MAIN"` (E2.1 fetch gate):** Firefox did not support `world: "MAIN"` manifest content scripts until
  **128**, so `strict_min_version: 128` is pinned. On older Firefox versions, the fetch/XHR gate layer does not load;
  the DOM submit/click gate and DNR remain. This is an **explicit degradation**, not a silent omission.
- **`declarativeNetRequest`:** Firefox supports it, but dynamic-rule quotas and details differ from Chromium. Host-
  list blocking must be calibrated against Firefox’s quota limits (not done; this is a real-device calibration item).
- **Native-messaging host:** Firefox uses a different template,
  [`com.agentguard.native.firefox.json`](../apps/extension-chromium/native-host/com.agentguard.native.firefox.json),
  with `allowed_extensions: [gecko-id]` rather than `allowed_origins`. Run
  `install-host.sh --browser firefox <gecko-id>` to install it. There is also a critical host-side difference:
  Firefox passes the **extension’s gecko id** as the caller identifier when starting the host, while Chromium passes
  `chrome-extension://ID/`. The installer therefore writes a browser-specific string to the `allowed-origin` file,
  and the origin validation in `guard-nm-host` compares the actual value passed by the browser. This behavior follows
  MDN documentation but **has not been tested on real Firefox** and must be tested before release.

**Unvalidated Firefox checklist:** real-device loading; whether the world:MAIN fetch gate actually blocks; DNR
quota; and whether the native host’s gecko-id origin behaves as documented. The scaffold—manifest, host template,
installation path, packaging, and anti-drift tests—is present, but the real-device step has not been performed.
These items are now an executable acceptance checklist in
[`acceptance-firefox.md`](./acceptance-firefox.md) (F1–F8) and are registered in release-gate as evidence requiring a
real device (`AGENTGUARD_EVIDENCE_ACCEPTANCE_FIREFOX`). It remains unvalidated until those steps are completed on
real Firefox with retained evidence.

## Safari — a different order of work that cannot be done here

A Safari Web Extension requires more than replacing a manifest:

- It must be wrapped in a macOS/iOS **application** by an **Xcode project** (with the shell generated by
  `safari-web-extension-converter`) and distributed through the App Store or as a signed application. It cannot be
  loaded as a zip like Chromium/Firefox.
- **Native messaging is completely different:** there is no stdio native-messaging host. Safari uses
  `SafariWebExtensionHandler` (a Swift class in an App Extension’s `NSExtension`), and the extension calls it with
  `browser.runtime.sendNativeMessage`. The `install-host.sh` manifest-directory + stdio-binary approach is
  **entirely inapplicable** to Safari. `guard-nm-host` would have to become, or be accompanied by, a Swift handler.
- Support for `world: "MAIN"` and DNR on Safari still requires investigation.

**Conclusion: Safari is a design item, not something that can be built or validated in this cloud environment**; it
requires macOS + Xcode + an Apple Developer account. Adding a half-finished directory that merely looks like a Safari
extension would repeat exactly what this project rejects: implementing a mechanism too weak to support its claim.
This section therefore provides only an honest description of the shape of the work, not a partial implementation.
If undertaken, it is a separate Xcode-centered workstream that naturally joins the iOS workstream (where
`ios-webshield` is currently a scaffold).

## Capability comparison (which protection layer exists in each browser)

| Protection layer | Chrome | Edge | Firefox | Safari |
|---|---|---|---|---|
| Scanning (injection/PII/trap/payment CTA) | ✅ | ✅ | ✅ (`chrome.*` accepted) | Design item |
| DOM gate: pre-execution submit/CTA-click blocking | ✅ | ✅ | ✅ | Design item |
| fetch/XHR gate (world:MAIN, E2.1) | ✅ | ✅ | 🟡 FF≥128 only; explicitly degraded otherwise | Design item |
| DNR host-list blocking | ✅ | ✅ | 🟡 Quota calibration pending | Design item |
| Host-signed audit (native messaging) | ✅ | ✅ | 🟡 gecko-id origin requires real-device validation | ❌ Requires Swift handler |

✅ = mechanism exists and is pinned by structural tests; 🟡 = mechanism exists but has an explicit limitation or
pending calibration; ❌ = not implemented. Every ✅ remains subject to the same overall limitation: **real-device
end-to-end behavior has not been validated** because this cloud environment cannot run those browser extensions in
their real environments.
