## 提交耗时诊断

随后在独立工作树只增加计时输出：主程序进入、初始化结束、批量审计事务的语句阶段与提交阶段。补丁不改变任何 SQL、事务顺序、`synchronous=FULL`、`fullfsync` 或 `checkpoint_fullfsync` 设置。这是独立诊断二进制，不能用它的结果覆盖上面的产品候选。

同一个诊断路径连续启动两次，每次新建合成工作区及审计库；预热 5 次后测量 100 次原生读取：

| 分项 | 第一次 | 第二次 |
| --- | ---: | ---: |
| 启动到进入 main | 2,806.917 ms | 3.945 ms |
| main 到初始化完成 | 40.369 ms | 30.193 ms |
| 两次提交的平均耗时 | 7.967 ms | 7.848 ms |
| 事务内语句阶段平均耗时 | 0.137 ms | 0.213 ms |
| 两次提交占所有请求耗时之和 | 91.8% | 89.0% |
| 请求 p95 | 12.010 ms | 10.036 ms |

提交阶段包含 SQLite 持久提交和当时的调度等待，不能全部称作磁盘设备耗时。主程序之前的延迟已单独测出，但本批没有进一步证明是哪个系统服务造成，不能直接归因于 Gatekeeper、签名或编译负载。此诊断意味着：继续减少少量 SQL 解析开销不是当前主要修复方向；删除执行前日志或关闭完整同步也不属于可接受的优化。
