# 郵件用戶端與網頁信箱聯合防護設計

狀態：**整體仍為設計候選；已實作預設關閉的實驗性 Chrome/Edge 網頁信箱模組，尚未實作信箱代理或接入真實信箱**。下文閘道、用戶端與批准流程仍是計畫。

## 目前可試用範圍（2026-09-07）

載入最新 Chromium 擴充功能，開啟彈出視窗 →「郵件設定」→「啟用實驗性網頁信箱檢查」。獨立開關不會停用既有付款防護；狀態只代表候選頁面，不代表實際投遞路徑已驗證。

- 候選 HTTPS 主機為 `mail.google.com`、`outlook.live.com`、`outlook.office.com`、`outlook.office365.com`，限 `/mail/` 路徑。已識別的寄送點擊、快捷鍵及表單事件核對主旨、正文與 To/Cc/Bcc，阻斷部分密碼、權杖/私鑰、通過校驗的卡號及典型提示注入；不是完整 DLP，不推測企業內外部收件人。
- 閱讀區檢查典型偽指令；已識別的連結點擊檢查協定及顯示主機錯配，不是惡意網址情報或郵件真偽認證。Unicode 只在比對視圖正規化，不改寫原文。
- **尚未實作附件內容掃描**：開啟後阻斷已識別的檔案選取、拖放、檔案貼上，以及帶有已識別附件或內嵌媒體的寄送；信箱頁面其他檔案控制項也可能被攔截。複雜地址、未知主旨/正文結構和超出文字預算時保守阻斷。
- 本機檢查；郵件專項記錄只保留風險類別、阻斷狀態、時間與網站來源，不保存正文、主旨、地址、附件名或完整連結；不連接信箱 API，不新增權限或 Native Messaging。關閉時不執行郵件專項閱讀掃描。
- 提示只有「關閉」，**沒有批准、單次放行或自動寄送**；關閉提示不會寄信，先前提交或自動同步的內容無法撤回。
- **缺口**：直接 API、草稿自動同步、未知控制項/附件路徑、未注入 frame、closed Shadow DOM、桌面用戶端和其他信箱。真實 Gmail/Outlook 頁面及 Edge 尚待驗收；目前證據限原樣擴充功能、真實 Chromium、合成 DOM 和本機接收端計數。

Node 22 執行 `make check-extension-gate`、`make e2e-extension`、`make ui-preview`；後兩項需要 Playwright/Chromium。用例 `WM-*` 的 `*-GAP` 刻意證明直接 API 可繞過，不是防護通過；下文整體 MAIL-01–10 計畫不因本模組而自動完成。

## 目標與關鍵選擇

涵蓋郵件用戶端與網頁信箱的收信、閱讀、附件處理及外寄風險。透明的意思是「一次明確授權與設定後，日常操作盡量不變」，不是零設定解密所有流量。

建議企業信箱以**伺服器端收發閘道為主，網頁及用戶端接入補充**。個人信箱沒有租用戶路由權限時，只能提供已驗證的用戶端／網站支援範圍，不能宣稱無法繞過或所有終端全面涵蓋。

| 接入位置 | 預定負責事項 | 必須明確的邊界 |
| --- | --- | --- |
| 企業郵件閘道 | 投遞／外寄前檢查，執行隔離、拒絕或等待核准 | 需要管理員路由授權；內部郵件、別名、轉寄及繞過路徑分別驗證 |
| 網頁信箱配接 | 正文提示注入、連結點擊、附件上傳及寄送前核對 | 按網站和瀏覽器版本驗證；不能僅靠 DOM 按鈕涵蓋背景工作、直接 API 或所有上傳 |
| 用戶端配接 | 可設定的 IMAP/SMTP 代理或官方寄送前擴充功能 | Outlook 其他協定及不支援擴充功能的用戶端，不是 IMAP/SMTP 自動涵蓋面 |
| 信箱 API 連線 | 帳號同步、補充掃描、隔離與狀態核對 | 收到通知後再掃描不等於投遞前攔截；寫入權限另行授權 |

Microsoft 365 連接器、Google Workspace 入站閘道與出站路由讓企業伺服器路徑具可行性；每個租用戶仍須獨立驗收。[Microsoft 連接器](https://learn.microsoft.com/en-us/exchange/mail-flow-best-practices/use-connectors-to-configure-mail-flow/use-connectors-to-configure-mail-flow)、[Google 入站閘道](https://support.google.com/a/answer/60730?hl=en-GB)、[Google 出站閘道](https://support.google.com/a/answer/178333?hl=en)

Apple MailKit 提供寄送前檢查回呼；Outlook Smart Alerts 也支援寄送事件，但用戶端、部署及離線模式皆有限制。這些是候選接入點，不是本產品已支援的聲明。[Apple MailKit](https://developer.apple.com/documentation/mailkit/mecomposesessionhandler/allowmessagesendforsession(_:completion:))、[Outlook Smart Alerts](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/onmessagesend-onappointmentsend-events)

## 資料與信任路徑

預定路徑：接入身分驗證 → 不可變寄送快照 → 共用規則判定 → 拒絕／待確認／允許此版本 → 受控投遞端 → 回執核對。企業入站郵件也在投遞前經過規則判定。

正文、HTML、附件檔名、連結及模型分析均是不可信資料。郵件內的「管理員已核准」「忽略規則」不能成為設定、授權或執行指令。模型只能提供風險線索，不能批准寄送、修改收件人或關閉檢查。

先解碼 MIME、擷取 HTML 顯示文字及 Unicode 比對視圖，再按預算分析附件；大小、壓縮展開比例、層級、耗時及重新導向次數均有上限。加密附件、解析失敗與端對端加密正文顯示「無法檢查」，依授權策略隔離或交人工處理，不得標綠通過。S/MIME 需要相應解密能力，不預設收集使用者私鑰以達成透明解密。[S/MIME 規範](https://www.rfc-editor.org/info/rfc8551/)

## 外寄核准的綁定內容

寄送快照擬包含帳號與租用戶、接入身分、寄件人、全部 To/Cc/Bcc、主旨、正文語義摘要與原始內容雜湊、每個附件的內容雜湊、策略版本、到期時間及一次性請求號。可讀摘要不能替代提交位元組核對；傳輸端添加的標頭與可編輯內容分開建模。

- 核准後再次比較寄送快照；收件人、正文、附件或策略變化即令舊核准失效。
- 位址依信箱語義比較，網域與顯示名稱分開；不得對完整位址一律轉小寫或忽略 Bcc。
- 逾時、斷線、身分變化或無法複核，不自動寄送。已提交但缺少回執時顯示「結果待核實」，先查投遞記錄，不盲目重試造成重複郵件。
- 核准、提交與最終投遞分開呈現；IMAP 同步、SMTP 接受或 API 接受不能混稱「收件人已收到」。

現有共用引擎、隱私分析、加密稽核與確認機制可評估複用；但目前 `guard-gateway` 是協作式 MCP 執行者，沒有郵件連接器、MIME 解析及投遞回執鏈路。郵件並行佇列、快照綁定與投遞冪等須新增並獨立測試。

## 帳號與隱私

採用服務商正式授權，分別解釋讀取、寄送及修改／隔離權限。憑據存入系統安全儲存，不寫記錄或前端持久化空間。撤銷或權限不足須降級並停止相關操作，不退回明文密碼或略過檢查。[Gmail OAuth](https://developers.google.com/workspace/gmail/imap/xoauth2-protocol)、[Microsoft OAuth](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)

預設只保留去識別化風險摘要、規則號、快照雜湊與回執，不保存完整郵件。隔離原件需另行啟用、加密、設定保留期限及可稽核刪除；租用戶間的權杖、佇列與儲存須隔離。附件沙箱不得使用使用者的網路身分或本機憑據。

## 設定入口與真實狀態

預定入口為「主動防護 → 郵件防護」：

1. **連線與涵蓋**：選擇企業路由或個人帳號，逐項說明權限、支援用戶端／網站及缺口；完成真實測試郵件後，對應路徑才可標記已驗證。
2. **待確認**：顯示外部收件人、原因及附件摘要。核對框預設未勾選，拒絕可直接操作；郵件變更、逾時或斷線使當前核准失效。
3. **活動記錄**：區分已檢查、已拒絕、待確認、已核准、已提交、結果待核實及未涵蓋，不以一個開關代表全面保護。

「防護設定 → 郵件」提供帳號、檢查／隔離策略、去識別化與保留期限、診斷及撤銷接入。每種接入有獨立健康狀態，網頁擴充功能停用不能虛構伺服器閘道的狀態。

本輪預覽僅使用合成郵件與本機介面狀態，不讀寫信箱、不執行 SMTP/API 請求。它只驗證互動、文案及核准失效流程，不驗證後端檢查、真實上傳阻斷或投遞。

## 實施階段與完成標準

| 階段 | 工作 | 通過標準 |
| --- | --- | --- |
| M0 | 設計與預覽 | 寬窄螢幕及鍵盤可用，未接入不顯示真實保護 |
| M1 | 本機假 SMTP 接收端、MIME 樣例、核准綁定與稽核 | 下列驗收集實測；拒絕、逾時或變更時接收數為 0 |
| M2 | 一個授權測試租用戶及一組網站／瀏覽器 | 進出站、內部及繞過路徑，回執可追溯，不盲目重試 |
| M3 | 用戶端與個人信箱 | 版本化的線上／離線、附件上傳及未涵蓋路徑矩陣 |
| M4 | 發佈 | 租用戶隔離、故障恢復、簽署、完整端對端與回復演練 |

本輪僅完成 M0 文件與預覽檢查，M1–M4 尚未完成。

## 郵件專用本機驗收集（尚未執行）

| 編號 | 代表情境 | 必須核對的結果 |
| --- | --- | --- |
| MAIL-01 | 普通文字、正常 Unicode、常規附件 | 正常投遞，不因正常語言誤攔 |
| MAIL-02 | HTML 隱藏指令、不可見編碼、偽造授權 | 只當作不可信內容，不觸發額外動作 |
| MAIL-03 | 敏感附件寄至外部 To/Cc/Bcc | 核准前接收 0 封，全部收件人可核對 |
| MAIL-04 | 改收件人、正文、替換同名附件 | 舊核准無效，只能提交已核對快照 |
| MAIL-05 | 逾時、斷線、撤銷帳號、確認程序重啟 | 未提交請求維持未寄送，恢復後重新複核 |
| MAIL-06 | 重複核准、並行同號、SMTP 斷線、API 回執遺失 | 不重複寄送，不確定結果可查核 |
| MAIL-07 | 壓縮炸彈、超大附件、S/MIME、解析失敗 | 預算有界，無法檢查不代表通過 |
| MAIL-08 | 網頁快捷鍵、先上傳附件、直調 API、停用擴充功能 | 依矩陣驗證，繞過顯示為缺口 |
| MAIL-09 | 跨租用戶相同郵件號、重放核准權杖 | 拒絕跨帳號／租用戶／會話授權 |
| MAIL-10 | 權限不足、TLS 錯誤、內部轉寄及別名 | 不降低授權與憑證檢查，逐一驗證路由 |

M1 報告須包含真實接收端數量、提交記錄、快照綁定、去識別化稽核及程序退出碼。既有通用評測、瀏覽器擴充功能測試或本輪預覽，均不能填作 MAIL 用例通過。
