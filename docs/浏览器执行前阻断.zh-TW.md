# 瀏覽器執行前阻斷（E2）

> 狀態：**已落地（in-page 向量）**。把 Chromium 擴充功能從「事後通知」升級為「執行前攔截」——但只在
> 它**夠得著**的地方，邊界如實劃清。

## 為什麼「事後通知」改不成「執行前阻斷」——除非換個位置

`background.js` 收到宿主判決時，那個 DOM 事件**已經發生**了：原生訊息是非同步的，宿主在事件之後
才看到它，沒有東西可以 hold。這不是實作偷懶，是位置決定的——觀察者攔不住它觀察到的東西。

E2 的做法是**換位置**：攔截邏輯搬進**內容腳本**，它跑在頁面裡、是同步的。一個捕獲階段的
`submit` / `click` 監聽器能在動作**真正發生之前** `preventDefault()` 把它按住，彈一個本機確認，
只有使用者點「允許這一次」才程式化重播放行。這條路徑**不經過**那趟非同步宿主往返，所以它能真的 hold。

## 攔什麼

內容腳本（`content.js`）在捕獲階段同步判兩類頁面自身的動作，判決邏輯在純模組 `guard-gate.js`：

| 觸發 | 判據 | 處置 |
|---|---|---|
| 表單 `submit` | 表單裡有「陷阱控制項 + 非必要 PII」已填 | preventDefault → 本機確認 → 允許後以 `requestSubmit(原 submitter)` 重播一次 |
| `click` / `submit` | 目標是付款/轉帳 CTA（文案匹配） | 同上 |
| **頁面直發的 `fetch` / `XHR`** | URL 路徑是付款形狀（pay/checkout/charge/transfer…）且非唯讀方法 | 頁面世界（`guard-page.js`）包裹後 await 確認才發，拒絕則 reject/abort（E2.1） |
| 網路請求 / 導航 | 主機被**引擎**判為惡意域（`INTEL-DOMAIN`） | 宿主把該主機放進回應的 `block_hosts`，`background.js` 安裝 declarativeNetRequest 規則，請求發出前 block（E5） |

前兩類是頁面 DOM 動作，內容腳本同步攔；第三類是網路層，交給 DNR（MV3 裡請求發出前攔的正確 API）。
每攔一次都 `sendMessage` 回 background，記進最近列表並轉宿主進簽名稽核——一次執行前阻斷和一次
判決一樣，是該留痕的事件。

## 覆蓋什麼、**不**覆蓋什麼（如實）

覆蓋：頁面**自己的** DOM 提交/點擊（付款 CTA、陷阱下的 PII 提交）；以及命中主機名單的導航/請求。

**~~一段直接 fetch()/XHR 的腳本~~ E2.1 已補上（在能搶到的前提下）。** 頁面世界的 `guard-page.js`
包裹 `window.fetch` 和 `XMLHttpRequest`，對付款形狀的出站請求在發出前 await 確認。仍**不**覆蓋：

- 一段在我們之前就拿走了原始 `fetch` 參照的腳本（早於 `document_start`、或從乾淨 iframe 借來的
  `fetch`）——MAIN world 裡頁面和我們平權，誰都能改 `window.fetch`，所以這是**盡力而為**不是鐵壁。
- 判據只看 URL 路徑的付款形狀、不看 body（body 因站而異、誤判高，誤攔比漏攔更容易讓人關掉門），
  所以它攔「長得像付款的直發請求」，不是「任何出站」。
- 跨源 iframe 裡的動作（內容腳本按 manifest 只在主框架跑）。
- **任何原生 app 的動作**——瀏覽器擴充功能夠不到。

一句話：這道門擋的是「在這個頁面上把這一步走完」，不是「這台機器上任何連網」。要攔「任何出站到
某主機」，那是 DNR（按主機）和 Linux jail 的 `scope.net`（E1，核心按連接埠）那兩層，不是這裡。

### E5：引擎判決 → 瀏覽器網路層硬攔（把兩層接上）

DNR 那一行以前是「如果宿主判定要攔某主機」——但**沒有東西**在產生這個名單，`block_hosts` 是條空
接線。E5 把它接上了：引擎本來就會判「這個 url 的主機是惡意域」（`is_malicious_domain` → 一條
`INTEL-DOMAIN` 的 Block 判決），現在宿主（`guard-nm-host`）把那個主機名從判決裡取出來，放進回應的
`block_hosts`，`background.js` 據此安裝一條 DNR 規則。於是鏈條閉合：**引擎判惡意 → 瀏覽器在該主機的
下一個請求發出前就硬攔**，而不再只是彈一個事後通知。

取主機名靠的是一個**共用契約**（`guard_schema::INTEL_DOMAIN_RULE_ID` + `MALICIOUS_DOMAIN_MSG_PREFIX`）：
生產端（guard-core 發判決）和消費端（nm-host 解析）引用同一對常數，措辭一改兩邊一起改、編譯期就
發現——不會一端悄悄改了另一端解析出空。只認結構化的 `INTEL-DOMAIN` rule_id、只取前綴後第一個詞
（主機名不含空白，門追加的「 (user denied…)」後綴被自然切掉）。這條擷取邏輯是純函式，有單元測試含反面
案例（別的 rule_id 不取、無前綴不取、帶門後綴也只取主機）。

**E7 擴展：不只攔「已知惡意」，還攔「這個任務本不該去的地方」。** 引擎除了判惡意域，還會判
「目的地越出了任務聲明的 `scope.hosts` 天花板」（`SCOPE-HOST` Block）。現在這類主機也一併進
`block_hosts`——用同一套共用前綴契約（`SCOPE_HOST_RULE_ID` + `SCOPE_HOST_MSG_PREFIX`，主機取兩個
`'` 之間那段，哨兵 `<unnameable>` 不進名單）。關鍵的安全性質**繼承自引擎**：`check_scope_host`
**只在任務聲明了 `scope.hosts` 時**才發這條（沒聲明 → 不發 → 不攔），所以絕不會因為「沒配 scope」
把使用者正常瀏覽全攔掉；聲明了 `hosts: []`（明確「不許出網」）才會攔一切出站。

### E8：名單累積語意（惡意域累積保留，越界隨工作階段過期）

E5 的第一版有個弱點：`installBlockedHosts` 每批判決**整體替換**動態規則——於是一條惡意域會在下一批
benign 判決（`block_hosts` 為空）到來時被清掉，硬攔只活到下一次乾淨判決。E8 按主機的**類別**給不同
壽命：

- **`malicious`（已知惡意域）：累積保留**，並落 `chrome.storage` 跨 service-worker 重新啟動存活（重新啟動時重新
  安裝）。有上限（`MAX_PERSISTENT`，尊重 DNR 動態規則配額），超了丟最舊的。
- **`out_of_scope`（越出任務範圍）：隨工作階段過期**（預設 30 分鐘沒被再次判越界就撤）。它是**任務相對**的，
  不該永久攔掉使用者對該主機的正常存取——一次任務沒聲明 booking.com，不意味著以後永遠不讓你上 booking.com。

合併/過期是純函式 `guard_gate.mergeBlocklist`（6 條 node 單元測試：惡意域累積不被 benign 清掉、越界到期撤銷、
再判重新整理過期、既惡意又越界歸持久、持久名單上限）。`nm-host` 現在給每個 `block_hosts` 項帶 `kind`
（`malicious` / `out_of_scope`），`background.js` 據此分流。

**如實**：
- DNR fail-open（安裝不上不假裝攔住，免得把瀏覽器弄到斷網），真 Chrome/Firefox E2E 未驗證。
- 工作階段過期是**時間**驅動（無強「工作階段結束」訊號），所以越界項最長活一個 TTL，不是精確到工作階段邊界。
- 惡意域清單來自內建情報基線（發佈前 `intel-keygen` 換金鑰那條仍在 `docs/发布阻塞项.md` 盯著）。
- **觸發面的誠實**：惡意域檢查對任何帶 `url` 的事件成立（含瀏覽器的 `ui_text`），所以惡意域→DNR
  在瀏覽器路徑上**當下就有效**；而 `SCOPE-HOST` 只對**網路流 / 資料流出**事件成立（引擎刻意不把
  「讀一個頁面」當成「發給它」，見 `check_scope_host` 註解），瀏覽器擴充功能現在發的是 `ui_text`、不是網路流
  事件，所以越界→DNR 的完整閉環要等擴充功能報網路流的那天。**這裡刻意不讓擴充功能把所有出站 URL 都發給
  宿主**——那違背「發現預設留在本機」的隱私底線。所以 E7 現在補全的是引擎/宿主這條**通用**橋（任何
  越界判決都會餵 DNR），Android/桌面的網路流事件已經能驅動它；純瀏覽器 `ui_text` 路徑的那一段是
  顯式殘餘。

### E9：把任務允許表下發給瀏覽器，本機判越界（不回傳 URL）

E7 補全了引擎/宿主這條通用橋，但留了個殘餘：純瀏覽器的 `ui_text` 事件不觸發 `SCOPE-HOST`，而**刻意
不讓擴充功能把所有出站 URL 都發給宿主**（違背「發現預設留在本機」）。E9 換個方向閉合它：**把允許表下發到
瀏覽器**，在**本機**判越界。

- `nm-host` 在回應裡帶 `scope_hosts`——目前工作階段 `scope.hosts` 授權的**快照**（引擎新增 `granted_hosts()`
  暴露它）。這是**策略**、不是瀏覽歷史：下發一張「允許去哪」的表，不回傳任何「去過哪」的 URL。
- `background.js` 把它存進 `storage`，`content.js` 推給頁面世界的 `guard-page.js`，後者在 fetch/XHR 門裡
  對每個出站目的地在本機呼叫 `scopeGateHost(host, allowlist)`：不在允許表裡就和付款形狀一樣彈確認。

安全攸關的一點：主機匹配 `hostInScope` 是 Rust `host_in_scope` 的 JS 鏡像，**必須拒同樣的後綴偽造**
（`stripe.com.evil.example` 不是 `stripe.com` 的子網域）。兩端語意漂移會造成 JS 放行一個 Rust 會攔的目的地。
`hostInScope_对齐Rust拒绝后缀伪造` 那條 node 測試把這些偽造案例釘死。

繼承的性質同 E7：`scope_hosts` 缺失（沒聲明）→ 本機不攔；`[]`（明確不許出網）→ 全攔。**如實**：這是
MAIN world 的客戶端檢查，和 fetch 門一樣是盡力而為（頁面能改 `window.fetch`）；它是對核心層（jail
`scope.net`，E1）和引擎判決（E5/E7）的**補充**，不是替代。允許表活性取決於該工作階段有沒有聲明 `scope.hosts`。

### E10：popup 管理面（可見 + 可解除）

累積名單（E8）現在在擴充功能 popup 裡可見：列出目前被攔的網路目的地，區分「惡意域」（累積）與
「越出任務範圍」（工作階段），每條一個「解除」按鈕——`background.js` 的 `get_blocklist` / `unblock_host` 訊息
支撐讀和刪，刪後立即重新安裝 DNR。**E12 溯源**：每條還顯示「觸發規則」（`INTEL-DOMAIN` / `SCOPE-HOST`）——
`nm-host` 的 `block_hosts` 每項帶 `rule_id`，background 存進 provenance 映射隨名單持久化，popup 第二行
顯示它，讓「這個主機**為什麼**被攔」一眼可見。這是可用性，不是安全能力，所以**不進** X-2 主張↔測試映射（那張表只
收有證明測試兜底的能力聲明）；它的正確性靠 `mergeBlocklist`（E8）那組已測的純邏輯，UI 本身按儲存庫
不變量只做無 sink 的 DOM 構造（`createElement` + `textContent` + `addEventListener`，不用 innerHTML）。

### E2.1 的 fail 方向

- 命中付款形狀 → **攔住等確認**：`fetch` 返回一個 await 決定的 Promise，拒絕則 reject；`XHR` 在
  確認前不真正 `send`，拒絕則 `abort`。在頁面未干預訊息通道的前提下，請求在「允許這一次」之前不會送出。
- 內容腳本 15s 內沒回應（極端情況）→ **fail-open 放行**，已聲明：這一層是加的一道，不該因為它
  自己卡住就把使用者的正常請求全掐死。真正的防線是多層疊加，不是這一層單點。
- **MAIN world 通道不是安全邊界。** 請求門與隔離世界透過頁面可觀察的 `window.postMessage` 交換
  `REQ`／`DECISION`／`SCOPE`；惡意頁面可偽造允許回應或 scope 訊息，也能看見下發的主機允許表。因此
  E2.1／E9 只是協作頁面上的盡力而為聯鎖，不能抵抗主動對抗頁面；真正的網路強制邊界只有擴充功能控制的 DNR。

## fail 方向：兩道門方向**不同**，都是有意的

- **內容腳本同步門：fail-closed 傾向。** 判決邏輯沒載入（`self.AgentGuardGate` 缺失）時，`gateEvent`
  直接返回、不改變頁面行為——它不會在「不確定」時假裝攔住。但更要緊的是：它攔下時是**真的**攔下
  （preventDefault 已經執行），不依賴任何非同步回應。
- **DNR 網路門：fail-open，且已聲明。** DNR 安裝不上時記一條、不假裝攔住。**故意**不做成 fail-closed：
  一個連不上 DNR 的擴充功能不該把使用者整個瀏覽器都弄到上不了網。它是內容腳本同步門的**加**一層，不是
  唯一防線。

把這條寫出來，是因為「某處 fail-open」如果不聲明，就和「以為處處 fail-closed」一樣危險。

## 驗證到哪一步（誠實）

- **判決邏輯**（`guard-gate.js`：哪類 finding 該攔、DNR 規則怎麼構造）是純函式，`scripts/gate.test.mjs`
  在 node 裡有 20 條單元測試，含反面案例（普通 finding 不攔，避免門變成雜訊）和 DNR 規則去重/排序/穩定 id。
  進 `make check-extension-gate` 與 release-gate。
- **DOM 接線**（`content.js` 的捕獲監聽、重播）除語法檢查外，還有 `content-event.test.mjs` 的 2 條
  最小事件鏈測試，涵蓋 click→submit 只確認／送出一次，以及批准權杖不外洩。
- **真 Chrome 端到端未驗證**：一次真實的付款提交在真瀏覽器裡是否被這道門按住、「允許這一次」重播是否
  精確等價，沒在真機上跑過。這和 jail 的 syscall 路徑、macOS 的 AX 推送是同一種誠實：安全邏輯用
  可測的純函式釘住，平台接線那層如實標為未在真實環境驗證。
