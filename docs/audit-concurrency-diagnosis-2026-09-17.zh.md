# Windows 并发审计失败：补齐可诊断证据

日期：2026-09-17。源码基线 `c6e59ba129caebbb422c3e938e7bd8b1a2ae2b1b`。本轮只修改原有审计并发测试的失败信息，产品事务、等待期限、持久性设置和全部原断言保持。固定 macOS App 为 Ver 2.1（024），未构建或改名。

## 已确认与仍未知

此前 `776c8c1` 的 [CI 35132513654](https://github.com/gcsagroup/agentguard/actions/runs/35132513654) 在 Windows 审计并发测试中失败：两名写者各追加 25 条，发生 1 次追加错误，原“50 条全部保留”要求未通过。旧测试只累计 `is_err()`，具体错误被丢弃；因此不能根据这份日志断言是 SQLite 锁超时、磁盘故障或提交后丢失，也不能以其他作业成功关闭问题。该 CI 最终 11 个作业成功、2 个失败，另一失败是 macOS 合成网关启动等待。

本轮给原测试增加每名写者的错误链、SQLite 主／扩展错误码、失败记录位置、单次耗时、最大追加耗时，以及实际日志模式和等待毫秒数。失败断言同时报告最终记录数、链是否完整和重复序号数。输出仅来自合成夹具，不包含用户审计内容。

仍要求追加错误为 0、记录总数为 50、重复序号为 0、链完整。没有增加自动重试、扩大 10 秒等待、减少并发、删除失败用例或改变 SQLite／SQLCipher 配置。

## 验证诊断本身

在独立、未提交的工作副本中，针对 `id-0` 加入 SQLite 拒绝触发器；主工作区没有该触发器。两名写者仍各尝试 25 条。该副本的原测试退出 **101**，准确输出：

- 写者 0 的第 0 条失败，错误为合成拒绝；SQLite 主码 `ConstraintViolation`、扩展码 **1811**。
- 两名写者实际均使用 `wal` 和 **10000 ms** 等待设置。
- 最终 **49 条、链完整、重复序号 0**，原“错误为 0”断言仍失败。

这是验证诊断有效性的受控故障，不是 Windows CI 根因复现，也不是功能测试通过。注入代码只在 `.artifacts/audit-concurrency-diagnosis-2026-09-17/fault-worktree/`，源文件及补丁保留，不进入正式提交。

正式主工作区最终代码在本机运行审计库测试：**111 通过、0 失败、2 原有忽略**。macOS 特有测试使数量与 Windows 不同，不能把该结果写成 Windows 验收。Clippy 全目标 `-D warnings`、格式与仓库 23 项不变量通过。固定 App 的 91 个文件及模式与 024 清单相同。

原始失败日志继续保留在 [iOS 焦点修正证据](evidence/ios-dialog-accessibility-2026-09-17.json) 指向的目录；本轮新增日志、故障副本及源文件摘要见[本轮证据索引](evidence/audit-concurrency-diagnosis-2026-09-17.json)。Windows 的具体失败原因需由新诊断或同条件复现确定，macOS 启动等待仍未解决；全部原发布门槛、AGD-027、F13 暂缓及发布 No-Go 保持。
