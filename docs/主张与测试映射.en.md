# Claim-to-Test Mapping (X-2)

> Status: **Designed + implemented (20 claims)**. The second cross-cutting recommendation from the seventh
> review extends the discipline behind `guard-cli coverage`—“claims must be verified against the repository, and
> unsupported claims are errors”—from **academic attack surfaces** to **user-facing capability claims** in store
> copy, the platform capability matrix, path models, and endpoint tables.

## Why this document exists

One recurring defect in this project always has the same shape: **a one-sentence capability claim is stronger than
the code behind it.** The platform matrix once said Android Critical Confirm was “✅ (notif),” while the declared
notification permission was never requested at runtime. Store copy can say “signed, tamper-evident audit trail,”
but without a mapping no one can pin down which test proves “tamper-evident.” `guard-cli coverage` already applies
this discipline to attack surfaces: every claimed rule must exist, its scenario must pass, and the scenario must
**actually hit** that rule, or the command fails.

X-2 applies the same technique to a different object: **user-facing** claims. The object is now a promise read by a
user rather than a paper’s attack surface. The principle is unchanged: **every external capability claim must point
to code and say “this implements it,” and point to a test and say “this proves it really triggers.” A claim that
cannot do so is an error, not a to-do item.**

## What the machine checks (and what it **does not**)

The mapping table is in `eval/capability-claims.yaml`, the checking logic is in
`crates/guard-eval/src/capability_claims.rs`, and the entry point is `guard-cli capability-claims` (included in
`make capability-claims` and release-gate).

Each claim records four things: a `claim`; where it is printed (`source.doc` plus a `source.anchor` text fragment);
the code that implements it (`mechanism`); and the test or tests that prove it (`proven_by`: test function name plus
source file).

The checker verifies **two hard facts**. Either one being false is an error:

1. **The claim is actually printed in the user-visible document.** `source.anchor` must occur as a substring of
   `source.doc`. This prevents drift in both directions: the mapping says “we advertise X” when the document does
   not, or the document changes its wording and quietly removes a capability while the mapping still lists it.
2. **Every proof test actually exists.** Every `fn <name>(` in `proven_by` must occur in the declared source file.
   Deleting or renaming a proof test without updating the mapping turns the check red—the same kind of pin used by
   `coverage.rs` and X-1’s inbound-face inventory.

`mechanism`—which code implements the capability—is **not** machine-checked. It is descriptive, like `mechanism`
in `coverage.rs`. Requiring its symbol to exist in a file would create **false precision**: renaming a function does
not mean the capability disappeared. What actually pins down that the capability remains is whether its **test**
still exists and passes. The mapping therefore places machine trust only in the two facts it can reliably evaluate
and leaves the rest for human readers.

### A derived rule: anchor text must be **specific to the capability**

An anchor cannot be a generic term (choosing “audit” would almost always match and would check nothing). It must be
wording that would be written **only when making that specific promise**, such as
`"signed, tamper-evident audit trail"` or `"label + icon dHash"`. Then “the document no longer says this” really
turns the check red. This mirrors the `coverage.rs` requirement that coverage means a rule was **hit**, not merely
that it **exists**: the check follows semantics rather than mere string presence.

Selection criterion: prioritize capabilities that can be implemented directly by **one claim** and already have
**strong proof tests**. These 20 are still not every user-facing claim; they are the set that can be honestly pinned
down today.

## Boundaries (stated plainly)

- **This table cannot automatically discover that you made another untested promise to users.** That would require
  natural-language extraction from documents and is out of scope. This is a **manually maintained** inventory. It
  guarantees that proof tests for **registered** claims are not silently removed and that their copy does not
  silently disappear. When adding a new external promise, it must be **actively** registered in
  `eval/capability-claims.yaml` with a test. This boundary is explicit and has the same nature as X-1’s inbound-face
  inventory and the `coverage.rs` corpus.
- **`mechanism` is not checked** (see above). If it drifts from reality, the gate will not turn red; preventing that
  drift relies on the proof test.
- **The endpoint table has a separate consistency test.** P2’s `端点表与实际路由一致` directly compares `/v1/*`
  routes with the endpoint table in `docs/local-api.md`, which is stronger than anchor text, so endpoints are not
  duplicated in this mapping.

## Residual user-facing claims not yet mapped

The capabilities that this table **does not yet** cover, but that the documentation really does state to users, are
listed explicitly for later scheduling:

- **Platform-matrix limitations that are not yet registered** (for example, Windows overlay covers only self-drawn
  overlays and Android Critical is post-event notification only). Each limitation is part of the promise and deserves
  a test proving that it really exists. Browser pre-execution gates, cross-browser consistency, and their boundaries
  are registered now, while real-browser E2E remains a release gate.
- **Privacy copy** (“browsing history is not uploaded by default”; “findings remain local by default”) needs a test
  proving the default path does not send data externally. It currently has configuration assertions, not end-to-end
  proof.
- **The iOS row** is truthfully all ❌ / “none.” There is no positive capability to implement and therefore no
  positive claim to map. This is an honest empty claim, not a gap.
- **Per-platform packaging/CI claims** (such as “macOS 3 packaging tests”) belong to the build-artifact layer and are
  orthogonal to capability semantics, so they are listed separately.

These items are not ignored; they are explicitly left outside the table so “all 20 mapped claims are green” cannot
be misread as “all promises made to users are covered.”

## Acceptance criteria (implemented form of this design)

- `guard-cli capability-claims` exists, checks `eval/capability-claims.yaml`, and exits nonzero for unsupported or
  stale claims; it is included in `make capability-claims` and release-gate. ✅
- An integration test (`crates/guard-eval/tests/capability_claims_repo.rs`) runs the same check against the **real
  repository**, including an anti-vacuity floor of at least 20 claims. ✅
- Mutation validation: renaming any registered proof test makes the integration test fail and identifies the exact
  claim; removing a capability’s anchor wording from a user document does the same. Both were tested (see the commit
  description). ✅
- This document distinguishes machine-checked facts from descriptive fields and explicitly lists residual items. ✅
