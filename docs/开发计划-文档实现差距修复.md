## 0. 总则

### 0.1 修复纪律(每条工单都必须满足)

沿用本仓已确立的规矩,不降级:

1. **红-绿回归测试**:每条修复配一个"没有它就变红"的测试;先让测试在未修状态下红,再修到绿。
2. **变异验证**:能做的都做——把修复还原(或注入等价 bug),确认对应测试立刻变红;记录在工单里。
   等价变异要降成真变异(像本轮 Landlock 的 `essential_write` 那样)。
3. **诚实标注**:在本容器里跑不到的路径(见 §5),只测纯逻辑,并在代码/文档里明说"落地路径未在此
   环境验证",不声称验过。
4. **文档同步**:改了行为就同步改对应文档;不制造新的文档漂移。

### 0.2 全局门禁(每个阶段收尾必须全绿)

- `cargo test --workspace`(当前基线 819 通过 / 0 失败 / 2 忽略,加 Kotlin 31)
- `cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`
- `bash scripts/release-gate.sh`(11 道自动门禁;6 项凭据/真机项保持"未验证"如实列出)
- `make check-msrv`(MSRV 1.87)
- Android:`:app:testDebugUnitTest` + `:app:assembleDebug`(设 `ANDROID_HOME=/opt/android-sdk`)
- 每阶段结束**回归**:新加测试不减少、不放宽已有断言;三处 KNOWN_MISS/ContractGate 计数不被悄悄改动。

### 0.3 分支与提交策略

- 每个阶段(P0/P1/P2/P3)一条工作分支,阶段内每条工单一个提交,提交信息说明"问题→修复→测试→变异"。
- 提交前 `git ls-files` 卫生检查:不入库 secrets、tarball、target、`local.properties`。
- **不**在 `master` 上直接堆修复;合并前跑完 §0.2 全套。
  (说明:本仓历史是 master 线性提交,若你希望继续这种方式,我按你的习惯来;默认按分支。)

### 0.4 本计划不做的事(non-goals)

- 不碰第一类"环境做不到"的项(Apple/Windows 证书、真机验收)——那不是代码问题。
- 不新增功能;只修"文档说了代码没做到"和"未公开缺陷"。
- 不重构无关代码;每条改动尽量小、可回滚、可单独 review。

### P0-A 情报签名 `sha256:` 降级绕过 —— 杀掉认证降级

- **问题**:发现 1。`ThreatBundle::verify` 的 `sha256:` 分支只比自算摘要、不看 pubkey(`guard-intel/src/lib.rs:103-110`);`load_release` 有同样的 sha256 分支(`:190-193`);`load_or_default` 的 ed25519 分支是空操作(`:156`);`api-serve` 走 `load_or_default` 完全不验(`guard-localapi/src/lib.rs:208`)。
- **修复**:
  1. `verify`:`sha256:` 分支仅作为**完整性**校验保留,但**任何需要认证的调用点都不接受它**。引入一个显式参数或双方法拆分:`verify_authentic(pubkey)`(拒绝 sha256)与 `verify_integrity()`(允许 sha256,仅自校验)。
  2. `load_release`:删掉 sha256 分支(或仅在 `allow_legacy: bool` 为真时走),有 pubkey 时**必须** ed25519。
  3. `load_or_default`:ed25519 空操作改为——软加载路径若遇 ed25519 但无 pubkey,**明确降级为空 default 并打警告**(不静默接受未验证内容),或直接拒绝(取决于软加载语义,见 D1)。
  4. `api-serve`:加 `--intel-pubkey`,有则走 `load_release`;无则用空 default(不加载未验证情报)并在启动日志警告。
- **回归测试**:
  - `sha256冒充签名在release路径被拒`:构造 ed25519 bundle,把 `signature` 改成 `sha256:<自算>`,`load_release(_, pubkey)` 必须 `Err`。
  - `load_or_default遇ed25519无pubkey不静默接受`:断言返回空 default(或 Err),且 `is_malicious_domain` 不含 bundle 里的项。
  - `api-serve无pubkey时不加载情报`:构造带恶意域名的 bundle,不传 pubkey,断言该域名**不**被判恶意。
- **变异验证**:还原"拒绝 sha256"的判断 → 第 1 条测试变绿(即漏过)→ 证明测试有效。
- **边界/异常**:合法 sha256 仅在显式 `--allow-legacy` 开发标志下允许(D1);bundle 文件缺失→空 default(安全);pubkey 文件损坏→Err;http 明文拉取与工单 P1-8/情报 MITM 相关(update.rs:89 也要拒明文或警告)。
- **QA**:`make intel-*` 相关目标 smoke;`intel-update`/`api-serve` 手动启动确认警告文案;确认现有 `release-security.md` 的"fail-closed"描述现在名副其实。
- **风险**:破坏依赖 sha256 bundle 的现有开发流程 → 用 `--allow-legacy` 过渡,并在 release-gate 里对**发布构建**禁用该标志。
- **工时**:1.5–2 人日。

### P0-B 审计 `check_inclusion` 接线 —— "增长-重写"篡改真正被抓

- **问题**:发现 2。`check_inclusion`/`chain_contains_hash` 仅被 `#[cfg(test)]` 调用;`audit-verify` 只用 `check_against`(`guard-cli/src/main.rs:2048`)。
- **修复**:`audit-verify` 见证分支里,当见证带非空 `last_record_hash` 时调 `prev.check_inclusion(|h| store.chain_contains_hash(h))`,出错置 `failed=true` 并打印 `BROKEN — <原因>`。
- **回归测试**:
  - `make audit-signing-demo` 加**用例 F**:建链→见证→删尾 K 条→补 K+1 条伪造行(seq/count 都增大)→`audit-verify` 必须 `BROKEN`(退出非 0)。
  - 单测 `见证包含性缺失时验证失败`:构造上述场景,断言 verify 路径(不是 test-only helper)返回失败。
- **变异验证**:注释掉 `audit-verify` 里新加的 `check_inclusion` 调用 → 用例 F 变绿(漏检)→ 证明它是真门。
- **边界/异常**:见证首次创建/缺失(不该误报);`last_record_hash` 为空(跳过包含性检查);签名日志 vs 仅防篡改日志(两者都要覆盖);`--pubkey` 省略走内嵌 key 时,record 签名对 pre-head 重写仍会失败(交叉确认这条路的行为)。
- **QA**:对正常库 `audit-verify` 仍打印 OK;**性能边界**——`chain_contains_hash` 现在是 `SELECT COUNT(*) ... WHERE record_hash=? OR prev_hash=?`,**没有索引**(store.rs 只有 ts/session 索引);单次 verify 一次调用尚可,但建议顺带加 `CREATE INDEX idx_audit_record_hash ON audit_events(record_hash)`,并在大库(如 10 万行)基准里确认 verify 时延可接受。
- **风险**:低。加索引会略增写入成本,可接受。
- **工时**:1 人日(含 demo 用例与索引)。

### P1-7 viewtree 按绝对计数上报 + 去掉 24 行一刀切

### P1-8 策略同步签名 + 拒明文

### P1-9 mount-ns `/dev` 只读 + 拒 uid 0(**决策点 D5:有功能风险**)

- **问题**:发现 12。`/proc* /sys* /dev*` 被排除出只读 remount(`mountns.rs:271`);root 运行时 `/dev` 可写,`dd of=/dev/sdX` 绕过只读。
- **修复(D5 择一或并用)**:(a) **拒绝以 uid 0 运行 jail**(最简单、最稳);(b) 把只读 remount 扩到 `/dev`(需谨慎:不能破坏 `/dev/null`、`/dev/urandom` 等设备的正常读写——只读**挂载**阻止的是文件系统写/建节点,设备驱动的读写通常不受影响,但需实测确认程序不被破坏)。
- **回归测试**:mount-ns 的探测在本容器里做的是真 `unshare`(前几轮已验部分可跑),故这条**可能可在容器/CI 里验**:`root运行被拒`(方案 a)可纯逻辑测;`dev下不可新建节点`(方案 b)需能跑 mount-ns 的环境。
- **变异验证**:方案 a——还原"拒 uid0"判断 → 测试变红。
- **边界/异常**:方案 b 的功能回归风险高——需在能跑 mount-ns 的 CI 上跑一组"jail 内程序正常读 /dev/urandom、写 /dev/null"的冒烟;若破坏则退回方案 a。
- **风险**:方案 b 中—高(可能破坏被约束程序);方案 a 低。**建议默认方案 a,方案 b 作为可选加固另立工单。**
- **工时**:方案 a 0.5 人日;方案 b 2 人日 + CI 验证。

### P1-10 `FS-SENSITIVE` 不可被用户确认批准

- **问题**:发现 13。`FS-SENSITIVE` 是 `Block + require_confirm:true`(`lib.rs:3152-3159`),`process_gated` 批准后降为 Allow;"删 `/`"可被点确认放行。
- **修复**:`FS-SENSITIVE`(及酌情 `FS-OUTSIDE`)设 `require_confirm:false`,变无条件 Block。
- **回归测试**:`删敏感目录不可被确认放行`:构造 `FS-SENSITIVE` 判决走 `process_gated` + 用户批准,断言仍为 Block/Refuse。
- **变异验证**:改回 `require_confirm:true` → 测试变红。
- **边界/异常**:确认这不影响合法的 `require_confirm` 家族(付款/转账仍可确认);与 `路径模型.md:44-51` 措辞一致。
- **风险**:低。
- **工时**:0.5 人日。

## 5. 环境边界:哪些在本容器里验不了,怎么处理
