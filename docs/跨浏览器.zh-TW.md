# 跨瀏覽器：Chrome / Edge / Firefox / Safari（E4）

> 一句話結論：**Edge 基本是免費的（同 Chromium），Firefox 是一次真實的移植（已做骨架，真機未驗證），
> Safari 是另一個量級（要 Xcode 包殼、原生訊息模型完全不同，本環境無法建置也無法驗證）。**

瀏覽器擴充功能的三樣東西決定了移植成本：**擴充功能 API 命名空間**、**manifest / 打包**、**原生訊息 host**。
下面逐個瀏覽器說清各自到哪一步、剩下什麼。

## Edge —— 直接可用（Chromium）

Edge 就是 Chromium，載入的是同一套 MV3 擴充功能：`chrome.*`、`declarativeNetRequest`、
`world: "MAIN"` 內容腳本全都一樣。所以：

- **擴充功能套件**：和 Chrome 同一個 zip（`package-store.sh` 不加參數那份）。
- **原生訊息 host**：只有 manifest 目錄不同——`install-host.sh --browser edge <extension-id>` 會安裝到
  Edge 的 `NativeMessagingHosts` 目錄（macOS `…/Microsoft Edge/…`、Linux `~/.config/microsoft-edge/…`）。
  允許鍵仍是 `allowed_origins: [chrome-extension://ID/]`（Edge 也用這個形式）。
- 發佈走 Edge Add-ons 商店。

剩下的只有真機冒煙（在真 Edge 裡載入、點一次付款確認）——和 Chrome 一樣屬於「真機 E2E 未驗證」。

## Firefox —— 已做移植骨架，真機未驗證

Firefox 是 WebExtensions，和 Chromium 大同小異，但有幾處**必須**處理，否則會**悄悄**少東西：

- **manifest**：單獨一份 [`manifest.firefox.json`](../apps/extension-chromium/manifest.firefox.json)，
  多了 `browser_specific_settings.gecko.id`（沒有它裝不上、原生訊息也對不上）和
  `strict_min_version: 128`（下面 world:MAIN 的原因）。內容腳本集、權限集和 Chrome 那份**必須一致**——
  由 `manifests.test.mjs` 釘住（漏一個 `guard-page.js`，fetch 門就沒了，而沒有東西會報錯）。
- **打包**：`package-store.sh --firefox` 把 `manifest.firefox.json` 作為套件裡的 `manifest.json`，其餘檔案
  和 Chrome 完全一樣。
- **`chrome.*` 命名空間**：Firefox 同時提供 `chrome`（回呼風格）和 `browser`（Promise 風格）。現有程式碼
  用的是 `chrome.*` 回呼風格，Firefox 認。所以**沒有**為此改程式碼——如果將來要用 Promise 風格，再引入
  `webextension-polyfill`，那時程式碼單源、兩邊都跑。
- **`world: "MAIN"`（E2.1 的 fetch 門）**：Firefox 到 **128** 才支援 manifest 裡的 `world: "MAIN"` 內容
  腳本，所以釘了 `strict_min_version: 128`。更舊的 Firefox 上，fetch/XHR 門這一層不會載入——DOM 門
  （submit/click）和 DNR 仍在。這是一條**如實的降級**，不是靜默缺失。
- **`declarativeNetRequest`**：Firefox 支援，但動態規則的配額和細節與 Chromium 有出入；名單主機攔截
  在 Firefox 上要按其配額上限校準（未做，真機校準項）。
- **原生訊息 host**：範本不同——Firefox 用
  [`com.agentguard.native.firefox.json`](../apps/extension-chromium/native-host/com.agentguard.native.firefox.json)
  的 `allowed_extensions: [gecko-id]`（不是 `allowed_origins`）。`install-host.sh --browser firefox <gecko-id>`
  安裝它。還有一處**宿主側**的關鍵差異：Firefox 啟動 host 時傳的呼叫方標識是**擴充功能的 gecko id**，而
  Chromium 傳的是 `chrome-extension://ID/`。所以安裝腳本寫進 `allowed-origin` 檔案的字串按瀏覽器不同，
  宿主（`guard-nm-host` 的 origin 校驗）比對的就是瀏覽器實際傳進來的那個——這條是按 MDN 文件寫的，
  **沒在真 Firefox 上跑過**，是發佈前必須實測的一項。

**Firefox 未驗證清單**：真機載入、world:MAIN fetch 門是否真攔、DNR 配額、native host 的 gecko-id
origin 是否如文件所述。骨架（manifest、host 範本、安裝路徑、打包、防漂移測試）都在，真機那一步沒做。
這幾條已經落成一份可執行的驗收清單 [`acceptance-firefox.md`](./acceptance-firefox.md)（F1–F8），並作為
release-gate 的一項「需真機」證據（`AGENTGUARD_EVIDENCE_ACCEPTANCE_FIREFOX`）登記在案——在真 Firefox
上走完並留證據前，它一直顯示為未驗證。

## Safari —— 另一個量級，本環境做不了

Safari Web Extension **不是**換個 manifest 就行的：

- 它必須被一個 **Xcode 工程**包成一個 macOS/iOS **應用程式**（`safari-web-extension-converter` 產生殼子），
  透過 App Store 或簽名應用程式分發——不能像 Chromium/Firefox 那樣載入一個 zip。
- **原生訊息完全不同**：沒有 stdio native messaging host。Safari 走
  `SafariWebExtensionHandler`（一個 App Extension，`NSExtension` 裡的 Swift 類別），擴充功能用
  `browser.runtime.sendNativeMessage` 打到它——`install-host.sh` 那套 manifest 目錄 + stdio 二進位檔在
  Safari 上**完全不適用**。`guard-nm-host` 得改成（或旁邊再寫）一個 Swift 的 handler。
- `world: "MAIN"` 與 DNR 在 Safari 上的支援度還要再核。

**結論：Safari 是設計項，不是能在這個雲端環境裡建置/驗證的東西**（要 macOS + Xcode + Apple 開發者帳號）。
硬塞一個「看起來像 Safari 擴充功能」的目錄進儲存庫，就是這個專案一直在反對的「實作一個不足以支撐其主張的
機制」。所以這裡只給出上面這份如實的形狀說明，不放半成品。真要做，它是一條獨立的、以 Xcode 工程為
中心的工作線，和 iOS 那條（`ios-webshield` 現在是腳手架）天然合併。

## 能力對照（哪層防護在哪個瀏覽器成立）

| 防護層 | Chrome | Edge | Firefox | Safari |
|---|---|---|---|---|
| 掃描（注入/PII/陷阱/付款 CTA） | ✅ | ✅ | ✅（chrome.* 認） | 設計項 |
| DOM 門：submit/CTA 點擊執行前攔截 | ✅ | ✅ | ✅ | 設計項 |
| fetch/XHR 門（world:MAIN，E2.1） | ✅ | ✅ | 🟡 僅 FF≥128，否則如實降級 | 設計項 |
| DNR 名單主機攔截 | ✅ | ✅ | 🟡 配額待校準 | 設計項 |
| 宿主簽名稽核（native messaging） | ✅ | ✅ | 🟡 gecko-id origin 待真機驗 | ❌ 需 Swift handler |

✅ = 機制在、結構測試釘住；🟡 = 機制在但有如實標註的限制/未校準；❌ = 未做。所有 ✅ 都仍受同一條
總限制：**真機端到端未驗證**——這些瀏覽器擴充功能在真實環境裡的行為，本雲端環境跑不到。
