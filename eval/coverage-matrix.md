# Published attack surfaces → AgentGuard coverage

Generated by `guard-cli coverage`. Every rule id and scenario named here is verified to exist, and every scenario is verified to pass — an unbacked claim fails the command.

**30 surfaces: 13 covered, 16 partial, 1 uncovered.** 103 attack scenarios are claimed by a surface, alongside 34 benign false-positive controls.

`partial` means the mechanism exists but is weaker than the published attack, or is a proxy for it; the note says how. Our own numbers are never the papers' numbers — see [eval-methodology.md](./eval-methodology.md) for why the attack-miss-rate we report is not the papers' ASR.

Notes:

- **Pop-up interference (injected between decision and execute)** (partial): Right mechanism, coarse granularity: it compares whole-tree fingerprints, not "is the element under the target coordinate still the intended element", which is what a coordinate-based click redirection actually needs.
- **Viewtree interference (a11y hierarchy diverges from render)** (covered): Requires OCR to have run for the same screen; the native bridge OCRs every 8th frame plus whenever a subliminal band trips.
- **Package-name forgery** (partial): `partial`, not `covered`, for three reasons. (1) **The digest is only as good as the adapter that produced it — and this is now enforced, not just documented.** An adapter that asks the OS (PackageManager on Android, SecCodeCopySigningInformation on macOS) is asking something the agent cannot forge. An adapter that forwards a digest the agent handed it gains nothing at all. This paragraph used to end "the Rust engine reads `signer_sha256` off the event, so the guarantee lives in the adapter, not here". That sentence described a hole and left it open: app signing digests are **public** (`apksigner verify --print-certs`, `codesign -dv`), so an attested digest is an identifier, not a secret, and anyone holding the local API token could present a correct one. Package-name forgery had simply moved one level up — from "pick any package name" to "pick a digest anyone can look up". The engine now refuses to reach `AppIdentity::Verified` unless the assertion arrived through a **verified adapter** (`AdapterIdentity::may_grant_trust`); otherwise it reports `AttestationUnverified`, which is still held to that app's own allow-list but inherits none of its privileges. Evidence *against* an identity — `SignerMismatch`, and a mid-session change of signer — is unaffected by the carrier, which is the same asymmetry the environment-survey rule follows. `app_identity_forged_public_digest` and `benign_flow_verified_task_app` are the attack/control pair; the second declares `via_verified_adapter` and the first is byte-identical without it. What keeps this `partial` rather than `covered` is the consequence: no shipped adapter signs yet, so in the shipped configuration **no app reaches `Verified`** — a real verified identity cannot get through either. That is a functional cost, not a hole, and preflight reports it (`adapter.keys.absent`). See docs/app-identity.md. (2) **The shipped digests are fixtures, not real publisher certificates**, and deliberately obvious ones. A registry pinning a wrong digest is worse than no registry: it looks verified and verifies nothing. A test asserts they stay obvious so that pinning a real value is a deliberate act. (3) **macOS and Windows attestation are not implemented, so enforcement is off by default.** Only the Android companion collects a digest; the desktop shells and the browser host send no attestation, and `require_attestation: true` would block a registered app's own deeplinks there. With it off, identity is resolved and impersonation is still blocked, but an unattested app falls back to the forgeable name match for its allow-list. Both modes are exercised by the corpus (`app_unattested_deeplink` vs `benign_registered_app_unattested`).
- **Image forgery for app identity (cloned icon + name)** (partial): Held at `partial`, and the limits are load-bearing rather than decorative. **Android only, and bounded by package visibility.** The check runs only when an event carries a `package`; macOS, Windows and the browser adapter send none and it does not run there at all. On Android it depends on `PackageManager` being able to see the *observed* package, and a clone is by construction not one of the registered packages — so the companion needs a MAIN/LAUNCHER `<queries>` entry, which it now has, with the privacy trade stated in the manifest. None of that is verified on a device: this repo has no Android CI. **The hash is a tripwire for exact clones, and cannot intervene.** Measured over 30 generated glyphs in the dominant real style (28 comparable), by a test in `guard-schema` so the figures are reproducible from the artifact, unrelated-pair distances run 0–27 (not "near 32"), 6.6% of pairs are within 4 bits, and four pairs hash identically because an 8x8 grid cannot resolve one stroke; the same icon hashed by two producers diverges by up to 4 bits. The distributions overlap, so no threshold separates them, and widening to 256 bits was measured and does not fix it. Hence icon-only evidence is LogOnly, and `lookalike_cloned_icon_only_001` is kept as an attack the corpus counts as a **miss** — attack_miss_rate is 1.1%, not 0.0%. **Containment is not a match**, so a clone named "WeChat Pay" escapes the label rule; 企业微信 / WeChat Work is a real different app whose name contains a registered one. **Only two typo shapes** (adjacent transposition, doubled letter) are matched: a general one-edit rule made Stride, Strive, Stripes, Stripo, Strip, WebChat and Elemi into Critical blocks. **Four-letter Latin names are below the information floor**, so the registry's own AMap is not protectable by label. **A forged package name still collapses this to §3.5's unsolved case.** With no attestation, an app claiming `com.tencent.mm` and wearing WeChat's face is indistinguishable from WeChat; the guard reports `APP-FACE-UNPROVEN` rather than calling it consistent, and that is the most it can do without an authority. **The registry is fixtures**, and an `icon_dhash` is an accusation template rather than a fail-closed pin — a wrong one accuses an innocent app. **The Kotlin producer has no test**: `AppFace.hashGrid` reimplements the pinned algorithm and this repo has no JVM test target.
- **Glitch tokens** (partial): `partial`, and the split between the two halves is the honest part. The **structural** half does not depend on knowing the model, and is what carries the surface: invisible characters (zero-width, soft hyphen, and the Unicode tag block that is today's invisible-prompt-injection vehicle), bidi *overrides* (Trojan Source), Latin words carrying Cyrillic or Greek lookalikes, combining stacks, and oversized tokens. The unifying property is a divergence between what a screen *renders* and what an agent *reads* — worth a finding on its own, because every other check in this engine reasons about the text as a string while the user reasons about it as pixels. The **glitch-token** half is a tripwire, not coverage. A glitch token is a property of one tokenizer's training data; ` SolidGoldMagikarp` is famous because of what GPT-2's BPE did with it, and the equivalent for another model is a string nobody has published. The list is a snapshot of public research and an attacker who reads it picks something else. AgentScan lists this class as unresolved, and a curated list does not resolve it. Precision took two passes. The first version fired on ZWJ emoji (15/15 tested — every family and profession emoji uses U+200D), subdivision flag emoji (which are *tag sequences*, so "the tag block has no legitimate use in UI text" was wrong), Persian ZWNJ (grammatically required), German soft hyphens, ICU/Fluent FSI…PDI interpolation wrappers (every localised app), real JWTs and data: URLs over the 256-char token threshold, and Greek letters used as engineering notation (Δt, μs, Ω). It also had no latch, so forty identical UI deltas produced forty alerts — the lesson this codebase had already written down for APP-UNATTESTED. And the 0.0% false-positive figure was measured on a corpus containing no emoji, no ZWNJ, no soft hyphen, no bidi isolate and no long token at all. All of that is fixed: ZWJ/ZWNJ/soft-hyphen removed, tag runs after U+1F3F4 skipped, bidi narrowed to the two overrides, threshold 2048, Greek dropped, and the finding reported once per class per session at Low severity. Two further corrections worth recording. `FW-TEXT-ANOMALY` at Medium **replaced** any Alert/Low or LogOnly verdict it merged with, so one zero-width character erased a latched APP-UNATTESTED, AGENT-SESSION-MISMATCH or FLOW-DERIVE — permanently, since those latch per session; `merge_keeping_reason` now keeps both reasons whichever wins. And the combining-stack threshold was justified by scripts (Devanagari, Thai) whose marks `is_combining` does not even list, so it works for Zalgo-style stacking and nothing else — stated rather than quietly extended, because a per-script threshold is its own piece of work. Not covered: an *image* of anomalous text (that is agentscan-image-forgery), and anomalies in fields no adapter sends.
- **Log leakage** (partial): `partial`, and the gaps are structural. (0) **The Rust redactors protect developer commands, not users.** `StdinConfirm` is never constructed in this repo and the other four Rust sinks are CLI commands; no shipping desktop or extension path calls `log_safe`. What protects a user today is the Kotlin `LogSafe` on the companion and the audit-row masking from iteration 16. The first version of this entry implied otherwise, and the doc claimed the Rust `println!`s land in logcat — they do not; the companion does not link the engine. (1) **No logcat monitoring.** The paper's framing is an agent leaking *into* the log. We report who can read it and we stop contributing to it; we do not read logcat to see what the agent put there — and we cannot: READ_LOGS is signature|privileged, so the check we would need is the permission we are warning about. (2) **The Kotlin half is untested on device, and mostly inert on API 30+.** `logReaders` compiles against the SDK and is wired through PayloadSerializer, as AppAttestor was in iteration 13, but no CI here runs an Android instrumentation test. Worse for the claim: from API 30 `getInstalledPackages` only returns *visible* packages and the companion deliberately does not request QUERY_ALL_PACKAGES, so on a current device the list is empty because the survey could not look. That is now carried explicitly — `log_readers_enumerable` defaults to false, the clean verdict says the check did not run, and it does not alert (an unavailable check is not a finding). The check becomes real only with QUERY_ALL_PACKAGES, a deployment decision with its own privacy cost. The half that works everywhere is the redaction of our own egress. (3) **Redaction is not encryption.** A masked row still says a payment card was on screen at a time in an app. That is deliberate — it is evidence — but a deployment treating the audit database as non-sensitive is making a mistake this does not fix. SQLCipher via AGENTGUARD_AUDIT_KEY is that answer and is off by default. (4) **The source scanner is a regression guard, not a proof.** It cannot see an alias, a non-print sink (tracing, a file write), or a field name added later. The robust fix is a redacting newtype, which the `HashMap<String, String>` event metadata gives nothing to hang on to. (5) **An environment survey is still forgeable by any local caller.** Scoping the ENV rules to `environment_survey` events stops a *page* from forging one; nothing verifies the event came from the companion, so `api-serve`'s /v1/events (bearer token) or the FFI (no auth) can forge one in either direction — including a clean survey that clears a latched Critical risk. Signing adapter assertions the way agents sign session attestations (iteration 15) is the fix and is not built. (6) **Content markers are still forgeable.** Only the ENV rules are event-scoped. `[AG_TRANSPARENT_OVERLAY]`, `[AG_STEGO_LSB]` and `[AG_UI_REVALIDATE]` match on any event type — content is what they are about — so a page can still claim there is an overlay. The general fix is a separate metadata channel for adapter assertions rather than smuggling them through ui_text; that is a schema change across four adapters and is not built.

Notes:

- **Subliminal visual injection** (covered): Strong band [0.008,0.08) plus a wide band [0.08,0.22) added in iter 6 to cover the paper's upper opacity levels. Luma contrast is a proxy for alpha, so the mapping from a stated opacity to a cell-contrast threshold is calibrated synthetically, not against the paper's rendering.
- **Invisible-zone injection (rounded corners / cutout)** (covered): Corner width formula implemented and unit-tested against the paper's R = 132 → w ≈ 78 at y = 12. Cutout rectangles must be supplied by the host; nothing here reads DisplayCutout automatically.
- **UI spoofing (phishing Activity over a target app)** (partial): Detects a foreground/actor mismatch and off-task apps. Does NOT verify that the Activity on screen belongs to the app it imitates — that needs app identity (signing cert), which is the aura-i gap below.
- **Screenshot tampering in the TOCTOU window** (covered): The ~2 FPS capture stream cannot observe a 50 ms window; the short end of the paper's range needs an on-demand double capture at the point of use.
- **Broadcast input interception (ADB_INPUT_B64)** (partial): Manifest-declared receivers only: an app that calls registerReceiver() at runtime is invisible. Package visibility also caps the list to the two declared actions.
- **Credential sniffing via a foreign accessibility service** (covered): Detection only, and presence is not proof of malice — a legitimate screen reader appears on this list, which is why it alerts rather than blocks.
- **Host-side command injection (shell=True on VLM text)** (partial): Unit-tested in guard-shell rather than as an engine scenario: SafeShell is a host-side gate, not an event on the decision pipeline, so no rule id or scenario applies. Advisory only — see docs/scope-and-non-goals.md.

Notes:

- **Pillar i: agent identity registry / attestation** (partial): `partial`, and the remaining gaps are structural. (1) **Only the session start is signed.** Signing every event would put an Ed25519 operation on the accessibility hot path and no adapter can do it today, so an attacker able to inject events into an already-attested session inherits its attribution. The same shape of boundary as the app attestor's, and the reason §4.4.6's "attribute each *action*" is only half met: attribution is per session, not per action. (2) **No mutual attestation.** The agent proves itself to the guard; the guard does not prove itself to the agent, so an agent cannot tell a real guard from a shim that approves everything. (3) **Replay defence is per-process and bounded.** Consumed nonces live in memory, so restarting api-serve forgets them and the nm-host — one invocation per message — never had them; the window holds the most recent 8192, and eviction beyond it re-admits an old attestation. A persisted nonce store is the fix and is not built. (4) **An event with no session id of its own is attributed to whatever the engine attested.** Attribution is refused for an event naming a *different* session (and reported once as AGENT-SESSION-MISMATCH), but most adapters tag no session at all, and one Engine is conceptually one session's guard while api-serve shares a single Mutex<Engine> across callers. A per-session engine is the fix and is not built. Two claims this note previously made were wrong and are worth recording. It advertised "audit records carry the attribution inside their hashed content" as a strength while the attribution lived in `human_message` — a field many rule messages build from event text — so any event could write an attribution for an agent it had no key for, into an anonymous session, and have it hashed and signed as authentic. And it framed the gap as "an attacker able to inject events into an *already-attested* session inherits its attribution", when an ended session also still lent its own: `agent_session_end` cleared the task allowlist and the task profile but not the identity. Both are fixed (typed `attributed_agent` column; identity cleared at session end and checked against the event's session), and both were found by review rather than by the corpus. Two of the rule ids above are **not** exercised by the corpus, and the corpus cannot exercise them: the eval runner tags every event in a scenario with that scenario's id, so it cannot express an event belonging to another session (AGENT-SESSION-MISMATCH) or one belonging to none (AGENT-SESSION-UNANCHORED). They are proven by unit tests instead — `events_from_another_session_are_not_attributed`, `a_foreign_end_cannot_close_an_attested_session`, `an_invisible_session_id_is_not_an_anchor` — and named here rather than left to look like corpus coverage. Also: `require_attestation` is off in the shipped registry because no adapter signs a session yet — with it off, a forged or replayed attestation is still refused, but an unsigned session proceeds. The shipped keys are fixtures whose private halves are in the repo; a test asserts the registry says so.
- **Pillar ii: semantic firewall (origin tagging, NER PII, context isolation)** (partial): `partial`, and the three gaps are structural rather than a matter of adding patterns. (1) **This is not NER.** There is no model. It recognises entities with *structure* — a checksum, an issuer prefix, a keyword next to a shape — and therefore cannot recognise the classes whose only signal is linguistic: a person's name, a street address, an employer, a medical condition. Where a checksum exists the finding is verified, which is what keeps it from alerting on every 16-digit order number; where none exists (SSN, passport, DOB) the entity is marked unverified and gated on a keyword, and is weaker evidence. (2) **Isolation cannot be enforced, only offered.** AgentGuard does not assemble the agent's prompt, so `wrap` is a primitive a host calls and the guard cannot tell whether it did. The enforced half is detection of breakout attempts in observed content, which needs nothing from the host. `on_context_breakout` is Alert by default for the same reason: whether those bytes are an attack or inert depends on the host's assembly, so the guard names them and lets the taint lattice refuse the critical action either way. (3) **Values are not observed, screens are.** No shipped adapter transmits form field *values* — only `field_id` / `profile_key` / `value_filled`. So entity recognition sees what an app rendered, not what the agent typed, and the `order_note`-with-a-passport case is caught only when the app also displays it. (4) **The label raise has no shipped producer.** It runs from `ingest_untrusted_value`, which needs `value_id` on the event, and no adapter, app, FFI caller or extension emits one — the whole flow lattice is in that position (see aura-iii-taint). So the raise is live for hosts integrating the lattice directly and for the corpus; the half that runs on every real event is FW-BREAKOUT, which needs only ui_text. (5) **Encoding evasions defeat entity recognition.** A PAN whose groups are separated by a non-breaking space (the normal rendering of `&nbsp;`-grouped card numbers), a double space, a newline, a tab, a full stop, an en dash, a zero-width joiner — or written in full-width or Arabic-indic digits — is not recognised. `detect_breakout` normalises its input; `recognise` does not. Also worth recording, because the note previously implied otherwise: the aggregate "attack miss rate 0.0%" does not certify this surface. With the label raise removed, fw_card_on_screen_exfil still counts as intervened on an unrelated Alert while the exfiltration succeeds; the check that carries the claim is that scenario's explicit decision_must_block FLOW-CONF. And a keyword false positive cannot fail any scenario, because unverified evidence never blocks — that precision is pinned by unit tests only.
- **Pillar iii: taint lattice, inheritance, declassification** (partial): Held to `partial`, not `covered`, and the reasons are structural rather than cosmetic. (1) Labels only track values AgentGuard is *told* about. An agent that reads a value off the screen and retypes it from its own context window, emitting no data_derive, is invisible. This is flow control over *declared* flows, not a sandbox — see docs/scope-and-non-goals.md. (2) Aura requires the tag be "cryptographically bound to the content throughout its lifecycle". Ours is a HashMap from memory key to value id inside one process: it survives a save/load round trip, and nothing more. A host that writes to its own store without emitting the event, or restarts, loses the binding. (3) Sink clearance is inferred from the session's `task_apps` declaration and an exact name match — not from a verified app identity. A malicious app that registers the declared name still inherits its clearance. That is the §3.5 / pillar-i gap and is still open. (4) `sink_kind` and the sink name itself are still taken from the event. The *clearance ceiling* is no longer negotiable by the event, but an agent that mislabels a network egress as an app_field gets the app_field ceiling. Closing this needs the adapter, not the policy, to classify the sink.
- **Pillar iii: plan-trajectory alignment** (partial): `partial`, and the gap is the important half of the paper's design. (1) **No per-action justification against the instruction.** Aura's check is a model call: does this action make sense given what the user asked? Ours is structural conformance to a plan an operator wrote — scope, count, order, completion. That catches the label-preserving drift the old string comparison missed, and it needs no model, but it is a weaker claim and cannot judge an action the plan happens to permit for a purpose the user never had. (2) **The plan is a step-kind grammar, not a trajectory model.** There is no notion of *which* room was booked or *whose* card was used, so an agent that books the wrong hotel conforms perfectly. (3) **Alert by default** (`on_plan_drift`). A new plan library is the easiest thing here to get wrong in the direction that costs users their work: an over-strict order clause stops a real booking mid-flow. Alerting first lets an operator see what their plans reject before it costs anyone a task. (4) **`require_plan: false` by default**, so a profile nobody has planned runs unconstrained after a one-time report. Failing closed would block every profile an operator has not yet written, which means the library never gets adopted. (5) **A step kind a rule does not declare is invisible to a budget.** Payments are enforceable because CRIT-001/CRIT-002 carry `step_kind:`; a deployment that writes its own rules for a critical action and omits the annotation gets a plan that reads as a constraint and counts nothing. A test asserts the shipped rules and plans agree, but nothing checks an operator's.
- **Pillar iv: non-deniable, attributed audit** (partial): Verified by unit tests and `make audit-signing-demo` rather than by engine scenarios. Key lives on the same disk, so a compromised host can re-sign; truncation is only caught by the out-of-band head witness. Reasoning traces and screen-state references are not logged.
- **Session-scoped least privilege (SA session token constrained to S_max)** (partial): Held at `partial`. **The ceiling is only as good as the plan.** A profile with no `scope:` is unconstrained, and that default is deliberate — failing closed would deny every task an operator has not yet scoped, which means the field never gets adopted, the same reasoning as `require_plan: false`. So an unplanned or unscoped session has no resource ceiling at all, and the shipped library covers four profiles. **A ceiling is a policy statement, and getting it wrong denies legitimate work.** The first draft of the shipped scopes invented key names the project's own `GuardContract` vocabulary does not use, and turned nine existing benign scenarios into Critical blocks; a second error left Meituan out of `book_hotel`, which is wrong in this market. Both were caught by the corpus, which is the argument for having one. **No semantic permissions beyond these three dimensions.** Aura's model is domains plus semantic permissions; this is apps, profile keys and hosts. There is no scope over deeplink schemes, clipboard use, or which *fields within* an app may be written. **The request channel is unauthenticated**, and "narrowing is harmless" was too strong: a request on a dimension with no ceiling used to be *installed* as the grant, which turned a bogus request into a block storm and, under `--confirm deny`, a paused engine. Requests are now ignored where there is no ceiling. The residue is that a narrowing is not attributable to the agent unless the session is attested. **Nothing declares a task unless a host or human chooses to.** The mechanism was first reachable only from the eval harness — every adapter's `start_session` sent empty metadata, so four hosts loaded the plan library and none could select from it. Now wired via `TaskDeclaration` / `start_task_session`, the envelope's `session_start` kind, both desktop shells (plan library + task selector) and `guard-cli replay`. Still: the default in every shell is unscoped, `guard-nm-host` has no session concept, and the desktop shells cannot be compiled in this environment so their wiring is parse-checked rather than run. **Nothing enforces that the grant was minimal.** A plan may declare a wide scope, and the guard has no way to know the task did not need it; least privilege is expressible here, not provable.
